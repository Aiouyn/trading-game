## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Goal
The Stabilizer Board of the Exchange is the only definition of the Stabilizer (ruling R04; 04 §3.17 references it). It is a deterministic PI controller that runs once per game day. Its input is the log of the activity-weighted median of engaged characters' NWrank divided by the designed wealth curve `W_target(age)` (03 §3.7.2). It moves four levers that act only on FAUCET and SINK flows:
- L1 NPC demand;
- L2 lifestyle and NPC-service price index;
- L3 high-volume transaction levy;
- L4 upkeep index.

Each lever has a range and a daily step. The controller has OBSERVE and ACTIVE modes, guards and alerts, and publishes the public Money Supply Report every game day plus the Stabilizer and Exchange Report every chapter. It never names a player and never touches prices, rates, taxes, fines, start cash, ads, grants, compute spot or any individual.

The same aggregation computes the Money Supply Index and NWI = NWrank / MSI (03 §3.8).

## Implementation steps
1. **Target curve** (03 §3.7.2).
   - `wTarget` interpolates `ln W` linearly in age between the table points: 0 → 5,000; 1 → 15,000; 7 → 500,000; 21 → 20,000,000; 56 → 300,000,000; 180 → 2,000,000,000; 365 → 6,000,000,000. Past 365 real days it is `6e9 × (1 + stab_target_growth_after_year)^(age − 365)`.
   - Age is in world-time real days (ticks / 17,280) since the character's `createdTick`.
   - All math uses dmath, so it is deterministic.
2. **Sample** (each partition, P13 post-commit at t = 719, after T03-17's NWrank).
   - For each chr:
     - `w = activityWeight(daysSinceActive)`, from `LAST_ACTIVE_TICK`;
     - the chr is engaged when `isEngaged` holds (`ACTIVE_DAYS` has ≥ `stab_engaged_min_active_days` distinct days in the last 168) and its age is ≥ 1 real day;
     - `q = NWrank_FDL / wTarget(age)`.
   - Also collect:
     - `designWeightedAll = Σ_all w × wTarget(age)`, over every character, for MSI;
     - `designWeighted`, the same sum over the engaged set, for the inflation guard;
     - the PEM in FDL (Σ ccy translated, T03-17);
     - `M0_sys` in FDL;
     - `N_a` (T03-11);
     - the per-chr NWrank map, used only for MSI and NWI and never published.
   - Send the sample to `STAB_HOME_ID` with `'NEXT'`. It arrives at COORD in R1 of t = 0 of the next day.
3. **Controller** (`runStabilizer`, COORD, P2 of DAY_OPEN). The spec's run "at t = 719 with effect from t = 0" becomes a run at t = 0 on the samples from t = 719, which have the same effect timing. The run:
   - Merge the samples sorted by `(partitionId)`, then entries by id. `e = ln(weightedMedian(engaged))`. An empty sample gives `e = 0`.
   - **Mode.** OBSERVE if `dayIndex − launchDay < stab_observe_game_days`, or if the engaged count is < `stab_min_sample`. Otherwise ACTIVE.
   - **Deadband** with `db = stab_deadband`: `eEff = |e| ≤ db ? 0 : e − sign(e) × db`.
   - **Saturation** means every lever is at the bound it would move toward for the sign of `eEff`. When `u > 0`, tightening moves L1 down and L2, L3 and L4 up; when `u < 0`, the reverse.
   - **Integral.** If not saturated, or if `sign(eEff) ≠ sign(I)`: `I = clamp(I + eEff, −stab_integral_max, +stab_integral_max)`. In OBSERVE, `I` stays 0.
   - **Output.** `u = clamp(stab_kp × eEff + stab_ki × I, −1, 1)`.
   - **Lever targets** (`LEVER_SPEC`, ranges and steps from `stab_lever_ranges`):
     - L1 = `1 − 0.10u`, range [0.90, 1.10], step 0.005;
     - L2 = `1 + 0.25u`, range [0.90, 1.25], step 0.005;
     - L3 = `0.5 + 1.5u` bp, range [0, 3.0], step 0.1;
     - L4 = `1 + 0.15u`, range [0.95, 1.15], step 0.003.
   - **Lever moves.** OBSERVE: levers held at neutral (L1 1.00, L2 1.00, L3 0.5 bp, L4 1.00); targets are still published. ACTIVE: `stepLevers` moves each lever toward its target by at most its step, then clamps it to its range. Values are rounded to 1e-9 to keep float state canonical.
   - Write `led.stab` (with history trimmed to 364 days) and `led.stablever` (`fromTick = tick`), and emit `stab.lever.changed` `{ lever, from, to }` PUBLIC for each lever that changed.
4. **Lever application by owners.** The levers are read with `leverValue`, and 03 itself applies none of them:
   - L1: 09 city demand pools; 10 elastic rent at half strength (`rentDemandMultiplier`). Listed NPC companies' modelled revenue is not affected, so share prices are never steered.
   - L2: 14 lifestyle catalog, NPC club dues and hosting; 16 Terminal/data tiers; 06 NPC auction fees; 09 NPC service prices and the catalog `c0` of new businesses; 10 NPC property services. Shown to players as the "Luxury CPI".
   - L3: 05 charges `MKT_TRANSACTION_LEVY` on a consolidated group's exchange notional above `levy_free_daily_notional` per game day.
   - L4: upkeep in 09, 10 and 14.
   `LEVER_READERS` documents these readers, and T03-28 exports them.
5. **Guards** (03 §3.7.6), as `stab.alert`, internal (ops):
   - `|e| > 0.5` for 28 consecutive days → `STRUCTURAL_IMBALANCE`. The Stabilizer keeps acting within its ranges.
   - Over the current chapter, the growth of `M0_sys / N_a` above 2× the growth of `designWeighted / N_a` → `INFLATION`.
   - ρ (T03-11 `rho` over the rolling game year of FlowDays, merged from the samples' partitions) below 0.75 or above 1.0 for 28 consecutive days → `RHO_BAND`. The §3.6 family bands go out of range (`familyBandCheck`) → `FAMILY_BAND`, reported in the same alert.
   - Lever values are state, not params. Changes to gains or ranges follow 02 §3.18 (param versioning).
6. **MSI** (03 §3.8, COORD at the same run):
   - `raw = PEM_FDL / (msi_money_share × designWeightedAll)`;
   - `ema += MSI_ALPHA × (raw − ema)`, with `ema` starting at `raw` on the launch day;
   - while `dayIndex − launchDay < stab_observe_game_days` (168): `MSI = 1.000` and `emaBaseSum += ema`, `emaBaseN++`;
   - at the end of that period, `emaBase = emaBaseSum / emaBaseN`;
   - afterwards, `MSI = clamp(ema / emaBase, MSI_prev × 0.995, MSI_prev × 1.005)`;
   - the published value is rounded to 4 decimals and emitted as `msi.updated` `{ msi, raw }` PUBLIC.
   - `nwi(id) = NWrank / MSI`, using the 4-decimal MSI as an E4 integer, half-even. Boards (15) show it with the label `real`.
7. **Reports** (03 §3.7.7).
   - **Daily** `stab.daily.report` PUBLIC with `MoneySupplyReport`: M0, M0_sys and M2 per currency; PEM and PEW (Σ NWrank of players in FDL); N_a; e; u; levers and their change; families for the day and the rolling year; ρ; MSI; mode.
   - **Chapter**, at CHAPTER_CLOSE: the Stabilizer and Exchange Report, built from history, `led.flowday`, and facts from 07 (CCP default-fund usage, systemic indicators), 08 and 21 (exploit-fix history).
   - Individual players are never named: no ids are present in any report payload, and a test asserts this.

# SPEC EXCERPTS (verbatim; binding game rules)

**[03 §1 Purpose]** (context)

## §1 Purpose

The ledger is the game's first law: **every unit of money and every unit of every asset exists on exactly one balance sheet, and moves only by a posting with a reason code**. This module defines:

1. the entity kinds and the balance sheet each one carries;
2. the full chart of accounts;
3. the double-entry posting model, its standard templates (pay, mint, burn, lend, revalue, FX) and the payment rail across settlement cash, bank deposits and partitions;
4. the complete reason-code catalog of the game, each code in exactly one class (FAUCET, SINK, TRANSFER, CREDIT_CREATE, CREDIT_DESTROY, REVALUE);
5. money aggregates (M0, M2, player-economy money and wealth), the faucet and sink inventory with target ratios, the **Stabilizer** PI controller, the **Money Supply Index (MSI)** and the **Net Worth Index (NWI)**;
6. valuation (marking) rules for every asset type, including illiquid ones;
7. consolidation of ownership chains, minority interests and intercompany elimination;
8. taxes in the five blocs and the Isla Serena free zone;
9. financial statements generated for every entity;
10. insolvency and bankruptcy accounting;
11. the invariants asserted every tick.

Design stance: real accounting where it creates gameplay (balance sheets, consolidation, taxes, credit creation, insolvency), simplification only where it would be invisible (no accrual-vs-cash tax timing nuances beyond those listed, no lease accounting standards). The ledger is also the evidence base for courts (13), the explanation base for "Why it moved" (18) and the data base for the Truth Machine (20).

#### §3.7.1 What it is

A diegetic institution, the **Stabilizer Board of the Exchange**, implemented as a deterministic controller that runs once per game day in the day-close hook (P2 at t = 719; lever changes take effect from t = 0 of the next day). It acts **only** on FAUCET and SINK flows (00 §5.4) through four levers. It never touches market prices or the price model, interest rates (04), taxes and tax brackets (04 fiscal; 01 §8.2 lever 2 is therefore removed), fines (13), start cash, ads or grants (fixed by L12 and 18), the compute spot price (single floating price, RESOLVED C3) or any individual player. Equity drift (01 §8.2 lever 1, second half) is also removed: the price model stays explainable (01 §0.1).


<!-- excerpt 03§3.7.2 -->
**[03 §3.7.2]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.7.2 Input: the wealth-tracking error

```
For each character i with engaged(i) (below) and accountAgeRealDays(i) >= 1:
   q_i = NWrank_i / W_target(age_i)                // NWrank in nominal FDL, §3.10
e = ln( weightedMedian(q_i, weight = w_i) )        // w_i = exp(-days_since_last_active/7)
```

- `engaged(i)`: at least `PARAM.stab_engaged_min_active_days` (DEFAULT 7) distinct game days with an accepted human (UI or API) intent in the last 168 game days (7 real days). Computed from state, so deterministic.
- `W_target(age)` is the designed median-engaged wealth curve from 01 §8.4 and §14.3, interpolated log-linearly in age (real days since the character's creation, measured in world time = ticks / 17,280):

| Age (real days) | 0 | 1 | 7 | 21 | 56 | 180 | 365 | > 365 |
|---|---|---|---|---|---|---|---|---|
| W_target (FDL) | 5,000 | 15,000 | 500,000 | 20,000,000 | 300,000,000 | 2,000,000,000 | 6,000,000,000 | × (1 + `PARAM.stab_target_growth_after_year` (DEFAULT 0.001)) per real day |

- If fewer than `PARAM.stab_min_sample` (DEFAULT 200) engaged characters exist, the Stabilizer is in OBSERVE mode.


<!-- excerpt 03§3.7.3 -->
**[03 §3.7.3]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.7.3 Controller

```
deadband: e_eff = 0                       if |e| <= db            (db = PARAM.stab_deadband = 0.05)
          e_eff = e - sign(e) * db        otherwise
integral: if not (saturated in the direction of e_eff) or sign(e_eff) != sign(I):
              I = clamp(I + e_eff, -Imax, Imax)                    (one game day per step; Imax = PARAM.stab_integral_max = 10)
output:   u = clamp(Kp * e_eff + Ki * I, -1, 1)                    (Kp = PARAM.stab_kp = 0.5, Ki = PARAM.stab_ki = 0.02)
```

`u > 0` means players are richer than designed: tighten (less demand, higher lifestyle prices, higher levy, higher upkeep). `u < 0`: loosen.

### §3.8 Money Supply Index (MSI) and Net Worth Index (NWI)

The NWI is the ranking metric (00 §4): net worth in **real** terms, so that "a dollar in year 3 is worth the same as on launch day" (01 §0.6).

```
design_money(t) = κ · Σ_i w_i · W_target(age_i)          over all characters (not only engaged), κ = PARAM.msi_money_share = 0.20
raw(t)          = PEM_FDL(t) / design_money(t)            (actual player money relative to designed money for this population)
ema(t)          = ema(t-1) + α · (raw(t) − ema(t-1)),     α = 1 − 2^(−1/28)  (half-life 28 game days), daily at day close
MSI(t)          = clamp( ema(t) / ema_base, MSI(t-1)·(1 − 0.005), MSI(t-1)·(1 + 0.005) )
ema_base        = mean of ema over the world's first 168 game days; MSI = 1.000 during that period
NWI_i(t)        = NWrank_i(t) / MSI(t)
```

- Reading: MSI = 1.10 means players hold 10% more money than the design path for a population of this age profile; every nominal dollar of net worth then counts as 0.909 "real" dollars on the boards.
- MSI is published daily with 4 decimals. Boards show NWI in "real $" with the label `real`; personal screens show nominal NW first and NWI second (17).
- Seasonal ladders (15) use NWI deltas exactly as 01 §14.4 defines.
