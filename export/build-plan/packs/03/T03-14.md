## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Goal
This task turns marks into book values. At day close, and on the slower cadences of 03 §3.9.2, it posts the revaluations that make the ledger's book value of each position equal its valuation rule. The steps are:
- mark-to-market of marketable positions (03 §3.3.8);
- expected-credit-loss provisions (§3.9.3);
- property, private-stake and collectible appraisals, with the revaluation-surplus routing of §3.9.4 and recycling on disposal;
- straight-line depreciation and amortization schedules;
- impairments to replacement cost or to the look-through value (models, goodwill).

Each step is a pure function of committed state plus marks. It queues ACCRUE entries through `ctx.ledger` in P2, and they commit in P13 of the same tick. T03-15 sequences the steps in the 03 §3.15 order. Tax basis is independent of every posting here: lots (T03-20) never read book value.

## Implementation steps
0. In T03-01's `LedgerFactKind` union, add four kinds. They are 03-owned fact names, so the edit stays inside unit 03:
   - `HELD_FOR_USE`: subject propId or the asset account key, value boolean, written by 10 or 09;
   - `APPRAISAL_EVENT`: subject propId or itemId, value `{ tick, kind: 'DISTRICT_SHOCK' | 'RENOVATION' | 'CONDITION' | 'AUCTION' }`, written by 10 or 06;
   - `REPLACEMENT_COST`: subject modelId, value Money string, written by 11;
   - `MODEL_IMPAIRMENT_PCT`: subject modelId, value fraction, written by 11.
   Every step reads its inputs from committed state (`ctx.read`) and marks. It writes only `led.sched`, `led.appr`, `led.goodwill` and `led.vrun`, and queues entries with `ctx.ledger.accrue` / `ctx.ledger.reclass` (requestedBy module '03'). Each `run*` function first checks `led.vrun[id].lastDay === ctx.cal.gameDay`. If they match, it returns `[]`; this guards against a second run in the same day, such as a halt and resume (03 §8 edge 11). Otherwise it sets `lastDay`. Entities are iterated in sorted id order and accounts in sorted key order, so the ids that `ctx.newId` assigns are deterministic. Each partition processes only the accounts its store holds. Skip entities in status DISSOLVED. Skip entities `IN_INSOLVENCY` only for appraisals that would raise value: the insolvency administrator keeps marks, and T03-25 applies recovery marks.
1. `accountsByCode`: read the `byCode` index of `led.account`, filter to `balance !== 0n || qty !== 0n`, and sort by key.
2. `mtmDeltaFor(read, a, params)`:
   - `target = closeMarkValue(read, a, params)` from T03-13, which is qty × the official close or the day-close mark of the 03 §3.9.2 row.
   - Return `undefined` in these cases:
     - the mark is missing, or `effectiveMark(...).stale` / halted (STALE marks keep the book; the next valid close catches up);
     - a.code is 1220 with sub `OWNED`, or for hardware (cost basis). RESERVED compute and OWNED compute credits are marked;
     - a.code is 1600 or 2600 when the position is cleared, i.e. its mark row has source `CLEAR` (set by 06). Cleared derivatives are carried at 0 after VM;
     - a.code is 1870 and the mark source is not `INDEX`. Those items go to the appraisal step.
   - Otherwise return `target − a.balance` for assets. For 2600 (a credit-normal liability whose balance is negative), return `−target − a.balance`; a positive result means the liability fell, which is a gain.
3. `runMarkToMarket`: for each code in `MTM_ACCOUNTS` and each account from `accountsByCode`, compute `d = mtmDeltaFor`.
   - If `d > 0n` (gain), post `ctx.ledger.accrue(E, d, ccy, 'LED_MTM_DAILY', a.code, 4070, { sub: a.sub })`, which is Dr asset / Cr 4070.
   - If `d < 0n`, post `accrue(E, −d, ccy, 'LED_MTM_DAILY', 5170, a.code, { sub: a.sub })`.
   - For 2600 the legs are mirrored: a gain is Dr 2600 / Cr 4070 and a loss is Dr 5170 / Cr 2600.
   - When the entity's class rule `revaluationTarget(entity, a.code, false)` returns OCI (never for these codes), throw `LEDGER_BUG`. Marketable assets always revalue through P&L (03 §3.9.4).
   - Return the totals. After commit, `book === closeMarkValue` for every revalued account (03#12).
4. `intradayMarkValue(read, a, tick, params) = a.balance + (valueAt(mark_now) − valueAt(mark_close))`. It uses `valueAccount` (T03-13) at `tick`, minus `closeMarkValue`; when either is undefined it returns `a.balance`. Nothing is posted (03 §3.3.8).
5. Schedules.
   - `registerSchedule` validates that the account exists, that the code fits `kind` (DEPRECIATION: 1830, 1840, 1850, 1880; AMORTIZATION: 1700, 1710, 1720, 1740), and that no ACTIVE schedule exists for the same account key. If the spec is invalid, it calls `ctx.reject('LED_BAD_SCHEDULE', ...)` inside an intent, or throws `LEDGER_BUG` from engine code.
   - Default `lifeDays`:
     - 1700: `ctx.params.num('model_useful_life_game_days')`;
     - 1710: `DATASET_LIFE_GAME_DAYS`;
     - 1740: `CHAPTER_GAME_DAYS`;
     - 1720 and 1830–1880: a value is required, because the licence term (11) and the useful life (09/11) come from the caller.
   - `startDay` defaults to today. `endDay = startDay + lifeDays`.
   - `dailyCharge(nb, salvage, n) = n <= 1 ? max(nb − salvage, 0n) : max(0n, divHalfEven(nb − salvage, n))`. Here `remainingDays = endDay − today`, and the final day takes the remainder, so the total charged equals the base exactly. Impairments posted by any module lower `netBook`, so later charges shrink automatically.
   - `runSchedules`, for each ACTIVE schedule:
     - If `netBookOf` is ≤ salvage or the asset balance is 0 (disposed), set the status to DONE or CLOSED respectively.
     - Otherwise, if `lastChargedDay < today`:
       - DEPRECIATION posts `accrue(E, c, ccy, 'LED_DEPRECIATION', 5120, 1839, { sub: `${assetAcct}:${sub}` })`, where the contra sub is `<assetAcct>:<sub>` (the "matching sub" of the chart row 1839);
       - AMORTIZATION posts `accrue(E, c, ccy, 'LED_AMORTIZATION', 5130, assetAcct, { sub })`.
     - Set `lastChargedDay = today`. If `today >= endDay − 1`, set DONE.
   - Missed days are not back-filled one by one. The remaining-base formula spreads them over the remaining days, so the total is preserved.
   - 1860 lifestyle durables (14, `LED_LIFESTYLE_DEPRECIATION`), 1200 inventory (09, `LED_INVENTORY_WRITEDOWN`), 1221 restricted compute (11, `LAB_COMPUTE_EXPIRY`, marked 0) and model decay (11, `LAB_MODEL_DECAY`) are posted by their owner modules in their own boundary hooks. This module never posts those codes.
6. `runReplacementCaps` (1700). Per model account, in this order:
   - if the fact `MODEL_IMPAIRMENT_PCT` for the modelId is > 0 and not yet applied today, post `LED_IMPAIRMENT` (Dr 5140 / Cr 1700:<modelId>) for `toMoney(fromMoney(book) × pct)` and clear the fact;
   - then, if `book > REPLACEMENT_COST`, post `LED_IMPAIRMENT` for the excess.
   The impairment lowers the schedule's net book, so later amortization uses the new base.
7. Appraisals (`runAppraisals`):
   - **Property, 1800**, for each account. The appraisal value is `valueAccount(read, a, tick, params).value`, using 10's APPRAISAL mark.
     - It is due when `today − lastDay >= ctx.params.num('prop_appraisal_cadence_game_days')`, or when an `APPRAISAL_EVENT` exists with `tick > lastDay` start tick.
     - Apply `next = appraisalCap(prev = book, value, event)`, where `appraisalCap` clamps to `[prev × 0.85, prev × 1.15]` (via `toMoney`, half-even) unless an event triggered the appraisal.
     - Route with `revaluationTarget(entity, 1800, getFact('HELD_FOR_USE', propId) === true)` and call `postRevaluation(..., 'LED_APPRAISAL', route)`.
   - **Collectibles, 1870**, whose mark source is not INDEX: re-appraise daily to `valueAccount` when an arm's-length auction result (`APPRAISAL_EVENT` kind AUCTION) re-based the multiple. Otherwise keep the last appraisal value, multiplied by the change in the category index.
   - **PE/VC stakes, 1570**: only when `ctx.cal.boundaries.has('QUARTER_CLOSE')`, the target is `qty × peMark(row, tick, ctx.params.num('pe_mark_decay_per_quarter'))`, capped by the 09 valuation and preference-adjusted (T03-13 computes this). Route 'PNL'.
   - `postRevaluation(ctx, a, target, code, route)` works on `d = target − book`:
     - **Route 'PNL'**: if `d > 0`, post Dr asset / Cr 4070; if `d < 0`, post Dr 5170 / Cr asset.
     - **Route 'OCI_3400'** (03 §3.9.4: excess above cost goes to 3400):
       - `S = appr.surplus` and `cost = book − S`;
       - `S* = max(0n, target − cost)`;
       - `oci = S* − S` and `pnl = d − oci`;
       - post `oci` as Dr asset / Cr 3400 (or the reverse when it is negative), with `valueLegB` 3400;
       - post `pnl` as above;
       - set `appr.surplus = S*`.
     - Both legs go in one entry when both are non-zero: use `ctx.ledger.accrue` twice with the same `refs: [a.key]`; atomicity per tick is guaranteed by P13.
     - Update `lastValue` and `lastDay`.
   - Characters and alliances always route 'PNL' (`revaluationTarget` returns PNL for them).
8. `recycleSurplusOnDisposal`: for each `led.appr` row with `surplus > 0n` whose account balance is 0 and qty is 0 (disposed in the day), post `ctx.ledger.reclass(E, surplus, ccy, 'LED_RECLASS', 3400, 4070)` (recycling to P&L, 03 §3.9.4), set `surplus = 0n` and delete the row.
9. ECL (`runEclProvisions`):
   - Gather `rows` from all registered sources. Drop rows where `rootOwnerOf(borrower) === rootOwnerOf(lender)`: intercompany receivables are carried at face (03 §3.9.2) and are eliminated in consolidation.
   - Group by `lenderId|portfolioId|ccy` and compute `target = eclAllowance(inputs)`.
   - Read `current = −committedBalance(accountKey(lender, 1309, portfolioId, ccy))`; 1309 is a contra-asset with a credit balance.
   - Post `accrue(lender, target − current, ccy, 'LED_ECL_PROVISION', 5150, 1309, { sub: portfolioId })`. A negative amount is a release; ACCRUE swaps the sides (T03-07).
   - Charge-offs (`BNK_LOAN_CHARGEOFF`) are posted by 07 on default resolution and reduce `current` before the next run.
   - Lenders with no rows today and a non-zero allowance release it to 0, because the portfolio was repaid.
10. Goodwill (`runGoodwillImpairment`, YEAR_CLOSE only): for each `led.goodwill` row:
    - `carrying = navAtAcquisition + committedBalance(owner:1730:<acquisitionId>)`, which is the acquisition cost less goodwill impaired so far (1580 itself is carried at look-through, so it cannot be the carrying value);
    - `lt = valueAccount(read, <owner:1580:entityId account>, tick, params).value` (look-through NAV, T03-16);
    - if `lt < carrying`, post `LED_IMPAIRMENT` (Dr 5140 / Cr 1730:<acquisitionId>) for `min(balance 1730, carrying − lt)`;
    - delete the row when the 1730 balance reaches 0.
11. Every posted entry has `memo` set to the step name (`mtm` / `ecl` / `appraisal` / `schedule` / `cap` / `goodwill` / `recycle`) for statements and the "Why it moved" view.

# SPEC EXCERPTS (verbatim; binding game rules)

**[03 §1 Purpose]** (context)

## §1 Purpose

The ledger is the game's first law: **every unit of money and every unit of every asset exists on exactly one balance sheet, and moves only by a posting with a reason code**. This module defines:

1. the entity kinds and the balance sheet each one carries;
2. the full chart of accounts;
3. the double-entry posting model, its standard templates (pay, mint, burn, lend, revalue, FX) and the payment rail across settlement cash, bank deposits and partitions;
4. the complete reason-code catalog of the game, each code in exactly one class (FAUCET, SINK, TRANSFER, CREDIT_CREATE, CREDIT_DESTROY, REVALUE);
5. money aggregates (M0, M2, player-economy money and wealth), the faucet and sink inventory with target ratios, the **Stabilizer** PI controller, the **Money Supply Index (MSI)** and the **Net Worth Index (NWI)**;
6. valuation (marking) rules for every asset type, including illiquid ones;
7. consolidation of ownership chains, minority interests and intercompany elimination;
8. taxes in the five blocs and the Isla Serena free zone;
9. financial statements generated for every entity;
10. insolvency and bankruptcy accounting;
11. the invariants asserted every tick.

Design stance: real accounting where it creates gameplay (balance sheets, consolidation, taxes, credit creation, insolvency), simplification only where it would be invisible (no accrual-vs-cash tax timing nuances beyond those listed, no lease accounting standards). The ledger is also the evidence base for courts (13), the explanation base for "Why it moved" (18) and the data base for the Truth Machine (20).

#### §3.3.8 Mark-to-market postings

At day close (P2 hook, postings in P13) every position in a marketable asset (1500, 1510, 1520, 1530, 1540, 1541, 1542, 1560, 1600/2600 uncleared derivatives, 1210, 1220 OWNED excluded (cost), 1870 when index-marked) is revalued to the day-close mark: `ACCRUE(E, |Δ|, LED_MTM_DAILY, dr=asset, cr=4070)` for gains or `dr=5170, cr=asset` for losses. After this, the account's book value equals `qty × close mark`. Intraday, NW uses `book + qty × (mark_now − mark_close)` without postings. Illiquid assets revalue on their own cadence (§3.9).

#### §3.9.3 Expected credit loss (loans, receivables)

`allowance = Σ_loans EAD × PD_12m × LGD` for performing loans and `EAD × LGD` for defaulted ones; PD from the borrower's rating or 07's scorecard, LGD from collateral (07). Updated daily with `LED_ECL_PROVISION`. Charge-off on default resolution with `BNK_LOAN_CHARGEOFF`.

**[03 §3.9.4]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.9.4 Revaluation surplus vs P&L

Companies holding property for their own use and intangibles carried above cost book the excess in 3400 (OCI) and recycle it to P&L on disposal. Everything else revalues through P&L. Characters have no OCI: every revaluation is P&L. Net worth includes both.
