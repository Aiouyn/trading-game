## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

   - Entry ids are content-addressed so that they do not depend on the partition count (INV-ENG-009): `newEntryId = () => entryIdFor(tick, module, phase, seed, n)`. `seed` is the template's first party id plus the code, and `n` counts the previous ids with the same `(tick, module, phase, seed)` on this partition. An entity's actions for one module and phase always run on that entity's home partition, so `n` is identical for every partition map. If 02 later exposes its IdFactory to `apiFor`, switch to `newId('ent')` (reconciler item).
   - `bookValueOf` comes from the committed account balance and qty (`divRoundHalfEven(balance * qty, accountQty)`).
   - `rail = railStateFor(rt)`.
2. Every G7 write method calls the matching `tpl*` builder (argument order exactly as G7), sets `fixedSources` from the hold's parts when `o.holdId` is given (holdId must exist, be ACTIVE and belong to the payer; else invalid `INV-BS-011`), pushes the entry to the queue and returns `entryId`. Invalid entries are pushed too (P13 records them so the TICK invariants fail; in safe mode, also add the culprit `{ invariantId: entry.invalid.invariantId, entityIds }` to the partition's failure list that `prepare` returns, so 02's safe-mode trace attributes it (02 §3.15.3 step 1)). Postings never commit before P13 (03 §3.3.2 rule 4).
3. Reads (committed state; queued entries are not included, G7): `balance(key)` = committed balance; `cash(e, ccy)` = Σ balances of e's money accounts in ccy (1001 including RESTRICTED subs, 1002, 1003, 1010); `available(e, ccy)` = Σ `spendable` over the unrestricted money accounts (restricted lots excluded: G7 callers that may use restricted cash call `availableFor`); `availableFor(e, ccy, code)` adds restricted lots when `catalog.get(code).restrictedOk`; `position(e, asset)` = Σ qty of e's accounts with that assetId (non-MEMO, issuance accounts excluded); `availableQty` = position − Σ active qty holds; `netWorth(e)` = installed `NetWorthFn`.
4. **Port.**
   - `ledgerProvider.createPartition(id, store)` returns a new `LedgerPartitionImpl` and keeps a module-level map `id -> partition` (for `globalCheck` and tests).
   - `apiFor(module, phase, tick)` returns the G7 impl and `createHoldApiImpl(rt)` over the partition's `TickQueue` of that tick. The queue is created lazily when `queue.tick !== tick`; a queue of an earlier tick that was never committed or rolled back is a `LEDGER_BUG`.
   - **Port holds.** `HoldApi.get` maps 03's `Hold` (T03-01, with `parts[]`) to the port `Hold`: `account = parts[0].accountKey`, `amount = Σ remaining`, `purpose = purposeCode ?? ref`. `placeQty`, `release` and `reduce` are the T03-08 implementations.
   - **`outgoingLegs()`** (called by 02 after R3):
     - for every queued entry not invalid, and every posting whose two accounts belong to entities with different `partitionId`, emit one `PostingLeg { entryId, legId: entryId + ':' + seq, fromPartition: this, toPartition: remote, body: LegBody }`;
     - mark the posting as split (`legOf`), so that `commitTick` applies only the local side, against `sys_SYSTEM:9900:<local>-><remote>:<ccy>`;
     - entries queued after this call (in P13) must be intra-partition. A posting that would need a split after `outgoingLegs` marks the entry invalid with `INV-LED-012 xpart_after_B3` (the P13 rules of T03-15 keep this from happening).
   - **`acceptLegs(legs)`** buffers the incoming legs for this tick, sorted by `(fromPartition, legId)`.
   - **`runP13(ctx)`**, invoked by the 03 ModuleDef's `phases.P13`, does in order:
     - the pre-work: restricted releases (T03-12), close stage `P13_PRE` and the facility conversion of co-located banks (T03-15);
     - `commitTick(rt, incomingLegs, ctx.emit)`;
     - the post-work: money update (T03-11), ownership (T03-16), period totals, intercompany and related parties (T03-18), rail changes and close stage `P13_POST` (T03-19), NWrank (T03-17).
     It caches the result for the tick; the order is fixed in T03-28.
   - **`prepare(tick)`**:
     - if `runP13` did not run this tick (the hook is missing), run `commitTick(rt, incomingLegs)` without `emit`, and report one failure `LED_P13_HOOK_MISSING`, with ok still true so the ALERT surfaces;
     - return `{ ok: true, failures, suspense, postings }`. `suspense.pairs` are the balances of every `sys_SYSTEM:9900:<a>-><b>:<ccy>` account of this partition. `postings` are the committed postings of the tick in port shape (`{ tick, entryId, debitAccount, creditAccount, amount, ccy, reason, refs }`).
     - The FATAL 03 invariants are evaluated by 02's invariant run over the registered InvariantImpls, not here.
   - **`commit(tick)`** drops the queue and the leg buffers; the store commit is 02's pointer swap.
   - **`rollback(tick)`** drops the queue, the legs and the cached result. Safe-mode replays re-run the phases, which rebuild the queue deterministically.
   - `queryPostings` and `balance` delegate to `ledgerTestHooks` over the partition store.
   - `snapshotRows()` returns `[]`: every 03 table is an ordinary store table and is already in 02's snapshot.
   - **`globalCheck(reports)`** (COORD, R5): for every pair `(a->b, ccy)`, `balance(a->b) + balance(b->a) === 0n` (I13, `INV-LED-005`); otherwise `{ ok: false, failures: [{ invariantId: 'INV-LED-005', observed, expected: '0' }] }`.
     - Global I3, I4 and I8 sums need per-partition totals that the port's reports do not carry. They are checked per partition by INV-LED-001/003/004/010 (T03-10, T03-11).
     - A `totals` field on the report for the cross-partition sum is a reconciler item.
5. `commitTick(rt, incoming, emit?)` stages everything through `rt.own` (phase P13), in this order:
   a. Incoming legs: apply each leg's local side (`LegBody.localKey`) against `sys_SYSTEM:9900:<thisPartition>-><fromPartition>:<ccy>`, the mirror of the sender's suspense (02 §3.14.2).
   b. Queued entries, in queue order:
      - if `invalid`, write the entry row (with `invalid`) to `led.entry` and skip it;
      - otherwise, for each posting, `normalizeDraft` then `validateDraft`. A failure marks the entry invalid with `INV-LED-007` and skips the whole entry (all-or-nothing, 03 §3.3.2 rule 5);
      - then apply: a posting marked split by `outgoingLegs` applies only its local side, against `sys_SYSTEM:9900:<local>-><remote>:<ccy>`. Every other posting goes through `applyPosting`.
      - A split posting of an entry that fails validation here leaves its remote leg applied. The suspense pair then no longer nets, so `globalCheck` aborts the tick. This is intended: cross-partition entries are backed by P1 holds (02 §3.14.3), so this path signals a bug.
   c. `applyPosting`: `ensureAccount` both keys. A debit does `balance += amount`, `qty += qty ?? 0n`; a credit does `balance -= amount`, `qty -= qty ?? 0n`. Both accounts are written through `own` (phase P13).
   d. Holds: for entries with `holdId`, call `consumeHold` with the amounts credited (paid out) from each part account; then `expireHolds`.
   e. Write the entry row (`led.entry`, staged). If `emit` is given, emit `ledger.entry.committed`:
      - visibility PARTIES;
      - `subjectIds` = the sorted non-system entities touched (kinds other than sys/cbk);
      - payload `{ entryId, reason, amount: headline.amount, ccy, counterpartyLabel }`;
      - `counterpartyLabel` = `'kind:' + kindOfId(counterpartyId)`, unless the counterparty is a public institution (exc, ccp, cbk, gov, reg, crt, rat), whose id may be shown. It is never another player's id (L11).
   f. At t = 719, delete `led.entry` rows older than `tick − ENTRY_RETENTION_TICKS`, iterating index byTick in order.
   Nothing is thrown. Balance shortfalls are left in place for the invariants (I10) to fail the tick (03 §3.3.2 rule 5).
6. Default `NetWorthFn` (book NW): Σ over the entity's non-MEMO ASSET accounts minus LIABILITY accounts, per currency, translated to the entity's reporting currency with fact `FX_MARK_E6` (`fxConvert`). T03-17 replaces it with the marked version.
7. `ledgerTestHooks` (exported as `ledgerProvider.testHooks`):
   - `balance` = the committed balance of `accountKey(entityId, code, ccy, sub)`;
   - `postings` = the postings of valid `led.entry` rows, filtered and ordered by (tick, entryId, postingSeq), in port `Posting` shape.
8. Invariants:
   - `INV_LED_009` (TICK, FATAL): every `writeSet` row of table `led.account` has `module === '03'` and `phase === 'P13'` (genesis commits also run as P13). Observed: `I-commit: account=<id> phase=<p> module=<m>`.
   - `INV_LED_013` (SNAPSHOT, FATAL): `ctx.facts.get('ledger.fold')` = `{ base: [key, balance, qty][], entries: Entry[] }`, supplied by the snapshot writer: the balances at the last verified snapshot and every committed entry since. `foldBalances(base, entries)` must equal every `led.account` row of `ctx.post` (same keys, same balance and qty). A missing fact fails with `fold input missing`; it never passes silently.
   - `INV_BS_012` (TICK, FATAL): every ACTIVE hold with `crossPartition` has `tick − placedTick ≤ ctx.num('inv_xpart_settle_max_ticks')`.

# SPEC EXCERPTS (verbatim; binding game rules)

**[03 §1 Purpose]** (context)

## §1 Purpose

The ledger is the game's first law: **every unit of money and every unit of every asset exists on exactly one balance sheet, and moves only by a posting with a reason code**. This module defines:

1. the entity kinds and the balance sheet each one carries;
2. the full chart of accounts;
3. the double-entry posting model, its standard templates (pay, mint, burn, lend, revalue, FX) and the payment rail across settlement cash, bank deposits and partitions;
4. the complete reason-code catalog of the game, each code in exactly one class (FAUCET, SINK, TRANSFER, CREDIT_CREATE, CREDIT_DESTROY, REVALUE);
5. money aggregates (M0, M2, player-economy money and wealth), the faucet and sink inventory with target ratios, the **Stabilizer** PI controller, the **Money Supply Index (MSI)** and the **Net Worth Index (NWI)**;
6. valuation (marking) rules for every asset type, including illiquid ones;
7. consolidation of ownership chains, minority interests and intercompany elimination;
8. taxes in the five blocs and the Isla Serena free zone;
9. financial statements generated for every entity;
10. insolvency and bankruptcy accounting;
11. the invariants asserted every tick.

Design stance: real accounting where it creates gameplay (balance sheets, consolidation, taxes, credit creation, insolvency), simplification only where it would be invisible (no accrual-vs-cash tax timing nuances beyond those listed, no lease accounting standards). The ledger is also the evidence base for courts (13), the explanation base for "Why it moved" (18) and the data base for the Truth Machine (20).

**[03 §3.3.2]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.3.2 Posting rules

1. `amount > 0n`; `debitAccount != creditAccount`; both accounts in `ccy`.
2. If `qty` is present: both accounts hold the same `assetId`; the debit account's `qty += qty`, the credit account's `qty -= qty`.
3. A posting may join accounts of two different entities (cross-entity). The **entry** must balance every entity it touches per currency (I2). This is guaranteed by building entries only through templates.
4. Only the ledger service in P13 applies postings. Modules call template functions in their phase; the functions validate eagerly (cheap checks), return an `entryId`, and queue the entry.
5. An entry is all-or-nothing: if any posting fails at P13 (e.g. insufficient balance after all holds settle), the whole entry fails and the tick aborts into safe mode (02 §3.15). Modules must therefore place holds for every amount that can fail.


<!-- excerpt 03§3.3.5 -->
**[03 §3.3.5]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.3.5 Cross-partition cash legs

When the two accounts of a rail posting are in different partitions, it is split into legs through `sys:9900` (02 §3.14.2). The central bank (FIN partition) holds its holder sub-accounts per holder; to avoid a FIN round trip for every payment, each PLAYER and CITY partition keeps a **local mirror** of its entities' 1001 balances and the cbk holder sub-accounts are updated from the legs at B3. The authoritative holder balance is the entity's own 1001; the cbk's 2001 total is checked against the sum of all 1001 balances in COORD (I5).

**[02 §3.14.2]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.14.2 Cross-partition postings

A posting whose two accounts live in different partitions is split into two **legs** through interpartition suspense accounts `sys:9900:<A>-><B>:<ccy>` (03 chart of accounts):

```
Partition A:  Dr A_account          Cr sys:9900:A->B   (or reverse)
Partition B:  Dr sys:9900:B->A      Cr B_account
```

Both legs carry the same `entryId` and `legId` and are exchanged at barrier B3. Invariant **I13** (03 §3.16): after P13 of every tick, for every currency and every pair (A, B), `balance(A->B) + balance(B->A) == 0`, checked by COORD from the partitions' reported suspense balances. A mismatch aborts the tick (§3.15).


<!-- excerpt 02§3.15.1 -->
**[02 §3.15.1]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.15.1 Two-phase commit

1. R4 (prepare): each partition applies its postings to a new ledger state, settles/releases holds, runs local invariants (03 §3.16), computes `stateHash`, reports `{ok, stateHash, suspenseBalances, invariantFailures[]}` to COORD.
2. R5 (decide): COORD checks every report plus global invariants (I3 global trial balance per currency, I4 M0 identity, I13 suspense, I8 quantity conservation across partitions). If all pass: writes `TickRecord` to the event store (durable, replicated, 19) and broadcasts `COMMIT(N)`. Otherwise broadcasts `ABORT(N)`.
3. R6: on `COMMIT`, partitions swap their state pointer to the new state and run P14. On `ABORT`, partitions discard the new state (the old one is untouched, §3.6.3) and await the safe-mode retry.
4. A tick is final only when its `TickRecord` is durable. Clients never see any effect of tick N before `COMMIT(N)`.
