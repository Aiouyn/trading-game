## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. Common prologue of every builder, in this order (first failure → `invalidEntry`, no throw):
   a. `entry = catalog.get(code)`: missing → `INV-LED-002 code=<code>`; template not in `allowedTemplates` → `INV-LED-002 template=<tpl>`;
   b. `catalog.mayRequest(code, env.moduleNumber)` false → `INV-LED-002 requester=<module>`;
   c. amounts: `amt >= 0n` after the negative-swap rule (a negative `amt` on ACCRUE/ACCRUE_PAIR swaps dr and cr, 03 §8 edge 18; on any other template negative is invalid `INV-LED-007`); `amt === 0n` returns an entry with no postings (allowed; it commits nothing) except QTY_ONLY codes;
   d. every named entity exists in `env.rail.entity` and is not DISSOLVED → else `INV-LED-007 entity=<id>`;
   e. value legs: `legA/legB` from `o.valueLegA/valueLegB` else the catalog default; a default of `@ASSET`/`@` without an override → `INV-LED-007 leg_missing`.
   The entry has `entryId = env.newEntryId()`, `tick`, `template`, `reason = code`, `requestedBy`, `holdId = o.holdId`, postings numbered 0.. in emission order with `refs = o.refs ?? []`; `headline = { amount: amt, ccy, counterpartyId: <the other party, if any> }`.
2. Postings per template (E:code = account of entity E; accounts per ccy; `cb = cbkId(ccy)`; sub-keys: holder subs on the cbk as T03-06, counterparty or contract subs per the 03 §3.2 Sub column):
   - PAY: cash leg `cashLeg(rail, A, B, amt, ccy, code, { restrictedOk: entry.restrictedOk, fixedSources: o.fixedSources })` then `Dr A:legA / Cr B:legB` (amount amt; sub = `o.sub` if given). `from === to` allowed only for `MAC_TREASURY_SWEEP` (cash leg between the two 1003 subs of `o.payeeSub`, no value leg).
   - SWAP_ASSET: (1) cash leg buyer→seller; (2) `Dr buyer:<legA>:<assetId> / Cr seller:<legB>:<assetId>` with `qty`, `assetId`, amount = `amt` (notional); (3) if the seller's account (legB) is an ASSET-class account: `bv = bookValueOf(seller account, qty)`; if `amt > bv`: `Dr seller:<legB>:<asset> / Cr seller:<4060|4090>` for `amt − bv`; if `amt < bv`: `Dr seller:<5160|5190> / Cr seller:<legB>:<asset>` for `bv − amt` (4090/5190 when `isNonFinancialAssetCode(legB)`). Issuance accounts (3100, 2300, 2310, 2320, 2330, 3150) get no adjustment.
   - MINT: (1) payee money: `Dr E:<receiving account> / Cr cb:<holder sub>` (via `cashLeg` with the cbk as payer, T03-06 CB_ISSUE); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:5900 / Cr E:<legA>` (default 4110). Restricted lot crediting for `ACCT_REWARDED_AD`/`ACCT_FRESH_START` is decided by T03-12 through `o.sub` (`RESTRICTED:<releaseTick>:<tag>`); the money account is then `E:1001:<that sub>`.
   - BURN: (1) `cashLeg(rail, E, cb, ...)` (destroys the holder's base money); (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr E:<legA> / Cr sys:4900`.
   - ELASTIC_IN (sector X must be `hh`/`frm`/`row` and `kindOfId(X)` ∈ `entry.elasticSectors`, else invalid): (1) payee money as MINT (1); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:2909:X / Cr X:1009`; (4) `Dr X:<legA> / Cr E:<legB>`; if `o.qty` (asset sold to the sector): (4) is `Dr X:<assetAcct>:<asset> / Cr E:<assetAcctFrom ?? assetAcct>:<asset>` with qty and the seller adjustment of SWAP step (3) for E.
   - ELASTIC_OUT: mirror: (1) payer's money destroyed via `cashLeg(rail, E, cb, ...)`; (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr X:1009 / Cr sys:2909:X`; (4) `Dr E:<legA> / Cr X:<legB>` (or the asset leg `Dr E:asset / Cr X:asset` with qty and no adjustment for the elastic seller: elastic sectors carry assets at the transaction price; they are outside every NW board).
   - LEND: (1) `Dr C:1010:B / Cr B:2100:C` (new deposit); if C's `receiveInto` is not a deposit at B, follow with a TRANSFER rail move of the same amount from `C:1010:B` to C's receiving account inside the same entry (reason `BNK_DEPOSIT_OUT` as supporting posting); (2) `Dr B:<legA>:<loanId> / Cr C:<legB>:<loanId>`. `BNK_SECURITY_PURCHASE`: step (2) is `Dr B:1520:<asset> / Cr C:<assetAcct>:<asset>` with qty and C's book adjustment.
   - REPAY: if C's paying source is not a deposit at B, first a rail move into `C:1010:B` (supporting `BNK_DEPOSIT_IN`); (1) `Dr B:2100:C / Cr C:1010:B`; (2) `Dr C:<legA>:<loanId> / Cr B:<legB>:<loanId>`. `BNK_SECURITY_SALE` mirrors.
   - CB_CREDIT: counterparty bank: (1) `Dr B:1002 / Cr cb:2002:B`; counterparty non-bank (QE from a fund, 03 §8 edge 16): `Dr F:<receiving money account> / Cr cb:2001:F` (or reserves of F's bank and the deposit legs, via `cashLeg` with the cbk as payer); (2) `Dr cb:<legA> / Cr cpty:<legB>` (1307/2120 for facilities; for `CBK_ASSET_PURCHASE` the asset leg `Dr cb:1520:<asset> / Cr F:<assetAcct>:<asset>` with qty and F's book adjustment); `CBK_FX_INTERVENTION_BUY`: (2) is the foreign leg: `o.ccy2/amt2` cash from cpty to cb via the rail in ccy2 plus `Dr cb:3800:<ccy2> / Cr cpty:3800:<ccy2>` and `Dr cpty:3800:<ccy> / Cr cb:3800:<ccy>` for amt.
   - CB_CREDIT_UNWIND: mirror of CB_CREDIT.
   - ACCRUE: one posting `Dr E:dr / Cr E:cr` (same entity; amount, qty if `o.qty` for quantity-bearing writedowns is not allowed: ACCRUE moves value only).
   - ACCRUE_PAIR: `Dr A:<legA> / Cr A:<income>` and `Dr B:<expense> / Cr B:<payable>`; defaults for `LED_ACCRUAL`: A receivable 1110 / income 4020, B expense 5090 / payable 2520; overrides `o.valueLegA` (A receivable), `o.valueLegB` (B payable); income/expense codes follow from the receivable (1110→4020/5090, 1100→4000/5000, 2540 rent payable→4010/5020, 2510 wages→ (B side only, A is hh: 4190)). Sub of both = `o.sub` (loanId or contractId).
   - FX: (1) ccy1 cash A→B; (2) `Dr A:3800:<ccy1> / Cr B:3800:<ccy1>`; (3) ccy2 cash B→A; (4) `Dr B:3800:<ccy2> / Cr A:3800:<ccy2>`. Each entity balances per currency (I2).
   - MOVE_QTY: `Dr B:<assetAcct>:<asset> / Cr A:<assetAcctFrom ?? assetAcct>:<asset>` with qty and amount = bookValue; plus `Dr A:<legA> / Cr B:<legB>` amount bookValue (skipped when bookValue is 0n; `qty` 0n with bookValue > 0 allowed only for `INSOLV_DEBT_DISCHARGE`, where both legs are explicit liability/receivable accounts).
   - RECLASS: one posting `Dr E:toAcct / Cr E:fromAcct` (moves a balance from `fromAcct` to `toAcct`; for a credit-normal balance the caller swaps). QTY_ONLY codes: `EQ_SPLIT` emits, for every account holding the asset (all holders and the issuer's 3100 issuance account), one posting `{ debitAccount: <that account>, creditAccount: 'sys_SYSTEM:9200:<assetId>:<ccy>', amount: 0n, qty: newQty - oldQty }` (a negative delta is normalized by swapping sides); 9200 is MEMO so books stay balanced, and the per-asset qty sum over non-MEMO accounts stays 0 because holders and issuer scale together (03 §8 edge 5). `LED_DISSOLUTION` emits no postings.
3. Every built entry is checked with `isBalancedPerEntity`; an unbalanced result (a builder bug) becomes `invalidEntry(... 'INV-LED-001' ...)`.
4. `composeEntries`: concatenates postings of supporting entries into the primary (renumbered), keeps the primary's `entryId`, reason and template; used for at-source taxes and fees inside a trade (T03-21).
5. `payProRata` (03 §8 edge 4): parts = `allocate(total, holders as weights)` (02 §3.9.3, ties by id byte order); one PAY cash leg + value legs per holder with part > 0n, all in one entry; holders with 0n receive nothing; the payer pays exactly `total`.
6. Elastic boundary (03 §3.5.2 context): any code whose class is FAUCET/SINK and has sectors must be called through ELASTIC_IN/OUT with a sector entity; payments between named balance sheets are TRANSFER templates.

# SPEC EXCERPTS (verbatim; binding game rules)

**[03 §1 Purpose]** (context)

## §1 Purpose

The ledger is the game's first law: **every unit of money and every unit of every asset exists on exactly one balance sheet, and moves only by a posting with a reason code**. This module defines:

1. the entity kinds and the balance sheet each one carries;
2. the full chart of accounts;
3. the double-entry posting model, its standard templates (pay, mint, burn, lend, revalue, FX) and the payment rail across settlement cash, bank deposits and partitions;
4. the complete reason-code catalog of the game, each code in exactly one class (FAUCET, SINK, TRANSFER, CREDIT_CREATE, CREDIT_DESTROY, REVALUE);
5. money aggregates (M0, M2, player-economy money and wealth), the faucet and sink inventory with target ratios, the **Stabilizer** PI controller, the **Money Supply Index (MSI)** and the **Net Worth Index (NWI)**;
6. valuation (marking) rules for every asset type, including illiquid ones;
7. consolidation of ownership chains, minority interests and intercompany elimination;
8. taxes in the five blocs and the Isla Serena free zone;
9. financial statements generated for every entity;
10. insolvency and bankruptcy accounting;
11. the invariants asserted every tick.

Design stance: real accounting where it creates gameplay (balance sheets, consolidation, taxes, credit creation, insolvency), simplification only where it would be invisible (no accrual-vs-cash tax timing nuances beyond those listed, no lease accounting standards). The ledger is also the evidence base for courts (13), the explanation base for "Why it moved" (18) and the data base for the Truth Machine (20).

#### §3.3.3 Templates (the only way to build entries)

Notation: `E:code` = account of entity E. `cb` = central bank of the currency. "Value leg" = the account that records what the payer gets and the payee gives (expense, income, asset, liability), chosen by the reason code's mapping table (each code lists its default value-leg accounts in the code catalog generator, 22/23 data; examples below).

| Template | Use | Postings |
|---|---|---|
| `PAY(A → B, amt, code, valueLegA, valueLegB)` | core-to-core payment for goods, services, fees, taxes, dividends (TRANSFER codes) | (1) cash leg via the payment rail (§3.3.4); (2) `Dr A:valueLegA / Cr B:valueLegB` |
| `SWAP_ASSET(A ⇄ B, asset, qty, price, code)` | purchase/sale of an asset for money | (1) cash leg buyer→seller via rail; (2) `Dr Buyer:assetAcct / Cr Seller:assetAcct` with `qty` and `amount = notional`; (3) seller's book adjustment: if seller's book value of the qty ≠ notional, `Dr Seller:assetAcct / Cr Seller:4060|4090` (gain) or `Dr Seller:5160|5190 / Cr Seller:assetAcct` (loss) |
| `MINT(sys → E, amt, code, valueLegE)` | FAUCET with no elastic counterparty (start cash, grants, ads, compensation) | (1) `Dr E:1001 / Cr cb:2001`; (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:5900 / Cr E:valueLegE` (default 4110) |
| `BURN(E → sys, amt, code, valueLegE)` | SINK with no elastic counterparty (fines' sink share, levies, licence fees) | (1) `Dr cb:2001 / Cr E:1001`; (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr E:valueLegE / Cr sys:4900` |
| `ELASTIC_IN(X → E, amt, code, valueLegX, valueLegE)` | FAUCET: an elastic sector X (hh, frm, row) pays a core entity | (1) `Dr E:1001 / Cr cb:2001` (or reserves if E is a bank); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:2909:X / Cr X:1009`; (4) `Dr X:valueLegX / Cr E:valueLegE` |
| `ELASTIC_OUT(E → X, amt, code, valueLegE, valueLegX)` | SINK: a core entity pays an elastic sector | mirror of `ELASTIC_IN` |
| `LEND(bank B → borrower C, amt, code)` | CREDIT_CREATE | (1) `Dr C:1010:B / Cr B:2100:C` (new deposit; if C's receiving account is settlement cash, the rail then moves it out of B as a TRANSFER payment); (2) `Dr B:13xx:loanId / Cr C:22xx:loanId` |
| `REPAY(C → B, principal, code)` | CREDIT_DESTROY | (1) `Dr B:2100:C / Cr C:1010:B` (deposit extinguished; if C pays from settlement cash, the rail first moves it into B); (2) `Dr C:22xx / Cr B:13xx` |
| `CB_CREDIT(cb → bank B, amt, code)` | CREDIT_CREATE at the central bank (M0_cb up) | (1) `Dr B:1002 / Cr cb:2002:B`; (2) `Dr cb:1307|1520 / Cr B:2120|asset sold` |
| `CB_CREDIT_UNWIND` | CREDIT_DESTROY at the central bank | mirror |
| `ACCRUE(E, amt, code, dr, cr)` | REVALUE, intra-entity non-cash: accrual, depreciation, provision, MTM, impairment, revaluation | `Dr E:dr / Cr E:cr` (one posting, same entity) |
| `ACCRUE_PAIR(A, B, amt, code)` | REVALUE accrual of a bilateral amount (interest accrued on a loan) | `ACCRUE(A, receivable/income)` + `ACCRUE(B, expense/payable)` in one entry |
| `FX(A ⇄ B, ccy1 amt1, ccy2 amt2, code)` | currency exchange | (1) ccy1 cash A→B via rail; (2) `Dr A:3800:ccy1 / Cr B:3800:ccy1`; (3) ccy2 cash B→A via rail; (4) `Dr B:3800:ccy2 / Cr A:3800:ccy2` |
| `MOVE_QTY(A → B, asset, qty, bookValue, code)` | asset transfer without consideration (gift, in-kind dividend, collateral title transfer, seizure, inheritance) | `Dr B:assetAcct / Cr A:assetAcct` with qty and amount = book value; plus value legs (`Dr A:expense or equity / Cr B:income or equity`) per code |
| `RECLASS(E, amt, code, fromAcct, toAcct)` | REVALUE, intra-entity moves with no value change (period close, current↔non-current) | one posting |

Every template returns the list of postings it generated; the code catalog defines which templates a code may use (`allowedTemplates`). A FAUCET code can only use `MINT` or `ELASTIC_IN`; a SINK code only `BURN` or `ELASTIC_OUT`; CREDIT codes only `LEND`, `REPAY`, `CB_CREDIT`, `CB_CREDIT_UNWIND`; REVALUE codes only `ACCRUE`, `ACCRUE_PAIR`, `RECLASS`; TRANSFER codes `PAY`, `SWAP_ASSET`, `FX`, `MOVE_QTY`. This is how "each reason code belongs to exactly one class" (00 §5.4) is enforced mechanically.

#### §3.3.6 Multi-currency

Each posting is in one currency. An entity's books balance **per currency** thanks to the currency trading accounts 3800 (template `FX`). Net worth in a reporting currency R:

```
NW_R(E) = Σ_ccy fx(ccy→R) · NW_ccy(E)     where NW_ccy(E) = Σ assets_ccy − Σ liabilities_ccy (including 3800 as equity)
```

The translated sum of the 3800 accounts is the entity's cumulative FX result; statements show it as FX gains/losses (§3.13.2). FX rates for translation are the official day-close marks of FX spot (05), intraday the latest clearing mid.

#### §3.5.2 Elastic sectors (how the aggregate economy plugs into an exact ledger)

The aggregate economy (Layer 1 of the living world: households, small firms, the rest of the world, V3 Part 7) is modelled by 04 (macro) and by 09/10 (demand pools, rents) with float models. Its spending is a **model output**, not a constrained cash balance. In the ledger:

1. Elastic sectors hold **real claims** booked exactly like any entity: deposits at core banks, bonds, shares (the free float not held by core entities), fund units, properties, loans to and from core banks. This keeps quantity conservation exact (I8) and lets bank runs, defaults and restructurings hit real balance sheets.
2. Their spending money is **virtual**: account `1009 Elastic money`, which may be negative, backed by `sys:2909`. When an elastic sector pays a core entity, the payment is a FAUCET (template `ELASTIC_IN`): outside money is minted at the central bank for the payee. When a core entity pays an elastic sector, it is a SINK (`ELASTIC_OUT`): the money is burned.
3. Consequence: the core economy is closed except at two kinds of edges, the `sys` issuer and the elastic sectors, and both are FAUCET/SINK codes. This resolves the old ambiguity (01 §8.1 called "NPC customers pay players" a faucet, while a full balance-sheet world would call it a transfer): **payments from the aggregate economy are faucets; payments between named balance sheets are transfers.**
4.
