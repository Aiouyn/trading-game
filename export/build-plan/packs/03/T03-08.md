## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `runtime.ts`: `LedgerRuntime` is created by T03-09 per (partition, module, phase, tick) and stored under the `RUNTIME` symbol on the LedgerApi object; `runtimeOf(ctx)` reads `(ctx.ledger as any)[RUNTIME]` and calls `ctx.fail('INV-LED-009', [], 'no ledger runtime', 'runtime installed')` if missing (never throw).
2. `registerEntity(ctx, spec)` (GLOBAL G7, 03 §3.1): if an entity with `spec.id` exists, return its id unchanged (idempotent). Otherwise create `LedgerEntity`: `nameKey` default `entity.<id>`; `homeBloc` = `spec.homeBloc` ?? bloc of `homeCity` from `ctx.content` (22 city → bloc) ?? the bloc whose currency is `reportingCcy`; characters always `reportingCcy 'FDL'` (03 §2.1: chr reports in FDL); `rootOwnerId` = `rootOwnerOf(ownerId)` or itself; `perimeter` = `perimeterFor`; `partitionId` = `spec.partitionId ?? ctx.header.partitionId`; `status 'ACTIVE'`; `createdTick = ctx.tick`; rail defaults CASH/CASH. Put into `led.entity` through `rt.own`. No accounts are created (lazy, 03 §3.1.2). The genesis entity `sys_SYSTEM` is registered by the 03 genesis (T03-28). Ownership/perimeter recomputation on control changes is T03-16.
3. `ensureAccount(rt, key)`: parse key; reject unknown chart code by `ctx.fail('INV-LED-007', [entityId], 'code=<code>', 'chart code')`; class from `classOfCode`; `isMoney = isMoneyCode(code, kind)`; `assetId = sub` for qty-bearing codes (T03-01 step 2); balance 0n, qty 0n for qty-bearing; `openedTick = rt.tick`.
4. Holds (02 §3.14.3, GLOBAL G7 `HoldApi` exactly, plus `HoldApiExt`):
   - `placeCash(owner, ccy, amt, expiresTick, ref)` = `placeCashFor(owner, ccy, amt, expiresTick, ref, '')` where purpose '' means "restricted cash not allowed" (the safe default: a hold without a purpose never relies on restricted cash).
   - `placeCashFor`: reject `LED_BAD_EXPIRY` if `expiresTick < tick` or `amt <= 0n`; `LED_ENTITY_FROZEN` if owner status is FROZEN or IN_INSOLVENCY (court freeze and insolvency freeze, 03 §3.14.3), or fact COURT_FREEZE true; parts = `payingSources(railState, owner, ccy, amt, { restrictedOk: catalog.get(purposeCode)?.restrictedOk ?? false })` restricted to sources with spendable > 0 (sources whose bank is frozen are skipped, 03 §8 edge 2); if Σ spendable of the parts < amt → `LED_INSUFFICIENT_FUNDS`, except when the shortfall would be covered by restricted cash that the purpose may not use → `LED_RESTRICTED_FUNDS` (acceptance test 03#32 relies on this code; T03-12 tests it). On success write a Hold `{ holdId: ctx.newId('hld'), kind 'CASH', parts, amount, remaining = amount, expiresTick, ref, placedTick, crossPartition, purposeCode, status 'ACTIVE' }` and return its id.
   - `placeQty(owner, assetId, qty, expiresTick, ref)`: accounts of the owner holding `assetId` (index byAsset, sorted by key); first with `committedQty − active qty holds ≥ qty` → one part; else `LED_INSUFFICIENT_QTY`.
   - `reduce(holdId, by)`: `remaining = max(0n, remaining − by)`, parts reduced in reverse draw order; `release(holdId)`: status RELEASED; `get` returns the record.
   - Holds are never visible to other players (L11): the hold table has no view in 03 except the owner's own (T03-27).
5. `consumeHold` (called by T03-09 when an entry with `holdId` is applied): subtract consumed amounts from the matching parts' `remaining`; the hold stays ACTIVE (a resting order may fill again) until released or expired; `remaining` reaching 0n sets status SETTLED.
6. `expireHolds`: every ACTIVE hold with `expiresTick < tick` → RELEASED (02 §3.14.3 rule 3).
7. Facts: id `${kind}:${subjectId}`, written through `rt.own` with `tick`; documented producers in the `LedgerFactKind` comments (T03-01). Tests seed facts with `putFact` in `asSystem`.
8. `TickQueue`: one per tick per partition, held by the provider (T03-09) in memory; `queuedDebit(key)` is maintained on push: for each posting crediting a money account (a credit reduces an asset balance), add the amount; entries carrying `holdId` add only the part beyond the hold's remaining on that account.
9. Cross-partition legs (03 §3.3.5): the rail state marks an account as remote when its entity's `partitionId !== rt.partitionId`; remote balances are not known locally, so `spendable` of a remote account is never consulted (holds are always local, 02 §3.14.3 rule 1). Splitting into legs is T03-09.
10. `INV_BS_011` (scope TICK, severity QUARANTINE per 20 Rule 3.2.5, def from 20 §3.1 row; costClass O_TOUCHED): over `ledgerView`: for every ACTIVE cash hold part, Σ remaining per account ≤ the account's staged balance (I11; "available balance before the holds"); every hold with `expiresTick < tick` is not ACTIVE (I11 second half); for every quantity account, Σ remaining of ACTIVE qty holds ≤ staged qty (I12: a qty pledged at most once; 07 records pledges as qty holds with the loan's maturity as expiry). Observed `I11: account=<key> holds=<n> balance=<b>` etc.

# SPEC EXCERPTS (verbatim; binding game rules)

**[03 §1 Purpose]** (context)

## §1 Purpose

The ledger is the game's first law: **every unit of money and every unit of every asset exists on exactly one balance sheet, and moves only by a posting with a reason code**. This module defines:

1. the entity kinds and the balance sheet each one carries;
2. the full chart of accounts;
3. the double-entry posting model, its standard templates (pay, mint, burn, lend, revalue, FX) and the payment rail across settlement cash, bank deposits and partitions;
4. the complete reason-code catalog of the game, each code in exactly one class (FAUCET, SINK, TRANSFER, CREDIT_CREATE, CREDIT_DESTROY, REVALUE);
5. money aggregates (M0, M2, player-economy money and wealth), the faucet and sink inventory with target ratios, the **Stabilizer** PI controller, the **Money Supply Index (MSI)** and the **Net Worth Index (NWI)**;
6. valuation (marking) rules for every asset type, including illiquid ones;
7. consolidation of ownership chains, minority interests and intercompany elimination;
8. taxes in the five blocs and the Isla Serena free zone;
9. financial statements generated for every entity;
10. insolvency and bankruptcy accounting;
11. the invariants asserted every tick.

Design stance: real accounting where it creates gameplay (balance sheets, consolidation, taxes, credit creation, insolvency), simplification only where it would be invisible (no accrual-vs-cash tax timing nuances beyond those listed, no lease accounting standards). The ledger is also the evidence base for courts (13), the explanation base for "Why it moved" (18) and the data base for the Truth Machine (20).

### §3.1 Entity lifecycle

1. Authored entities (all `cbk`, `gov`, `reg`, `crt`, `exc`, `ccp`, `rat`, `sys`, the elastic sectors, NPC banks, funds, insurers, listed NPC companies, named NPC actors) are created at genesis from 22 with genesis balance sheets. 2. Player entities are created by intents of the owning module (chr by 14 `acct.create`; cmp by 09; fnd by 08; bnk by 07; ins by 08; ali by 15; biz by 09; prop by 10). Each new entity gets its accounts lazily on first posting.
3. An entity can be dissolved only with all balances at zero except equity accounts closing to zero (or via insolvency §3.14). Dissolution posts `LED_DISSOLUTION` (REVALUE class, amount 0 check record).

**[03 §3.3.5]** (from spec file 03-LEDGER-AND-ACCOUNTING.md)

#### §3.3.5 Cross-partition cash legs

When the two accounts of a rail posting are in different partitions, it is split into legs through `sys:9900` (02 §3.14.2). The central bank (FIN partition) holds its holder sub-accounts per holder; to avoid a FIN round trip for every payment, each PLAYER and CITY partition keeps a **local mirror** of its entities' 1001 balances and the cbk holder sub-accounts are updated from the legs at B3. The authoritative holder balance is the entity's own 1001; the cbk's 2001 total is checked against the sum of all 1001 balances in COORD (I5).


<!-- excerpt 02§3.14.3 -->
**[02 §3.14.3]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.14.3 Holds

1. Any intent that commits money or assets that a different partition will consume places a **hold** on the actor's account in P1 (or inline in P4/P5 for NPC and AI intents). `available = committed balance - Σ active holds`. A hold is local to the owner's partition and therefore cannot be double-spent across partitions.
2. Holds carry `expiresTick`: for an order, the tick it would expire (good-for-tick orders expire at N; resting orders keep a hold equal to their maximum notional plus fees until cancel or fill); for a P2P atomic swap, N; for a contract escrow placement, N (escrow itself is a posting into the CCP escrow account at P13).
3. In P13 each hold is **settled** (converted into the postings of the fill or transfer, and released for the unused part) or **released**. A hold whose `expiresTick < N` is released automatically.
4. **Atomic multi-party settlement** (P2P swap of a business for money across partitions): both sides hold in P1, the swap's legs are prepared in R3, and P13's two-phase commit makes them commit together or not at all. If either side fails validation, neither leg is produced and both holds release.
5. Holds are never visible to other players (L11), only to the owner and to the court via discovery (13).
