## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Goal
The per-tick heart of margin. Each P7 it marks every account with a changed mark, picks the IM model by account type, moves the account between OK, CALL, LIQUIDATING and DEFICIT, issues and expires calls, and opens margin liquidation jobs in the 07A engine with a planner that closes the largest IM contributor first until IM ≤ equity / 1.1. ## Implementation steps
1. Model dispatch (`ACCOUNT_RULES`): CASH none; RETAIL_MARGIN `retailIm`; PORTFOLIO `max(SCAN, HVaR-PB)` × the PB multiplier in [1.0, 1.5] (`up` PB tier, default 1.0) then add-ons; MEMBER_* the service model (LD/CRY SCAN, OTC/CDS HVaR, REPO haircut sum) with MM = IM. Between recomputes use `scaleIm`.
2. Equity per §3.16.1. Collateral counts at `valueAfterHaircut` with the CCP venue for MEMBER, PB venue for PORTFOLIO, BILATERAL for broker retail; ineligible or wrong-way collateral counts 0. Each posted unit is a pledge (T07A-02) so it cannot be sold or re-pledged (§9 Y11).
3. Transitions (§3.16.2): RETAIL `equity < MM` → LIQUIDATING now; `MM ≤ equity < IM` → CALL (pre-trade accepts only risk-reducing orders, `CCP_CALL_RISK_REDUCING`); `≥ IM` → OK and any open call MET. PORTFOLIO / PB / MEMBER: `equity < IM` with no open call → `MarginCall(IM − equity, due = tick + 30)`; `equity < 0.6·IM` → LIQUIDATING (MEMBER: return `memberDefault` for T07B-10); call unmet at due → FAILED and LIQUIDATING (member default for MEMBER).
4. Liquidation: `openJob({ source: 'MARGIN', ownerId, lines: all positions, penaltyTo: ownerIsClient ? memberId : RETAIL_INS_FUND (retail at an NPC broker) | cryInsFundId(product) (CRY), proceedsTo: accountId })`. `marginPlanner` re-plans each tick with `closeOrder` on marginal IM per unit expected cost until `IM(remaining) ≤ equity/1.1`, or everything when equity ≤ 0. Orders made in P7 of N reach 05 in P6 of N+1 (07A engine). Held owners liquidate exactly like everyone, always at the fair-value band. When nothing is left and equity < 0 → DEFICIT and call T07B-07 `settleDeficit`.
5. VM at P13: for every cleared position `ΔPV = PV_now − lastPv`; post `CCP_VARIATION_MARGIN` between the account and `SERVICE_ACCOUNT[service]` (gain: service pays; loss: account pays), update `lastPv`. Post in (service, assetId, accountId) order. Rounding: each ΔPV is `toMoney` half-even; because the CCP holds the mirror leg of every position (INV-CCP-001), the service account's sum is Σ of the same rounded amounts with opposite sign, so it nets to exactly zero.
6. Intents: deposit arrives at P13 of the submission tick and counts from the next P7 (§3.16.3); Held characters may deposit. Withdraw rejects with `CCP_WITHDRAW_BUFFER` when `equity − amount < 1.1·IM`. `setType` requires LIC4 (`CCP_NOT_LIC4`).
7. `INV_CCP_003`: for each service, Σ of last tick's `CCP_VARIATION_MARGIN` amounts over all member accounts + the service account = 0.

# SPEC EXCERPTS (verbatim; binding game rules)

**[07 §1 Purpose]** (context)

## §1 Purpose

This module is the **plumbing of money and leverage**: where every unit of cash actually sits, how banks create credit and destroy it, how they fund themselves, how confidence in them rises and collapses, how they fail and are resolved, how leverage is extended to traders (broker margin, prime brokerage, repo, securities lending), and how the Clearing House stands between counterparties, collects margin and absorbs defaults through a waterfall.

It gives the game its systemic layer (V3 §3.1, §3.3, §3.4):
- **Credit cycles are caused**: lending standards loosen in booms and tighten in busts as bank capital and losses move (§3.5).
- **Bank runs are feedback loops** fed by losses, rumors and other runs, stoppable by central-bank liquidity, deposit-insurance action, recapitalization or a rescue merger, and they leave a permanent record (§3.9).
- **Procyclical margin** turns a volatility spike into forced deleveraging, which is the cleanest cascade in the game (§3.15, §3.16).
- **The default waterfall** gives large players mutualized, "too big to fail" risk (§3.17).
- **Players can run banks** (§3.11): earn net interest margin, carry duration, credit and run risk, and fail for real.

Design laws:
1. Money is either **settlement cash** (a direct claim on a central bank, 03 account 1001: the default, risk-free money of every non-bank, earning nothing unless 04 pays on it), a **bank deposit** (03 account 1010, a claim on a bank: earns interest, carries the bank's risk), or a bank's **reserves** (1002). The payment rail between them is 03's (03 §3.3.4); this module owns everything about banks and deposits. In this module `fear = F / 100`, F = 04's Fear Index (04 §3.14.1).
2. A loan creates a deposit (`CREDIT_CREATE`); a repayment destroys one (`CREDIT_DESTROY`). Base money (M0) changes only through 03 faucets and sinks and 04 central-bank operations.
3. Liquidations and close-outs use fair-value price bands, never a crashed print (01 §9).
4. Nothing reveals an individual player's positions or strategy (L11). Systemic dashboards publish aggregates only.

**Status of numbers:** every `PARAM.*` value in this module, and every choice tagged `DEFAULT`, is `DEFAULT (Mathis may override)`. Locked decisions L1–L15 (00) and the 00 time model are not defaults. The full list is in `_notes/07-notes.md`.

**[07 §3.16.1]** (from spec file 07-BANKING-CREDIT-CLEARING.md)

#### §3.16.1 Every tick (P7)
For every margin account with any position whose mark changed: `equity = cash + Σ long marks − Σ short marks + Σ derivative PVs (06 marks) − accrued fees and interest`. Compare with IM and MM (current or scaled per §3.15.5). Variation margin on cleared positions is realized: the change in PV moves between the account's cash and the CCP each tick at P13 (`CCP_VARIATION_MARGIN`, TRANSFER), so derivative P&L is cash (V3 §3.3).


<!-- excerpt 07§3.16.2 -->
**[07 §3.16.2]** (from spec file 07-BANKING-CREDIT-CLEARING.md)

#### §3.16.2 Status transitions
- RETAIL: `equity < MM` → LIQUIDATING immediately; `MM ≤ equity < IM` → CALL (only risk-reducing orders accepted); `equity ≥ IM` → OK.
- PORTFOLIO, PB, MEMBER: `equity < IM` → `MarginCall(amount = IM − equity, due = now + 30 ticks)`; `equity < 0.6 · IM` at any tick → LIQUIDATING (members: default declaration); call unmet at due → LIQUIDATING / member default.
- Consequences land next tick (02 rule): liquidation orders created in P7 of tick N are submitted to P6 of tick N+1.
- Held characters (03): liquidation orders are created exactly as for anyone else and always use the fair-value band (03 "margin calls during Held liquidate at fair value").

**[07 §3.16.3]** (from spec file 07-BANKING-CREDIT-CLEARING.md)

#### §3.16.3 Meeting a call
`bank.margin.deposit` (cash or eligible collateral), reducing positions, or (PB) agreed term changes. Deposits arrive in P13 of the submission tick and count from the next P7.


<!-- excerpt 07§3.16.4 -->
**[07 §3.16.4]** (from spec file 07-BANKING-CREDIT-CLEARING.md)

#### §3.16.4 Liquidation algorithm (accounts, repo, buy-ins, CCP hedging all use it)
```
target: reduce positions until IM(remaining) ≤ equity / 1.1, or close everything if equity ≤ 0
order of closing: largest IM contribution first (marginal IM reduction per unit of expected cost); ties by assetId
per tick per position: qty_slice ≤ PARAM.liq_max_participation (0.20) × expected tick volume (ADV / ticks in session)
limit price: fairValue · (1 ∓ band),  fairValue = 06 mark (§3.3.3 of 06, the band-clamped value) or perp mark price
band_0 = clamp(2 · σ_tick · sqrt(30), 0.5%, 3%), band widens by +1% per unfilled tick, cap 10%
closed markets: queued for the next opening auction with participation ≤ 20% of the opening auction volume
penalty: 1% of liquidated notional → retail: TCH retail insurance fund; client: its clearing member; CRY: product insurance fund (TRANSFER, reason `CCP_LIQUIDATION_PENALTY`)
```
Liquidation never trades at a crashed print because limits are anchored to fair value, and it never exceeds 20% participation, so one liquidation cannot become a flash crash by itself; many simultaneous liquidations still can (intended cascade).
