## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `preTradeCheck` (P1, called by 05 for every order whose principal `onBehalfOf` is a `fnd`; reject codes returned to the actor only, nothing else happens): (0) actor is a fund operator (`FUND_NOT_MANAGER`); fund status allows trading: FROZEN allows only engine liquidation (manager orders `FUND_FROZEN`), WINDING_DOWN and CLOSED allow none (`FUND_NOT_ACTIVE`); `reduceOnly` orders skip rules 2–4. (1) asset class ∈ `allowedAssetClasses` (`FUND_MANDATE_ASSET_CLASS`), asset region (issuer bloc; FX: both currencies) ∈ `allowedRegions` (`FUND_MANDATE_REGION`), a sell that would take the position below zero requires `shortAllowed` (`FUND_MANDATE_SHORT`), derivatives (OPTION, FUTURE, PERP, SWAP, CDS) require `derivativesAllowed` (`FUND_MANDATE_DERIVATIVE`), the manager's license ≥ `requiredLicense(asset, act)` (`FUND_NO_LICENSE`); leveraged ETFs (§3.2.5) never in MONEY_MARKET or LONG_ONLY funds (`FUND_MANDATE_ASSET_CLASS`). (2) post-trade gross leverage `Σ|exposure| / NAV ≤ maxGrossLeverage` (player funds ≤ `PARAM.fund_max_leverage_player`; NPC funds `npcLeverageCap`), exposures with `deltaNotional` (`FUND_MANDATE_LEVERAGE`). (3) post-trade position value ≤ `maxPositionPctNav × NAV` (player ≤ `PARAM.fund_max_position_pct`) (`FUND_MANDATE_POSITION`). (4) related-party cap: if `relatedHolder(...)`, post-trade position ≤ `PARAM.fund_related_cap_pct × NAV` (`FUND_RELATED_CAP`). NAV is the last struck NAV adjusted by today's fills (valuation from `valueHolder` at the last marks); the check uses `o.price` (limit or last price).
2. Rule 5 (self-match) is 05's: 05 never matches a fund order against an order of the manager or a linked account; 08 supplies the membership through `MandatePort.managedFundsOf` (T08-29). This task documents it and tests it in the integration (08#10 second clause).
3. `relatedHolder`: the manager, any entity in the manager's ownership chain, or a 19-linked account (`linkScore ≥ PARAM.fund_link_score_block`) holds ≥ `PARAM.fund_related_float_pct` of the instrument's float, or is in `ports.companies.insiders(issuer)`. `fileRelatedTrades`: every fund fill (`fillsOfTick`, fund account) in such an instrument → `fund.relatedHoldingFiled` PUBLIC `{ fundId, assetId, sizeBand }` (bands: <$100k, $100k–1M, $1–10M, >$10M) emitted at the next t = 719 (within 1 game day).
4. `shadowManagerTrades` (§3.1.12, evidence only, 13 owns offences): (a) exit liquidity: within 1 game day, the manager (chain or linked) sold an asset the fund bought; (b) front-running: the manager's personal trades in the same asset and direction within 1 game day before fund trades of ≥ 2× the personal size. Each detected pair emits `fund.managerTradeShadow` SEALED `{ fundId, managerId, assetId, personalFillIds, fundFillIds, pattern }`. Detection keeps a rolling 720-tick window of manager-group and fund fills (from `fillsOfTick` each tick) in `fnd.shadow_window` (T08-01), rows pruned after 720 ticks.
5. `checkLevel3RelatedPurchase`: a fund buying a Level-3 asset from a related party must price within ±10% of the NPC valuer's appraisal, else `FUND_RELATED_VALUATION` (the 09 private-stake market calls this through `FundsPort` when the buyer is a fund; 08 also emits `fund.managerTradeShadow` with `pattern: 'RELATED_VALUATION'` on each attempt; the "+30 surveillance score" is 13's consumption of that event).
6. `driftCheck` (DAY_CLOSE after the strike): positions above `1.25 × maxPositionPctNav × NAV` start a cure timer (`positionDriftSinceTick[assetId]`); if still above after `PARAM.fund_drift_cure_days` game days → status FROZEN (`fund.frozen` PUBLIC, reason `DRIFT`) until back below (checked daily; unfreeze emits `fund.unfrozen`). Leverage above `1.1 × maxGrossLeverage` is handed to 07 margin rules (no 08 action; emit nothing). Prices moving never forces a trade otherwise.
7. `fund.updateMandate` (actor manager/sponsor; new limits within the same caps as T08-04 `validateTerms`): `pendingMandate = { mandate, effectiveTick: tick + PARAM.fund_mandate_notice_days × 720 }`, `gateFreeUntilTick = effectiveTick`, `gateFreeReasons += 'MANDATE_NOTICE'`; emit `fund.mandateChangeNotice` PARTIES `{ old, new, effectiveTick }`. `fund.updateFees`: if any rate increases → same notice and gate-free window, `lastFeeIncreaseTick = tick`, `fund.feeChangeNotice`; pure cuts apply at once. Inside the window redemptions also pay no early-exit fee (T08-07 reads `gateFreeReasons`).
8. `fund.setTransparency`: raising the level is effective next game day; lowering takes 7 game days (`pendingTransparency`). `investorDisclosure`: NAV_ONLY → daily NAV + monthly return; EXPOSURES (default, D145) → buckets rounded to 5% granularity (`round(x/0.05)×0.05`), leverage, liquidity profile; TOP_POSITIONS_DELAYED → plus top 5 positions as % of NAV as of 7 game days ago (from `fnd.position_snapshot` rows (T08-01) that `writePositionSnapshot` writes at each strike and prunes after 28 days); FULL_DELAYED → full list as of 28 game days ago. Every investor view is bound by the automatic NDA clause of 15 (recorded in the view payload as `ndaClause: true`).
9. Filings (§3.1.16, ruling R20): the holdings report is 15's `HOLDINGS_QUARTERLY`; 08 exposes `fundHoldingsForFiling(store, fundId, quarterEndTick)` in transparency.ts returning up to 20 long listed-equity positions each ≥ 0.5% of the reportable book with quantities, for 15 to file 21 game days after quarter end. Ownership-threshold aggregation (fund + manager) is 15's, using `MandatePort.managedFundsOf`. `PARAM.fund_filing_aum` is retired (R20): never read it.

# SPEC EXCERPTS (verbatim; binding game rules)

**[08 §1 Purpose]** (context)

## §1 Purpose

This module is the buy-side and risk-transfer half of the institutional layer (V3 Part 3.5, 3.6, 3.8):

1. **Funds** let capital be pooled and managed under a mandate: players run hedge funds, long-only funds, funds of funds, credit funds, venture and private-equity funds, money-market funds, ETFs and (at Dynasty rank) sovereign wealth funds. Investors (players and NPC allocators) buy units at NAV. Track record, trust and betrayal are public (MASTER-BIBLE VI #2). Theft is impossible by construction; market abuse through a fund is possible and prosecutable (roadmap Q6, resolved §3.1.12).
2. **ETFs** are funds with listed units and a primary market. Authorized participants (APs) create and redeem baskets to keep price near NAV. ETF flows move the underlying; in a crisis, basket illiquidity opens real discounts.
3. **Securitization** turns pools of loans, mortgages, receivables and leases into tranches (senior, mezzanine, equity) sold to investors. Default correlation, underwriting standards and rating methodology together can produce a 2008-style event from rules, never from a script.
4. **Rating agencies** grade sovereigns, corporates, banks, insurers, funds and tranches. Grades move spreads and trip collateral, mandate and capital rules, so cliff effects create gameplay.
5. **Insurance and reinsurance** price and absorb operational, property, cyber, liability and catastrophe risk. Losses from storms, cyber pandemics and unrest propagate from policyholders to insurers, reinsurers and cat-bond holders.

Design rules: every flow is a ledger posting with a reason code (03); every price comes from a model a player can learn or from an auction; no actor gets private information (L11); every institution can fail by rule and leaves a public record.

#### §3.1.8 Mandate enforcement

Pre-trade, in P1, for every order whose actor is a fund (manager trading for the fund):

1. Instrument's asset class ∈ `allowedAssetClasses`, region ∈ `allowedRegions`, `shortAllowed` and `derivativesAllowed` respected (and the manager holds the license the instrument needs).
2. Post-trade gross leverage (Σ|exposure| / NAV, using delta-adjusted notional for derivatives from 06) ≤ `maxGrossLeverage` (player funds ≤ `PARAM.fund_max_leverage_player = 1.5`; NPC funds per §6.1).
3. Post-trade position ≤ `maxPositionPctNav` (player ≤ `PARAM.fund_max_position_pct = 0.20`).
4. Related-party cap: if the manager (or any entity in the manager's ownership chain or 19-linked accounts) personally holds ≥ `PARAM.fund_related_float_pct = 0.01` of the instrument's float, or is an insider of the issuer (09 §3.10 insider list), the fund's position is capped at `PARAM.fund_related_cap_pct = 0.05` of NAV, and every fund trade in that instrument is filed publicly within 1 game day (`fund.relatedHoldingFiled`).
5. Self-match: 05 never matches a fund order against an order from the manager or a linked account (the same rule as wash-trade prevention).

A failing order is rejected with the rule code; nothing else happens. Post-trade drift (prices move) never forces a trade, except: leverage above `1.1 × maxGrossLeverage` hands control to 07 margin rules; a position above 1.25 × `maxPositionPctNav` must be reduced within `PARAM.fund_drift_cure_days = 3` game days or the fund is FROZEN until it is.

Mandate change: `fund.updateMandate` takes effect after `PARAM.fund_mandate_notice_days = 24` game days (24 real hours). During the notice every investor may redeem gate-free and without early-exit fee. Fee increases follow the same notice; fee cuts are immediate.

#### §3.1.12 Betrayal: what is possible and what is punished (resolves roadmap Q6, option A)

Theft is impossible by construction: fund assets are only in custody; the manager has trade rights and no withdrawal path except crystallized fees and his own units. No "exit scam" exists (roadmap Q6 option B rejected). What remains is market abuse, all public and prosecutable:

| Abuse | Detection | 13 offence |
|---|---|---|
| Fund as exit liquidity (manager dumps personal holdings into fund buying) | §3.1.8 rule 4 filings + 13 surveillance comparing manager sells vs fund buys within 1 game day | S5 market abuse |
| Front-running the fund | manager's personal trades in the same asset and direction within 1 game day before fund trades of ≥ 2× the personal size | S5 |
| Related-party valuation (fund buys manager's private stake) | Level-3 assets bought from a related party must price within 10% of the NPC valuer's appraisal, else blocked; +30 surveillance score on attempt (09 §3.12 shares the rule) | S4 if attempted repeatedly |
| Style drift within mandate | style-drift score on the page (§3.1.13); not an offence | none |
| Abrupt closure | page incident (§3.1.11) | none |

Penalties for S5 fund abuse bind as in the roadmap §2.2: fine 8% of NW (floor $100,000, per-verdict cap 35% of NW), 100% disgorgement, 1.5× restitution paid first from the manager stake (§3.1.10), the Victim Compensation Fund advances 50% of restitution immediately (13), a fund-management ban of 1,344 game days (8 real weeks) during which all the manager's funds wind down, and a permanent line on the profile and fund page. 13 owns the sanction mechanics; this module emits the evidence events (§5).

|---|---|
