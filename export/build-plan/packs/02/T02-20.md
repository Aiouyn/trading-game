## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)

```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `core.clock.get` (public): tick = last committed; gameDate and phase from T02-05 (phase WEEKEND on weekend days, HOLIDAY on an all-bloc holiday for the default bloc FDL); mode from the scheduler (HALTED while halted); `nextSealEtaMs` from T02-19; each next boundary tick from `nextBoundaries` and its UTC estimate `scheduledUtcMs(anchor, tick)` (chapter end via `chapterEndUtcEstimate`, recomputed after reanchors, 02 §3.19.4).
2. `core.calendar.get {year}` (public): holiday table of that year (all blocs), session tables of every product family (T02-05 `sessionState` sampled per tick-of-day range, merged into contiguous runs), boundary schedule (every DAY_OPEN/DAY_CLOSE is implicit, so list week/month/quarter/year/chapter boundaries and phase changes), and scheduled public events merged from the `CalendarEventSource`s of 04/06/09/16 sorted by (tick, module, kind); chapter end added by 02 itself with its wall-clock estimate.
3. `core.header.get {fromTick, toTick}` (public): toTick − fromTick + 1 ≤ 10,000 else Q_RANGE_TOO_LARGE; toTick ≤ lastCommitted else Q_NOT_COMMITTED; headers are returned as stored (their `entropyReveal` and `epochSeedReveal` fields are present only from the tick where they were published, so the query never leaks an unrevealed value).
4. `core.receipt.get {intentId}` (actor only): locate the tick, rebuild the Merkle proof over canonEncode of the sealed intents of that tick in the hashed order (T02-07 leaf rule), verify it against the header's intentsRoot, compute the fair-order percentile = floor(100 × position / count) (only the percentile is shown on the screen, 02 §7), and attach the outcome from `result`. A viewer that is neither the actor nor the `onBehalfOf` principal gets Q_FORBIDDEN.
5. `core.integrity.verify {tick}` (public): per the R28 epoch scheme (24 R28 > 02 §3.11 per-tick wording): epoch of the tick, its published commit C_e; if the epoch secret has been revealed, check `epochCommitHash(e, S_e) == C_e` (else COMMIT_MISMATCH) and recompute e(N) = HMAC(S_e, "tick" ‖ N) and compare with the stored header reveal (else ENTROPY_MISMATCH); if not yet revealed return revealed false, reason NOT_YET_REVEALED.
6. View models (02 §7, layouts in 17): tick pulse (heartbeat countdown from nextSealEtaMs, tick, game date and time in ET, phase badge, mode badge when CATCHUP or HALTED); calendar (from `calendarGet`); receipt sheet ("Sealed in tick T", percentile, "Verified" when proofVerified, outcome); integrity page (latest commits and reveals, verifier input wired to integrityVerify, epoch commits and reveals, uptime share = 1 − halted real time / total real time since genesis, halts and reanchors history from the anchor and halt log, public determinism incident count); halt banner (reason key, expected resume, a countdown during the `resume_notice_ms` window); clock-adjusted notice (visible for 720 ticks from each reanchor tick, with the new chapter end; the client shows it once). All text is i18n keys; no strings in the engine.
7. Determinism: queries do not touch the Store's write API and do not draw RNG; views read only `StoreRead` (G6 ViewHandler signature).

# SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

### §3.3 The tick driver: phases across partitions

**Rule 3.3.1 (bulk-synchronous phases).** Each tick runs the 15 phases of 00 §5.2 in order. For every phase `Pk`:
1. COORD broadcasts `PhaseStart(tick, Pk, fencingToken)` to all partitions.
2. Each partition runs `runPhase(Pk, tick, inbox_k)` where `inbox_k` is every `PhaseMessage` addressed to an entity it homes and produced in phases `< k` of this tick (or in P13/P14 of the previous tick for next-tick consequences), sorted by `canonicalKey`.
3. Each partition publishes its `outbox` to the bus subject `ph.<tick>.<k>.<destPartition>` and then `PhaseDone(tick, Pk, partitionId, outboxCount, digest)`.
4. When all `PhaseDone` messages arrive, COORD starts `P(k+1)`.
A phase in which a partition kind has no work (for example CITY in P6) still sends `PhaseDone` immediately. Phases are barriers; no partition starts `P(k+1)` before COORD says so.

**Rule 3.3.2 (phase ownership by partition kind).**

|---|---|---|---|---|---|---|---|
| P0 ingest | seals batch, assigns order keys, splits by home | receives its intents | – | – | – | – | – |
| P1 validate | validates sys/adm inputs | validates player intents, places holds (§3.5.3) | validates order shape vs instrument rules | validates prop/biz intents routed to it | validates bank/fund/ins intents for NPC-hosted products | margin pre-check | – |
| P2 calendar | boundary hooks; macro step at day close (04) | daily accrual hooks | session phase changes (05) | – | rate resets | – | – |
| P3 world | global world scheduler, news (16) | – | – | city events | – | – | actor decisions (16) |

**Rule 3.3.3 (phase time budget).** A tick has `TICK_REAL_SECONDS = 5` s of wall time. Default per-phase wall budgets (maximum across partitions, including barrier overhead):

| Phase | Budget ms | Phase | Budget ms |
|---|---|---|---|
| P0 | 100 | P8 | 300 |
| P1 | 250 | P9 | 300 |
| P2 | 50 | P10 | 150 |
| P3 | 200 | P11 | 100 |
| P4 | 300 | P12 | 150 |
| P5 | 900 | P13 | 250 |
| P6 | 600 | P14 | 300 |
| P7 | 300 | **Total** | **4,250 (slack 750)** |

Budgets are `PARAM.phase_budget_ms_P0 … PARAM.phase_budget_ms_P14` (values above). Intents for tick `N+1` are collected by gateways while tick `N` runs, so intake never consumes phase budget.

**Rule 3.3.4 (overrun: wait, never skip, never commit partially).**
1. If a phase exceeds its budget, nothing is cut. The tick simply finishes late; the next seal happens at `max(scheduledSeal(N+1), commit(N) + PARAM.min_inter_tick_gap_ms = 200)`. World time slows; it never jumps.
2. COORD measures `lateness = commitWallMs(N) − scheduledCommit(N)`. If lateness > 0 on `PARAM.catchup_trigger_ticks = 3` consecutive ticks, `WorldStatus` becomes `CATCHING_UP` (shown to clients as a small clock badge, 17).
3. While `CATCHING_UP`, the inter-tick gap shrinks to `PARAM.catchup_gap_ms = 200` until the world is back on schedule or `PARAM.catchup_max_ticks = 120` ticks pass; after that the schedule is re-based (the real-time anchor of the calendar moves forward by the accumulated delay; the game calendar itself is never skipped). Re-basing is recorded as a `sys.clock_rebased` event.
4. **Load levers are inputs, never side effects.** If COORD decides to reduce load (for example the AI-phase DU scale-down of 11), it submits a `SystemInput sys.load_scale { scale }` into the **next** batch. The engine reads it like any other input, so replay reproduces it exactly. A partition never changes its own behaviour based on wall-clock time or measured load.
5. A phase that has not reported `PhaseDone` after `PARAM.phase_hard_timeout_ms = 15000` is treated as a partition failure (§3.7.4).

**Rule 3.3.5 (next-tick consequences).** A consequence discovered in phase `k` that would require an earlier phase to rerun (for example a margin call found in P7 that becomes a liquidation order, or a hack resolved in P10 opening a session) is emitted as a `PhaseMessage` addressed to tick `N+1`, phase of its owner. It is stored with the tick's outputs and delivered in that phase's inbox on the next tick. This is the only way a cascade propagates, and it keeps every cascade ordered and replayable (vision/02-multiplayer §3.2 rule "consequences land next tick").
