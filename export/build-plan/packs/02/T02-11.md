## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

2. `defineModule`: checks that `id` starts with `module`, that every table's `module` equals `m.module` (MOD_TABLE_OWNER), every event kind has a namespace prefix allowed for the module (MOD_EVENT_NS), every intent kind namespace allowed (MOD_INTENT_NS), stream prefixes are registered in `STREAM_REGISTRY` for this module (MOD_STREAM_FOREIGN via T02-06 `matchStream` on the prefix + ':x' or the bare key), and freezes the object. # SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

**[02 §3.5.2]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.5.2 System rule (from 00 §5.2, restated with detail)

- A phase may read: (a) any state committed by earlier ticks; (b) outputs of earlier phases of the same tick that are visible to its partition (local outputs, or messages delivered at a barrier).
- A phase writes only: its own module's entities in its own partition, events, outgoing partition messages, and **posting requests** queued for P13.
- Money and asset balances seen during P1–P12 are **pre-tick balances minus holds plus intra-tick provisional changes the owning module tracks itself**. The ledger balance itself changes only in P13. A module that needs "cash available now" calls `ledger.available(account)` = committed balance − active holds (03).
- Postings never commit before P13. If P13 fails, nothing of the tick exists (§3.15).


<!-- excerpt 02§3.6.2 -->
**[02 §3.6.2]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.6.2 Obligations of every module inside `step()`

1. No reading of `Date`, `performance`, `process.hrtime`, environment variables, files, network, timers, `Math.random`, `crypto.getRandomValues`, or any global mutable state.
2. Randomness only from the module's own RNG streams (§3.10).
3. Money only through ledger posting requests (00 §5.4); quantities of assets only through the ledger's asset postings (03).
4. IDs only through `newId(kind)` (§3.13).
5. Floats only through the rules of §3.7 and the `dmath` library (§3.8); conversions to money only through `toMoney` and the fixed-point helpers (§3.9).
6. Iteration only over sorted collections (§3.7.3).
7. No exceptions for control flow. A module that detects an impossible state returns an `InvariantResult { ok: false }` and does not throw; `step()` itself catches any thrown error, converts it to a failed invariant `I0 (uncaught)` naming the module and entity, and the tick goes to safe mode (§3.15).
8. Bounded work per tick: every loop over entities must be bounded by state size; no unbounded retries; rejection sampling is forbidden (§3.10.5).


<!-- excerpt 02§6 -->
**[02 §6]** (from spec file 02-TIME-ENGINE-CORE.md)

## §6 NPC behaviour

1. NPCs (liquidity providers, named actors, NPC institutions, aggregate sectors) act only inside the pipeline: they produce **NPC intents** in P3/P4 (and institutional actions in P7/P8) with `channel = 'NPC'`. NPC intents have no signature or nonce, receive `orderKey` like player intents (computed from the same tick entropy), and pass the same validation rules (licenses, balances, holds). This is the fairness rule of 00 §5.5 applied to NPCs: no NPC has a private API.
2. NPC decision cadences are tick-based and staggered by `fnv1a32(npcId) mod cadence` so they spread across ticks (16 defines cadences; default named-actor review every 30 ticks).
3. NPCs never see sealed intents of the current tick before they decide (P3/P4 read committed state and the header only). In particular NPC liquidity quotes in P4 do not see players' orders of tick N (05).
4. Aggregate sectors (`hh`, `frm`, `row`) are updated at day close by 04 (macro) and hourly by 09/10 (demand), never per tick.

#### §3.3.3 Templates (the only way to build entries)

Notation: `E:code` = account of entity E. `cb` = central bank of the currency. "Value leg" = the account that records what the payer gets and the payee gives (expense, income, asset, liability), chosen by the reason code's mapping table (each code lists its default value-leg accounts in the code catalog generator, 22/23 data; examples below).

| Template | Use | Postings |
|---|---|---|
| `PAY(A → B, amt, code, valueLegA, valueLegB)` | core-to-core payment for goods, services, fees, taxes, dividends (TRANSFER codes) | (1) cash leg via the payment rail (§3.3.4); (2) `Dr A:valueLegA / Cr B:valueLegB` |
| `SWAP_ASSET(A ⇄ B, asset, qty, price, code)` | purchase/sale of an asset for money | (1) cash leg buyer→seller via rail; (2) `Dr Buyer:assetAcct / Cr Seller:assetAcct` with `qty` and `amount = notional`; (3) seller's book adjustment: if seller's book value of the qty ≠ notional, `Dr Seller:assetAcct / Cr Seller:4060|4090` (gain) or `Dr Seller:5160|5190 / Cr Seller:assetAcct` (loss) |
| `MINT(sys → E, amt, code, valueLegE)` | FAUCET with no elastic counterparty (start cash, grants, ads, compensation) | (1) `Dr E:1001 / Cr cb:2001`; (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:5900 / Cr E:valueLegE` (default 4110) |
| `BURN(E → sys, amt, code, valueLegE)` | SINK with no elastic counterparty (fines' sink share, levies, licence fees) | (1) `Dr cb:2001 / Cr E:1001`; (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr E:valueLegE / Cr sys:4900` |
| `ELASTIC_IN(X → E, amt, code, valueLegX, valueLegE)` | FAUCET: an elastic sector X (hh, frm, row) pays a core entity | (1) `Dr E:1001 / Cr cb:2001` (or reserves if E is a bank); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:2909:X / Cr X:1009`; (4) `Dr X:valueLegX / Cr E:valueLegE` |
| `ELASTIC_OUT(E → X, amt, code, valueLegE, valueLegX)` | SINK: a core entity pays an elastic sector | mirror of `ELASTIC_IN` |
| `LEND(bank B → borrower C, amt, code)` | CREDIT_CREATE | (1) `Dr C:1010:B / Cr B:2100:C` (new deposit; if C's receiving account is settlement cash, the rail then moves it out of B as a TRANSFER payment); (2) `Dr B:13xx:loanId / Cr C:22xx:loanId` |
| `REPAY(C → B, principal, code)` | CREDIT_DESTROY | (1) `Dr B:2100:C / Cr C:1010:B` (deposit extinguished; if C pays from settlement cash, the rail first moves it into B); (2) `Dr C:22xx / Cr B:13xx` |
| `CB_CREDIT(cb → bank B, amt, code)` | CREDIT_CREATE at the central bank (M0_cb up) | (1) `Dr B:1002 / Cr cb:2002:B`; (2) `Dr cb:1307|1520 / Cr B:2120|asset sold` |
| `CB_CREDIT_UNWIND` | CREDIT_DESTROY at the central bank | mirror |
| `ACCRUE(E, amt, code, dr, cr)` | REVALUE, intra-entity non-cash: accrual, depreciation, provision, MTM, impairment, revaluation | `Dr E:dr / Cr E:cr` (one posting, same entity) |
| `ACCRUE_PAIR(A, B, amt, code)` | REVALUE accrual of a bilateral amount (interest accrued on a loan) | `ACCRUE(A, receivable/income)` + `ACCRUE(B, expense/payable)` in one entry |

Every template returns the list of postings it generated; the code catalog defines which templates a code may use (`allowedTemplates`). A FAUCET code can only use `MINT` or `ELASTIC_IN`; a SINK code only `BURN` or `ELASTIC_OUT`; CREDIT codes only `LEND`, `REPAY`, `CB_CREDIT`, `CB_CREDIT_UNWIND`; REVALUE codes only `ACCRUE`, `ACCRUE_PAIR`, `RECLASS`; TRANSFER codes `PAY`, `SWAP_ASSET`, `FX`, `MOVE_QTY`. This is how "each reason code belongs to exactly one class" (00 §5.4) is enforced mechanically.
