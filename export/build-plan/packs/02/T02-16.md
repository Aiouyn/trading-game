## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Goal
Guarantee that no tick ever commits with a failed FATAL invariant and that the world recovers deterministically (02 §3.15, 20 Rule 3.2.2 as adopted by 24 D417): any error thrown inside a phase is caught and turned into invariant `I0` naming module and entity; an aborted tick is re-run in safe mode with posting-level validation and an attribution trace; the first failing item is quarantined (INTENT, ENTITY or SUBSYSTEM) and recorded in the re-issued, hashed header; when no single item is attributable, bisection over the tick's intents (T20A-02) finds culprits; quarantined intents are rejected `SYS_QUARANTINED` (a second one for the same actor and kind within a real day blocks that kind, `SYS_KIND_BLOCKED`); a failure with no culprit, a subsystem failing 5 ticks in a row, or exhausted attempts halts the world (`HALTED_EXCHANGE`). Every branch writes an `InvariantViolation` and a `RegressionCase` record (as outputs for 19.B to persist). ALERT invariants (INV-ENG-010 phase budgets) never block.

## Implementation steps
1. Trap: every module call made by the runtime (validate, apply, phase function, boundary hook, genesis, invariant check) is wrapped by `trapPhase` with its attribution; the failure is recorded as a FATAL failure for P13 (02 §3.6.2 rule 7). `toMoney(NaN)` therefore becomes failed invariant `I0.nan` (02 AT 16) and the tick goes to the ladder.
2. Normal attempt fails (any FATAL failure or ABORT from T02-15) -> nothing of the attempt is published: discard its events, postings, deltas, results (02 AT 31), emit `core.safe_mode.entered` PUBLIC {tick, attempt} with a SEALED twin carrying {invariantId, trace} and internal `tm.invariant.failed`, `tm.safe_mode.entered`.
3. QUARANTINE-severity failures (20 Rule 3.2.5) with an attributed intent: re-run the tick once with that intent rejected SYS_QUARANTINED in NORMAL mode (modules have no per-entity phase entry points, so a full deterministic re-run is the per-entity re-run); if it passes, commit NORMAL; otherwise continue with step 4.
4. Ladder via `decideLadder` (T20A-02) with hooks:
   - `runSafe(quarantine)` = re-run tick N from the committed state of N−1 with the same header, intents and entropy, `postingValidation = true` (every posting request is checked by the ledger port at queue time) and a full trace; quarantined INTENTs skipped (rejected SYS_QUARANTINED, holds released, message "This action could not be processed and has been sent for review. Nothing was charged." via i18n key `err.SYS_QUARANTINED`), ENTITYs frozen for the tick (runtime `skip.entities`: the bound store hides frozen entities from `iter`/`range`/`index` and rejects writes to them for that tick, so no module accrues or operates them; flagged 'ENGINE_REVIEW' in T_WORLD.frozen), SUBSYSTEMs skipped (phase function `<module>.<phase>` not called; state carries forward).
   - `passesWithout(excluded)` = safe re-run with those intents excluded (fair order of the rest unchanged, INV-MKT-006).
   - options: maxAttempts = PARAM.safe_mode_max_attempts (3), bisect {maxTrials 24, budgetMs 20,000, now = deps.clock}, subsystemHaltAt = 5.
   Safe mode never changes entropy, RNG of non-quarantined work or the fair order (02 §3.15.3 rules).
5. Verdict COMMIT_SAFE: header.quarantine = entries (kind, id, reason = first failing invariant id, decidedAtAttempt): the header is re-issued and hashed, so replay of the recorded header reproduces the same exclusion (02 AT 29); commit with mode SAFE; emit `core.safe_mode.recovered` {tick, quarantinedCount}, `tm.intent.quarantined` PRIVATE to each quarantined actor, internal `tm.safe_mode.recovered`, `tm.bisect.result`; tracker.record per quarantined intent: BLOCK_KIND -> the actor's later intents of that kind are rejected `SYS_KIND_BLOCKED` in P1 until staff clear (state in T_QUARANTINE). `recoveredWithoutQuarantine` -> HIGH RegressionCase "normal vs safe mode discrepancy" (determinism defect). Update subsystem streaks in T_WORLD (increment for quarantined subsystems, reset others).
6. Verdict HALT: world status HALTED_EXCHANGE in the coordinator (not a committed tick: the world stays at N−1 committed), public event `tm.world.halted` {tick, reasonCategory: 'SYSTEM_CHECK'} plus `core.halt` {reason key 'halt.system_check'}; no further tick commits until a RESUME directive (T02-19). For SYSTEM_INPUT culprits (20 §8 edge 4) the same halt applies.
7. Records: one InvariantViolation per failing invariant (attempt NORMAL or SAFE_MODE, outcome QUARANTINED / RECOVERED_IN_SAFE_MODE / PARTITION_HALTED / ALERT_ONLY) and one RegressionCase per tick with a ReproBundle from `deps.bundleFor(tick)` (severity HIGH, CRITICAL for halts); returned in LadderOutcome for 19.B to persist (no I/O here).
8. INV-ENG-010 (TICK, ALERT): durations come from the injected clock and never enter hashed state; failing it emits internal `tm.invariant.alert` and `core.budget.overrun` {partitionId, phase, ms} telemetry; the tick commits.
9. Edge cases covered here (02 §8): 7 (atomic swap side quarantined: both legs absent, both holds released: test), 12 (NaN in one business -> entity quarantined for the tick; repeated failures listed in records); 20 §8 edges 1 (chapter-boundary tick re-runs P2 hooks in safe mode, no double firing: INV-ENG-007 holds), 2 (holds from T−1 survive rollback of T), 3 (pair culprits), 4 (system input -> halt).

# SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

#### §3.15.2 Rollback

Rollback of the current tick is free (discard the prepared state). **No committed tick is ever rolled back** in the live world. Errors found later are corrected by **compensating postings** (`ADM_CORRECTION_*` reason codes, 03 §3.4) through two-approval admin intents (21), with a targeted list of beneficiaries found by replay (02-multiplayer §10.1). This keeps the event log append-only and the world history honest.

**[02 §3.15.3]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.15.3 Safe mode (deterministic isolation)

When `ABORT(N)` happens because of invariant failures:

```
attempt = 1
loop while attempt <= PARAM.safe_mode_max_attempts (DEFAULT 3):
  1. Re-run tick N with the same header, intents and entropy, with posting-level validation ON:
     every posting request is checked against I1/I2/I10/I16 at the moment it is queued, and
     each module's work is attributed (module, entityId, intentId) in a trace.
  2. Identify the first failing item in canonical order:
       - a player/AI/NPC intent whose processing produced the failing posting -> quarantine INTENT
       - else an entity whose scheduled processing produced it              -> quarantine ENTITY
       - else a module-level computation (e.g. 04 macro step)               -> quarantine SUBSYSTEM
  3. Add the QuarantineEntry to header.quarantine (the header is re-issued for tick N; quarantine is
     part of the hashed header, so replay reproduces the exact same exclusion).
  4. Re-run tick N with quarantined items skipped:
       INTENT     -> rejected with REJECT_SAFE_MODE (holds released, player notified "Order not processed, no charge")
       ENTITY     -> the entity is frozen for this tick (no accrual, no ops; flagged 'ENGINE_REVIEW')
       SUBSYSTEM  -> the subsystem's phase for this tick is skipped; its state carries forward unchanged
  5. If all invariants pass -> COMMIT with mode = SAFE; emit core.safe_mode.recovered; page ops (19, 21).
  6. Else attempt += 1.
if still failing: HALT the world (§3.20), mode = HALTED; page ops at highest severity.
```

Rules: a quarantined ENTITY stays frozen in later ticks only if ops sets a persistent freeze (admin directive); by default it is retried at the next tick (if it fails again, safe mode repeats). A quarantined SUBSYSTEM is retried next tick, and after `PARAM.safe_mode_subsystem_repeat_halt` (DEFAULT 5) consecutive quarantines the world halts. Safe mode never changes the entropy, the RNG state of non-quarantined work, or the fair order.

## §8 Edge cases

1. **Tick 0.** Genesis state is produced by `createWorld(genesisConfig)` (pure, from the content seed); tick 0 runs the full pipeline with start-of-period hooks for chapter 1, year 1, quarter 1, month 1, week 1, day 1. `prevTickHash` of tick 0 = SHA-256('TYC/genesis' || genesisStateHash).
2. **Day close at t = 719 coinciding with month, quarter, year and chapter end** (e.g. the last tick of a chapter that is also a year end): end hooks run innermost first (day, week, month, quarter, year, chapter). Day-close may use up to 400 ms from slack; a chapter-end tick may exceed 5 s and is the expected worst case; scheduling absorbs it via CATCHUP.
3. **Holiday on a coupon date**: modified following; accrual continues daily so the coupon amount is unchanged.
4. **Order submitted for a closed product** (weekend equity order): accepted and queued (it holds funds) if the order type allows queuing (05), otherwise rejected `REJECT_MARKET_CLOSED`.
5. **Intent arriving exactly at the seal**: belongs to whichever batch the gateway had open when it processed `SEAL(N)`; the gateway is single-threaded per connection, so there is no ambiguity.
6. **Gateway crash mid-batch**: intents in its open batch are lost unless acknowledged; clients only treat an intent as submitted after the gateway's `ack(intentId, tick)` (19). Lost intents are resubmitted by the client with the same `intentId` and nonce; duplicates in later ticks are rejected `REJECT_REPLAY` if the first one was sealed.
7. **Safe mode quarantines a player's intent that was part of an atomic swap**: the counterpart's leg is also not produced (atomicity), both holds release, both players see "not processed".
8. **A stream that is never drawn for a long time**: no mixing occurs while unused; when next drawn, it mixes that tick's entropy (state from the last use plus fresh entropy). At epoch change it is re-seeded regardless.
9. **New content mid-chapter** (a new city opens): its streams are seeded from the current epoch root on first use; existing streams are untouched.
10. **Partition count changes**: does not alter any result (IDs include `partitionId`, so new entities created after a rebalance get different IDs than they would have; that is acceptable because replay reproduces the actual history including the rebalance directive).
11. **Replay across an engine version boundary**: the replay engine switches bundle at the `VERSION_CUTOVER` tick and applies the recorded migration.
12. **NaN produced by a model** in one business: safe mode quarantines that entity for the tick; repeated failures surface in ops with the entity id.
13. **Clock skew on the coordinator host after failover**: the standby uses its own disciplined clock; any skew is absorbed by slewing; a large jump forward produces lag, handled by CATCHUP or REANCHOR.
14. **A real-world leap second or DST**: irrelevant; UTC monotonic schedule; DST does not exist in game time.
15. **Player in a time zone where the game week rotates**: game weekday at a given real hour shifts by 3 hours per real day (24 mod 7 = 3), so a player who always plays at 20:00 local sees a different game weekday each day. This is intended (every real-world region gets every phase, 02-multiplayer §2.2).
16. **Chapter end during a halt**: the chapter ends at its game-day boundary after resume; ladders settle then.
17. **Very large money amounts in floats** (> $9B): handled per §3.9.2; exact computations use bigint helpers.
18. **Overflow of tick counter**: `Tick` is a JS number up to 2^53 (about 1.4 billion years at 5 s); no overflow.

### §3.2 Invariant execution and failure handling

**Rule 3.2.1 (when checks run).** TICK invariants run in P13 after postings are staged and before commit, on every partition, over that partition's write set; the aggregate ones (INV-LED-003, -004) are computed per partition as partial sums and summed by COORD at the P13 barrier before COORD issues commit (19 §3.3). PHASE invariants run at the end of their phase on the partitions of the kind that runs that phase. DAY_CLOSE invariants run in P13 of the tick with tick-of-day 719. SNAPSHOT invariants run in the snapshot writer against the serialized state before upload; a failing snapshot is not uploaded and the previous one stays current. OFFLINE invariants run in the shadow verifier (§3.11.1) and in nightly jobs.

**Rule 3.2.2 (failure ladder for FATAL).** When any FATAL invariant fails on tick `T`:
1. The partition reports `PhaseDone(P13, failed=[ids])`. COORD does not commit `T` anywhere; every partition calls `rollback(T)` (19 §2.6).
2. **Safe-mode replay** (02): COORD re-runs tick `T` from the committed state of `T − 1` with every partition in single-threaded safe mode (extra assertions on, per-phase invariant checks for every scope, phase outputs logged in full).
3. If safe mode passes all invariants, its result commits with `TickRecord.safeMode = true`, a `tm.safe_mode.recovered` event is emitted (internal) and a RegressionCase of severity HIGH is filed with the normal-mode failure (the discrepancy between modes is itself a determinism defect).
4. If safe mode fails, COORD runs **bisection** (Rule 3.2.3) to find culprit intents.
5. If bisection isolates culprit intents, those intents are **quarantined** (Rule 3.2.4) and tick `T` commits without them.
6. If bisection finds no culprit (the failure happens with zero player intents, i.e. a system defect), COORD sets world status `HALTED_EXCHANGE` (19 `WorldStatus`), clients show the diegetic "Trading halted by the Exchange" overlay (17), on-call is paged at incident level INC-1 (21 §3.17), and the world waits at tick `T − 1` committed. Resume needs a hotfix deploy that passes the FAST regression for this case (§3.9 G4 hotfix path).
7. In every branch, an `InvariantViolation` record and a RegressionCase with a full ReproBundle are written.

**Rule 3.2.3 (bisection).** Let `B` be tick `T`'s sealed intents in canonical order (system inputs are never bisected out; they are re-applied in all trials). Trials re-run tick `T` in safe mode with a subset of `B`:
```
candidates = B
while |candidates| > 1 and trials < PARAM.tm_bisect_max_trials (default 24):
    half = first ⌈|candidates|/2⌉ of candidates (canonical order)
    if run(T, intents = B − half) passes: candidates = half          // culprit is inside half
    else if run(T, intents = B − (candidates − half)) passes: candidates = candidates − half
    else: break                                                       // interaction between both halves
culprits = candidates if run(T, B − candidates) passes else ∅
```
Total bisection wall time is bounded by `PARAM.tm_bisect_budget_ms = 20000`; if the budget runs out with no culprit, branch 6 of Rule 3.2.2 applies. Bisection uses only the intents of tick `T`; it never drops intents of earlier ticks. Because ordering inside a tick depends only on `orderKey` (INV-MKT-006), removing intents does not reorder the rest.

**Rule 3.2.4 (quarantine).** A quarantined intent is rejected with `IntentResult.status = 'REJECTED'`, `rejectCode = 'SYS_QUARANTINED'` and the localized message "This action could not be processed and has been sent for review. Nothing was charged." Its actor is not penalized and not flagged for cheating on that basis alone. A second quarantine for the same `(actorId, kind)` within `PARAM.tm_quarantine_repeat_window_ticks = 17280` (1 real day) places a temporary block on that intent kind for that actor until a staff member clears it in the admin console (21 §3.6), because a reproducible culprit may be an exploit in progress. The quarantined intents and their actors are attached to the RegressionCase.

**Rule 3.2.5 (QUARANTINE-severity invariants).** Some invariants name a single entity as the fault (for example INV-BS-011 holds exceeding balance for one character). For these, the partition rejects the specific intent or phase message that produced the write, re-runs only that entity's work for the phase (the store supports per-entity undo within a tick), and the tick continues. If the per-entity re-run still fails, escalate to Rule 3.2.2.

**Rule 3.2.6 (no sampling).** Invariants are never sampled or skipped for performance. If the invariant budget threatens the tick budget, the response is optimization or more partitions, never fewer checks. Budget: `PARAM.tm_invariant_budget_share = 0.10` (invariants may use up to 10% of P13's budget at the STANDARD preset and 100k CCU target, measured in the load gate §3.14).

**Rule 3.2.7 (ALERT-severity).** The tick commits; an internal `tm.invariant.alert` event is emitted; the Truth Machine dashboard shows it; on-call is paged for INC-3 or higher per 21 §3.17's table; a RegressionCase of severity MEDIUM is filed.

## §8 Edge cases

1. **Invariant failure on a chapter-boundary tick.** The boundary hooks (P2) re-run with the tick in safe mode; ladder settlement waits for the committed tick; the boundary is never skipped or doubled (INV-ENG-007).
2. **Failure while a cross-partition transfer is in flight.** The rollback of tick T releases holds placed in T; holds from T − 1 stay and settle in the replay (INV-BS-012 bounds them to 2 ticks).
3. **Bisection hits an intent pair that only fails together** (e.g. two linked accounts in the same tick): bisection breaks without a single culprit; if removing both passes, both are quarantined; otherwise Rule 3.2.2 step 6.
4. **The culprit is a system input** (an admin parameter change or ad grant): system inputs are never quarantined automatically; the world halts (step 6) and staff revert the system input through a new two-person `adm.*` input (21 §3.2).
5. **Shadow verifier falls behind by more than a game day** after a snapshot gap: it reloads the latest DAILY snapshot and continues; the skipped range is verified by a nightly OFFLINE replay job so no tick goes unverified for more than 2 real days.
6. **Engine version change mid-chapter.** Equivalence and version replay compare like with like: an `EquivalenceRun` never mixes engine versions; version replay uses intended-change effective ticks (Rule 3.3.6).
7. **A band's metric is undefined** for a seed (e.g. no recession happened, so recession length is undefined): the seed is excluded from that metric and `seedsUsed` reported; if fewer than 80% of seeds define the metric the run is extended with more seeds until 80% do or 3× the seed count is reached, then reported as `INSUFFICIENT_DATA` (counts as fail at G3 only for ACCOUNTING bands).
8. **A system is built but its flag is off in production.** Its bands and hunts run in G3 anyway (with the flag on in harness worlds); they block only the release that turns that flag on, not other releases.
9. **WITHHELD seeds exhausted mid-chapter** (too many G3 runs): fresh indices are drawn from the same salt; the set never reuses a retired index.
10. **A test agent hits a rate limit or a license gate.** That is data: the agent waits as a player would; hunts that need a license first progress the agent to it legitimately (or start from a fast-forwarded MIRROR character with that license).
