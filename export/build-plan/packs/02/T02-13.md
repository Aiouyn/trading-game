## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `hookPlan`: boundaries present at the tick; end hooks first in END_HOOK_ORDER (DAY_CLOSE, WEEK_CLOSE, MONTH_CLOSE, QUARTER_CLOSE, YEAR_CLOSE, CHAPTER_CLOSE: innermost first) then start hooks in START_HOOK_ORDER (CHAPTER_OPEN, YEAR_OPEN, QUARTER_OPEN, MONTH_OPEN, WEEK_OPEN, DAY_OPEN, HOUR: outermost first), then PHASE_CHANGE; within a boundary, modules in module-number order (03, 04, 05, …; core '02' first). Entities in sorted id order is the module's own loop (document in JSDoc: modules must iterate `store.iter` which is sorted). Hooks run in P2 after P0/P1 (02 §3.4) on the partition that owns the module's state (T02-14 routes; single partition here).
2. Core's own boundary work (module '02' hooks, implemented here as functions T02-21 registers): PHASE_CHANGE -> `core.phase.changed` {phase, productFamiliesOpen} PUBLIC; DAY_OPEN with holidays -> `core.holiday` {holidayId, blocs} PUBLIC per holiday; every *_OPEN/*_CLOSE of week/month/quarter/year/chapter -> `core.period.boundary` {period, edge, index} PUBLIC; CHAPTER_OPEN -> `core.epoch.rotated` {epoch, publicRootCommit, revealedEpoch?} PUBLIC; DAY_CLOSE commit -> `core.day.closed` {dayIndex, gameDate canonical string} emitted in P14 after commit; every commit -> `core.tick.committed` {tick, worldHash, intentsRoot, mode} PUBLIC (worldHash is known after P13; emit in P14 with seq after all phase events).
3. Consequences: `ctx.send(to, kind, body, 'NEXT')` messages are collected after P12, sorted by canonicalKey, and written to T_INBOX (`inbox_<N+1>`) as part of tick N's state (so they are hashed and survive a crash). At tick N+1, R1 starts by delivering them: phase handlers read them via `ctx.inbox(kind)` in the phase named by the consequence (`PhaseMessage.phase` = executedIn), and SYSTEM consequence intents (liquidations, contract payments, freezes) are prepended to P1 processing BEFORE any intent of N+1, in canonicalKey order, bypassing rate limits (02 §3.5.4 table). After delivery the inbox row is deleted. `CONSEQUENCE_KINDS` lists the 8 rows of the table (liquidation order P7->P1, default-waterfall step P7->P7, bank-run wave P8->P8, hidden session opened P10->P10, freeze/Held start P11->P1, contract scheduled payment P12->P1, corporate action effective P2->P2, news publication P3->delivered at P14).
4. B1/B2/B3 messages in single-partition mode are delivered to the target phase within the same tick (T02-14 implements barriers); here they go into the inbox of the next phase in the same runtime.
5. Delta filter (INV-ENG-005, L11): each ClientDelta carries `sourceVisibility` and `partyIds`. Rules: PUBLIC -> any recipient incl. `pub:*`; OWNER -> recipient must equal the single owner id; PARTIES/PRIVATE -> recipient ∈ partyIds and never a `pub:` channel; SEALED events never produce deltas. A delta violating its rule is dropped and recorded in the audit fact; INV-ENG-005 fails when the audit is non-empty (TICK, FATAL: the tick does not commit, so the leaking code is found by safe mode). Events with PARTIES/PRIVATE visibility get `partyIds` defaulting to subjectIds when omitted.
6. INV-ENG-007 (TICK, FATAL): post T_WORLD.tick === pre T_WORLD.tick + 1 (genesis: pre absent and tick 0); `FACT_HOOKS_FIRED` equals `hookPlan(calendarOf(tick))` exactly (no boundary skipped or doubled, 20 §8 edge 1).
7. Edit `PartitionRuntime.runTick` to call these at the right places; nothing else changes.

# SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

### §3.4 What happens at each boundary

Boundary hooks run in **P2 calendar** of the tick where the boundary occurs. Two kinds exist: **end-of-period hooks** run at the period's last tick (`t = 719` of its last day), after P0/P1 but before P3; **start-of-period hooks** run at `t = 0` of the period's first day. When several periods end at the same tick, end hooks run **innermost first** (hour, day, week, month, quarter, year, chapter); when several start, start hooks run **outermost first** (chapter, year, quarter, month, week, day, hour). Inside one hook, owners run in module-number order (03, 04, 05, …, 16), then entities in sorted id order.

Note on accruals: 00 §5.1 says accruals post at day close (t = 719). The day-close hook therefore runs in P2 of t = 719, but the accrual **postings** are queued to P13 like every posting (00 §5.2 rule). Macro (04) runs at day close inside P2 so its new state is visible to P3–P12 of t = 719 and to every later tick.

#### §3.5.4 "Consequences land next tick"

Everything that a later phase of tick N discovers and that would require new matching, new validation or new holds becomes an input of tick N+1. This is the single rule that keeps cascades ordered and replayable (02-multiplayer §3.2). Complete list of cross-tick consequence kinds (each owner defines payload):

| Consequence | Produced in | Executed in tick N+1 phase |
|---|---|---|
| Liquidation order (margin call not met) | P7 | P1 (bypasses rate limits; channel `SYSTEM`) |
| Default-waterfall step | P7 | P7 |
| Bank-run withdrawal wave (deposit flight computed from confidence) | P8 | P8 |
| Hidden session opened | P10 | P10 |
| Freeze / Held start (after 1 game-day grace, 13) | P11 | P1 (validation reads it) |
| Contract scheduled payment, option exercise, penalty | P12 | P1 (as SYSTEM intents) |
| Corporate action effective (split, dividend ex-date) | P2 | P2 |
| News publication to clients | P3 (generated) | delivered to clients at P14 of N, after N+1's intake is already open (02-multiplayer §3.2) |
