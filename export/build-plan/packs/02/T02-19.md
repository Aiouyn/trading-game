## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. Anchor: genesisUtcMs is the tick-0 instant (DEFAULT 18:00:00 UTC on launch day, set in GenesisConfig of T02-17). `applyReanchor` adds `deltaMs` to `reanchorOffsetMs` and appends a history row; it never changes any tick number or any tick-count duration (02 §3.19.4). The anchor is stored in `T_WORLD` (core.world row) so it is part of state and replay.
2. Seal rule (02 §3.19.1): tick N may seal at `max(scheduled(N) + slewMs, lastSealUtcMs + minInterval)` with minInterval 5,000 ms in NORMAL and `catchup_min_interval_ms` (2,500) in CATCHUP, and only after N−1 is committed (`decideSeal` returns WAIT otherwise). The decision returns the `sealUtcMs` that goes into the header (a recorded input, so replay never reads a clock).
3. Modes (02 §3.19.3), evaluated in `decideSeal` from `lag = now − scheduled(lastCommitted + 1)`: lag ≤ 0 -> NORMAL; 0 < lag ≤ `catchup_max_lag_ms` (300,000) -> CATCHUP (seal as soon as N−1 commits, never sooner than 2,500 ms after the previous seal, so lag shrinks by up to 2.5 s per tick); lag > 300,000 -> REANCHOR: the next sealed tick carries `AdminDirective {kind: 'REANCHOR', payload: {deltaMs: lag}}`, the anchor offset grows by `lag`, mode returns to NORMAL, and P14 emits `core.reanchor {deltaMs, newChapterEndUtc}` (T02-13 schema). Every tick number runs: there is no tick skipping. 19 §3.3's `CATCHING_UP` WorldStatus is shown while mode is CATCHUP (status mapping in step 8).
4. Skew (02 §3.19.2): the host feeds `SkewSample`s; `measureSkew` takes estimate minus the median of at least 3 sources (fewer than 3 throws EngineFault 'CLOCK_SOURCES'); when |skew| > `clock_max_skew_ms` (250) `slewStep` moves `slewMs` toward −skew by at most 10 ms per tick; |skew| > 2,000 ms also sets `page = true` (19.B pages ops). Gateway and client clocks are never inputs. A forward jump after a coordinator failover appears as lag and is handled by CATCHUP or REANCHOR (02 §8 edge 13).
5. HALT (02 §3.20.2): `haltWorld` is called for an `adm.halt` directive (validated by T02-18) or for a T02-16 ladder verdict HALT (automatic, one approval). Mode HALTED: `decideSeal` always returns WAIT with untilUtcMs = resumeAtUtcMs or a far sentinel; no tick seals, so no world time passes (no accrual, no cooldown, no offline-cap progress: they are tick counts). `intakeGate` returns `REJECT_HALTED` and 19's gateway answers the client with `core.intent.rejected {code: 'REJECT_HALTED'}` (the intent is not queued). `core.halt {reasonKey, expectedResumeUtc?}` is published by the host as a PUBLIC out-of-tick notice and repeated in the first tick after resume. WorldStatus becomes HALTED_EXCHANGE for unplanned halts and MAINTENANCE for planned ones (19 §2.1 WorldStatus values).
6. RESUME (02 §3.20.3): `announceResume` requires resumeAtUtcMs ≥ now + `resume_notice_ms` (60,000) (also checked by T02-18 as DIR_RESUME_NOTICE); at resume the first tick N = lastCommitted + 1 carries `REANCHOR {deltaMs = resumeAtUtcMs − scheduled(N)}` (reason HALT or MAINTENANCE) and `RESUME` directives, so scheduled(N) equals resumeAtUtcMs and the world resumes in NORMAL mode. P14 of that tick emits `core.resume` and, when the halt was a Truth Machine halt (reason key 'halt.system_check'), `tm.world.resumed {tick}` (20 §5). The first tick after resume is fair-ordered like any other (02 §9 halt exploit counter).
7. Maintenance (02 §3.20.4 as amended by 24 R29): `maintenanceToDirectives` turns a validated `adm.maintenance.schedule` into a planned HALT at startUtcMs and a RESUME at startUtcMs + durationMin; all markets halt (an engine halt covers every product family). Partial halts (one instrument, exchange or institution) are not engine halts and are not implemented here (05, 07, 13 own them).
8. Status mapping for `CoreWorldRow.status` and `core.clock.get`: NORMAL -> RUNNING, CATCHUP -> CATCHING_UP, HALTED -> HALTED_EXCHANGE or MAINTENANCE. On every commit the status is written by P14 from the decision's mode; a HALTED status is written by the host into the coordinator state (no tick commits while halted).
9. Outage review (02 §3.20.6): when an unplanned halt resumes after more than `outage_compensation_threshold_min` (30) real minutes, the host emits an ops record for 21's compensation review; the engine computes no money compensation (no world time passed, L7).
10. Wall-clock rules: `wallClockElapsedMs` reads only `ctx.header.sealUtcMs` (recorded input). Modules with real-time rules (14 dormancy at 30 real days, real-day quarantine windows of T02-16) use it; such rules keep progressing across a halt because the first tick after resume has a later sealUtcMs, while tick-count durations do not move.

# SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

#### §3.19.1 Schedule

```
scheduled(N) = genesisUtcMs + N * 5000 + reanchorOffsetMs
```

The coordinator seals tick N at `max(scheduled(N), sealed(N-1) + minInterval)` where `minInterval = 5000 ms` in NORMAL mode and `PARAM.catchup_min_interval_ms` (DEFAULT 2,500) in CATCHUP mode. Processing of tick N starts when N is sealed **and** N-1 is committed.


<!-- excerpt 02§3.19.2 -->
**[02 §3.19.2]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.19.2 Clock source and drift

- The coordinator's time source is the host clock disciplined by NTP/chrony against at least 3 sources, read as a monotonic clock offset by a periodically verified UTC estimate. Gateways' and clients' clocks are never used for sealing.
- Drift tolerance: if the coordinator's UTC estimate disagrees with its sources by more than `PARAM.clock_max_skew_ms` (DEFAULT 250 ms), it slews (adjusts the schedule gradually by at most 10 ms per tick) rather than jumping; skew > 2,000 ms pages ops.
- Clients receive with every tick `{tick, nextSealEtaMs}` and estimate their offset to the server with an NTP-style 4-timestamp exchange on the WebSocket (19). This is used only for the tick-pulse countdown ring (17); a client's clock can never change which tick an intent lands in.


<!-- excerpt 02§3.19.3 -->
**[02 §3.19.3]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.19.3 Lag and catch-up

`lag = now - scheduled(lastCommitted + 1)` (how far the world is behind its schedule).

| Lag | Mode | Behaviour |
|---|---|---|
| ≤ 0 | NORMAL | 5,000 ms cadence |
| 0 < lag ≤ `PARAM.catchup_max_lag_ms` (DEFAULT 300,000 = 5 real minutes = 60 ticks) | CATCHUP | seal as soon as the previous tick commits, but never sooner than 2,500 ms after the previous seal (players always get at least 2.5 s of intake per tick); the client pulse shows "catching up"; lag shrinks by up to 2.5 s per tick |
| lag > 5 real minutes | REANCHOR | the coordinator issues `REANCHOR { deltaMs = lag }` at the next tick: `reanchorOffsetMs += lag`, mode returns to NORMAL. The missed real time is **not simulated**: the world simply resumes; the game calendar falls behind wall-clock by `lag` forever (the 1 real hour = 1 game day rate of L9 is preserved; only the phase of the clock shifts). Clients see a one-time "Exchange clock adjusted" notice |

There is no "skipping" of ticks: every tick number runs, because skipping would break accrual and auction continuity. A world that is slower than real time for a sustained period (p99 work > 5 s) is a capacity incident; the planner adds partitions at the next daily boundary.


<!-- excerpt 02§3.19.4 -->
**[02 §3.19.4]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.19.4 Why world-clock durations are safe across reanchors

All durations are tick counts (§3.1.3), so a reanchor neither shortens nor lengthens anyone's protection, Held time, cooldown or loan term. Chapter boundaries are game-day based (every 1,344 game days), so a reanchor of `x` ms moves future chapter ends later in wall-clock time by `x`; the chapter's announced end time on the UI is recomputed and the ladder settles at the game-day boundary as defined (15).


<!-- excerpt 02§3.20 -->
**[02 §3.20]** (from spec file 02-TIME-ENGINE-CORE.md)

### §3.20 Halts and maintenance in a persistent world

1. **Zero-downtime is the default.** Deploys roll partition by partition at tick boundaries using graceful handover (02-multiplayer §11): the new process loads the latest snapshot + log, catches up, and takes over at a boundary. Most deploys cause no halt.
2. **HALT** (admin directive with two approvals, or automatic after safe-mode failure): the coordinator stops sealing new ticks after the last committed tick. Clients show the diegetic banner "Trading halted by the Exchange" (17). No world time passes: no accrual, no hidden-session progress, no cooldown progress, no offline-cap consumption. Intents submitted during a halt are rejected with `REJECT_HALTED` (not queued, so nobody gets a privileged first position on resume).
3. **RESUME**: the coordinator issues `REANCHOR { deltaMs = halt duration }` then resumes NORMAL mode. The first tick after resume is sealed at least `PARAM.resume_notice_ms` (DEFAULT 60,000) after the resume announcement, so every client can reconnect before trading resumes.
4. **Planned maintenance window** (only for changes that cannot be rolled, e.g. storage migrations): at most `PARAM.liveops_maintenance_max_minutes` (DEFAULT 30, owned by 21 Rule 3.3.3) real minutes per event and at most one event per real week, announced at least 24 real hours ahead (UI banner, push to opted-in players, Wire item), scheduled in the lowest-activity (quietest) real hour computed by 21 Rule 3.3.3 (ruling in 24); all markets, including crypto, perps and 24h commodities, are halted. Implemented as HALT + RESUME.
5. **Partial halts** (one instrument, one exchange, one institution) are market rules owned by 05 (circuit breakers), 07 (CCP), 13 (regulators); they are game events, not engine halts, and time keeps flowing.
6. Long outages: any unplanned halt longer than `PARAM.outage_compensation_threshold_min` (DEFAULT 30) triggers 21's compensation policy review; because world time stops with the halt, compensation is never money for "lost income" (no income was lost), only cosmetic goodwill (L7).

### §3.3 The tick driver: phases across partitions

**Rule 3.3.1 (bulk-synchronous phases).** Each tick runs the 15 phases of 00 §5.2 in order. For every phase `Pk`:
1. COORD broadcasts `PhaseStart(tick, Pk, fencingToken)` to all partitions.
2. Each partition runs `runPhase(Pk, tick, inbox_k)` where `inbox_k` is every `PhaseMessage` addressed to an entity it homes and produced in phases `< k` of this tick (or in P13/P14 of the previous tick for next-tick consequences), sorted by `canonicalKey`.
3. Each partition publishes its `outbox` to the bus subject `ph.<tick>.<k>.<destPartition>` and then `PhaseDone(tick, Pk, partitionId, outboxCount, digest)`.
4. When all `PhaseDone` messages arrive, COORD starts `P(k+1)`.
A phase in which a partition kind has no work (for example CITY in P6) still sends `PhaseDone` immediately. Phases are barriers; no partition starts `P(k+1)` before COORD says so.

**Rule 3.3.4 (overrun: wait, never skip, never commit partially).**
1. If a phase exceeds its budget, nothing is cut. The tick simply finishes late; the next seal happens at `max(scheduledSeal(N+1), commit(N) + PARAM.min_inter_tick_gap_ms = 200)`. World time slows; it never jumps.
2. COORD measures `lateness = commitWallMs(N) − scheduledCommit(N)`. If lateness > 0 on `PARAM.catchup_trigger_ticks = 3` consecutive ticks, `WorldStatus` becomes `CATCHING_UP` (shown to clients as a small clock badge, 17).
3. While `CATCHING_UP`, the inter-tick gap shrinks to `PARAM.catchup_gap_ms = 200` until the world is back on schedule or `PARAM.catchup_max_ticks = 120` ticks pass; after that the schedule is re-based (the real-time anchor of the calendar moves forward by the accumulated delay; the game calendar itself is never skipped). Re-basing is recorded as a `sys.clock_rebased` event.
4. **Load levers are inputs, never side effects.** If COORD decides to reduce load (for example the AI-phase DU scale-down of 11), it submits a `SystemInput sys.load_scale { scale }` into the **next** batch. The engine reads it like any other input, so replay reproduces it exactly. A partition never changes its own behaviour based on wall-clock time or measured load.
5. A phase that has not reported `PhaseDone` after `PARAM.phase_hard_timeout_ms = 15000` is treated as a partition failure (§3.7.4).

**Rule 3.3.5 (next-tick consequences).** A consequence discovered in phase `k` that would require an earlier phase to rerun (for example a margin call found in P7 that becomes a liquidation order, or a hack resolved in P10 opening a session) is emitted as a `PhaseMessage` addressed to tick `N+1`, phase of its owner. It is stored with the tick's outputs and delivered in that phase's inbox on the next tick. This is the only way a cascade propagates, and it keeps every cascade ordered and replayable (vision/02-multiplayer §3.2 rule "consequences land next tick").

**Rule 3.3.1 (levels of halt).**
