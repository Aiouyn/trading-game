## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `IdFactory.newId(kind)`: kind must match ID_KIND_RE (else EngineFault('I0.id_kind')); seq per kind starting 0 (SortedMap<kind, number>); digest = sha256Concat('TYC/id', salt, kind, u48be(tick), partitionId, u32be(seq)); id = kind + '_' + base32Crockford(u48be(tick) ‖ digest[0..9]) (16 bytes = 128 bits -> 26 chars, last char carries 3 bits padded with zeros). 
2. INV-ENG-003 (TICK, FATAL): for each fact row recompute the id from (salt, kind, tick, partitionId, seq) and compare; ids unique within the log; and `ctx.pre.get(table, id)` is undefined for every table the engine reports the id written into (the engine supplies `{id, table}` pairs under fact 'core.ids.written'). Fact keys are constants exported here.
3. Merkle: as documented in the export comment; proof siblings bottom-up. Leaves for `intentsRoot` are canonEncode of each sealed intent in fair order (T02-08 calls this).
4. `deriveTickEntropy`: value = sha256Concat('TYC/tick-entropy', worldId, u48be(N), eN, intentsRoot, prevWorldHash); words = 8 big-endian uint32 of value.
5. `EntropyBuffer` (R28 implementation of 02 §3.11.1 guarantees):
   - Secrets are created only through `ensureCommitted`; each new S_e = source.random32(); its commit C_e = epochCommitHash(e, S_e) with `publishedAtTick = (e - 1) * epochTicks - 1` (the last tick of epoch e-2), so every tick N of epoch e has its commitment public at least epochTicks = 720 ticks before N (02's `entropy_commit_lead_ticks` guarantee). For epochs 0 and 1 at genesis the commit is published in the genesis header (tick 0); document that the 720-tick lead holds from epoch 2 on and that epochs 0–1 are committed before tick 0's intake opens.
   - There is no way to replace a secret: `setSecret` always throws `EntropyChangeRefused('ENT_ALREADY_COMMITTED')` when a commit exists, and 'ENT_UNKNOWN_EPOCH' otherwise (secrets are never injected from outside).
   - `reveal(currentTick)`: epoch e is revealable when `currentTick >= (e + 1) * epochTicks - 1 + revealLagTicks`; so for any tick N of epoch e the reveal tick is ≥ N + 1,000.
   - `eOf(N)` = HMAC-SHA-256(S_e, utf8('tick') ‖ u64be(N)). When S_e is missing (failover without the buffer) return `{fallback: true}` and the caller uses `fallbackEntropy(prevTickHash)` and sets the header flag `entropyFallback` (02 §3.11.1).
6. `EpochRootStore`: public roots come from the injected `publicRootFor` (the coordinator generates 32 random bytes per chapter outside step()); secret epoch root per 02 §3.11.4. `harnessEpochRoots(localSeed)`: secretRoot = SHA-256('TYC/harness-secret' ‖ localSeed), publicRoot(k) = SHA-256('TYC/harness-public' ‖ localSeed ‖ u32be(k)).
7. `partyRollU`: subject ids sorted with cmpStr; the 53-bit value from the first 7 bytes (top 53 bits) of the digest divided by 2^53.
8. Exploit counters covered here (02 §9): seed prediction (lazy mixing uses `TickEntropy` words, epoch rotation, S streams never revealed: `EpochRootStore` never exposes secretRoot), operator rigging (commitment before intake; intentsRoot mixed into entropy), ID datamining (ids embed tick; 12 uses rotating labels from `ops.label:<chrId>`; nothing here).

# SPEC EXCERPTS (verbatim; binding game rules)

**[02 §1 Purpose]** (context)

## §1 Purpose

The world of TYCOON is one persistent, deterministic simulation that advances in discrete **ticks** of 5 real seconds. This module defines:

1. **The clock and calendar**: how a tick maps to a game date, time of day, trading phase, week, month, quarter, year and chapter, plus the holiday calendar of each bloc and what happens at every boundary.
2. **The tick pipeline**: the 15 phases P0 to P14 of 00 §5.2, how they run across invisible partitions, their time budgets, and what happens when a tick fails (rollback, safe mode).
3. **The pure `step()` contract**: the world advances only through a pure function of (state, sealed intents, entropy). No module may read the wall clock, a random source, the network or the disk inside `step()`.
4. **Determinism**: the coding rules, the deterministic math library, the fixed-point conversions (`toMoney` and friends), and the RNG streams (xoshiro128**, one stream per purpose and subject).
5. **Provable fairness**: commit-reveal entropy and fair intra-tick ordering, so the operator can prove it never rigged an outcome and no player can predict one.
6. **Persistence of time**: snapshots, event sourcing, replay, audit, versioning, catch-up when the server lags, clock drift, and maintenance in a world that never resets.

Design goals, in priority order: (a) the same inputs always give bit-identical outputs on any machine running the same engine version; (b) no player can gain anything from latency, device, timing or knowledge of the server; (c) a tick never commits partially; (d) the 5-second rhythm holds at 100k concurrent players and 750k AI agents (00 §5.7, 02-multiplayer §1).

### §2.6 Entropy

```ts
interface EntropyCommit { forTick: Tick; commit: Hash32; publishedAtTick: Tick; }
interface TickEntropy {
  tick: Tick;
  value: Hash32;      // SHA-256('TYC/tick-entropy' || worldId || tick || e(tick) || intentsRoot || prevTickHash)
  words: Uint32Array; // the 8 32-bit words of value, for cheap stream mixing
}
```

`e(tick)` is a 32-byte secret drawn from the coordinator's cryptographic random source (outside `step()`), generated `PARAM.entropy_commit_lead_ticks` ticks in advance and committed in a header before any intent of that tick can be submitted.


<!-- excerpt 02§3.11.1 -->
**[02 §3.11.1]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.11.1 Commit-reveal per tick

- The coordinator keeps a buffer of secrets `e(N)` for future ticks, generated from its cryptographic random source (outside the engine; stored in the secret store, 19).
- **Commit:** `C(N) = SHA-256('TYC/commit' || worldId || N || e(N))` is published in the header of tick `N - PARAM.entropy_commit_lead_ticks` (DEFAULT 720 = 1 game day ahead). Because it is published before tick N's intake opens, the operator is bound to `e(N)` before seeing any intent of tick N.
- **Reveal:** `e(N)` is published in the header of tick `N + PARAM.entropy_reveal_lag_ticks` (DEFAULT 1,000, kept from 02-multiplayer §3.3). Anyone can then check `SHA-256(...e(N)) == C(N)`.
- If the coordinator ever fails to have a committed `e(N)` (bug, failover without the buffer), tick N uses `e(N) = SHA-256('TYC/fallback' || prevTickHash)`, the header flags `entropyFallback = true`, and a public integrity incident is logged (21). The standby coordinator replicates the entropy buffer synchronously, so this should never happen in normal failover.

- Implementation (ruling in 24): 19 §3.12 realises these per-tick secrets with one epoch secret `S_e` per game day, `e(N) = HMAC-SHA-256(S_e, "tick" ‖ N)`; the epoch commitment `C_e` (published at the end of epoch `e−2`, so at least 720 ticks before any tick of epoch `e`) replaces the per-tick `C(N)`, and `S_e` is revealed 1,000 ticks after epoch `e` ends, which is never earlier than `N + 1,000` for any tick `N` of the epoch. The guarantees of this section (bound before intake, reveal no earlier than `N + entropy_reveal_lag_ticks`) are unchanged.

**[02 §3.11.2]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.11.2 Tick entropy

```
TickEntropy(N).value = SHA-256('TYC/tick-entropy' || worldId || N || e(N) || intentsRoot(N) || worldHash(N-1))
```

Neither the operator (committed to `e(N)` in advance) nor any player (does not know `e(N)`) can steer it. Including `intentsRoot` means even a leaked `e(N)` does not let the operator pre-compute outcomes before intents arrive.


<!-- excerpt 02§3.11.3 -->
**[02 §3.11.3]** (from spec file 02-TIME-ENGINE-CORE.md)

#### §3.11.3 What is public

Each `TickHeader` is public (served by the read API, 19) except that `entropyReveal` appears only after the lag. Players can download headers and verify (a) commit/reveal pairs, (b) that their own intent was included, using a Merkle inclusion proof from `intentsRoot` (the "Receipt" button, §7). They cannot recompute RNG draws because epoch roots (§3.11.4) are secret during the epoch.

### §3.13 Deterministic IDs

`newId(kind)` inside `step()`:

```
seq    = per-(partition, tick, kind) counter, starting at 0
digest = SHA-256('TYC/id' || worldSeedPublicSalt || kind || tick || partitionId || seq)
id     = kind + '_' + base32Crockford(tick as 6 bytes big-endian || digest[0..9])   // 26 chars like a ULID
```

`worldSeedPublicSalt` is a public constant of the world (not secret: IDs need not be unpredictable, only unique and replayable). Replay produces identical IDs. IDs embed the tick and therefore creation order; where that must not leak (connection entries in 12), the public label is a separate rotating random label from `ops.label:<chrId>` (00 §3.2).

## §9 Exploits and counters

| Exploit | Counter |
|---|---|
| Predicting prices from a leaked or guessed seed | per-tick entropy mixing (§3.10.3) from committed, secret `e(N)`; epoch rotation per chapter; S streams never revealed |
| Operator rigging an outcome after seeing intents | commitment `C(N)` published 720 ticks before tick N; `intentsRoot` mixed into entropy; public verification |
| Sniping the end of a tick (late submission to see others' orders) | sealed batches; nobody sees anyone's intents of tick N before commit; uniform-price auctions; fair `orderKey` order unknowable in advance |
| Getting a privileged position in a contested intent (unique asset) | `orderKey` from unknown entropy; modules use auctions or pro-rata where fairness matters |
| Latency advantage from being near the server | none: the batch boundary is the seal; ordering does not depend on arrival time |
| Replaying a captured intent | per-actor strictly increasing nonce, intent id uniqueness, `intent_max_age_ticks` |
| Flooding a tick to slow the world | per-character 20 intents/tick (00 §5.5), gateway quotas (19), DU caps for AIs; deterministic load shedding in modules |
| Exploiting a halt (queue orders to be first on resume) | intents during a halt are rejected, not queued; resume notice 60 s; first tick fair-ordered |
| Exploiting reanchor (claim lost time) | world time stops with the halt; durations in ticks; no lost income exists to compensate |
| Datamining IDs to learn creation order of secret entities | rotating public labels for sensitive lists (12); IDs only expose creation tick for entities whose existence is public |
| Diffing client deltas to infer hidden state | 19 sends only owner-visible data; events carry visibility; timing of deltas is per tick for everyone |
| Bugs in a phase that print money | P13 invariants abort the tick; safe mode isolates; compensating postings afterwards; replay finds beneficiaries |
| Inconsistent results between machines (exploitable desync) | `dmath`, canonical encoding, shadow verification, CI replay before cutover |

### §3.12 Entropy, commit-reveal and verifiable rolls

**Rule 3.12.1 (epochs).** Entropy is managed in epochs of `PARAM.entropy_epoch_ticks = 720` (one game day). Before epoch `e` starts, COORD obtains a fresh 256-bit secret `S_e` from the KMS-backed generator and publishes `C_e = SHA-256("tycoon-entropy" ‖ e ‖ S_e)` in the batch of the last tick of epoch `e−2` (so the commitment is public at least one full epoch in advance) and in a `sys.entropy_committed` PUBLIC event.

**Rule 3.12.2 (tick entropy).** `entropy(N) = HMAC-SHA-256(S_e, "tick" ‖ N)` for tick `N` in epoch `e`; this is 02's per-tick secret `e(N)`, and the value fed to RNG streams is 02 §3.11.2's `TickEntropy(N)`, which also mixes `intentsRoot(N)` and `worldHash(N−1)` (02 owns the entropy guarantees; ruling in 24). 02's RNG streams are seeded as `seed(stream, entity, N) = SHA-256(worldSeed ‖ entropy(N) ‖ streamId ‖ entityId)` for world-internal draws, and **player-party rolls** (breach, detection, any roll a player can dispute) use `rollU = u53(SHA-256(entropy(N) ‖ rollDomain ‖ sortedSubjectIds ‖ rollIndex)) / 2^53`, which does not involve the secret world seed, so players can verify it.

**Rule 3.12.3 (reveal).** `S_e` is revealed `PARAM.entropy_reveal_lag_ticks = 1000` ticks after epoch `e` ends (vision/02-multiplayer §3.3: "revealed at N+1000"), by `sys.entropy_revealed { epoch, secret }` (PUBLIC). Anyone can check `C_e`. Until reveal, nobody outside the world hosts can compute any tick's entropy, so no one can predict auction order keys or rolls.

**Rule 3.12.4 (verify a roll).** Each player-party roll event carries `{tick, rollDomain, subjectIds, rollIndex, threshold, outcome}` in the party's private event (thresholds as the owning module exposes them; where a module shows only bands, the band). After reveal, `GET /api/v1/verify/roll?eventId=…` recomputes `rollU` from the revealed secret and returns `rollU`, the threshold and whether `rollU < threshold` matches the recorded outcome. The same function is in `packages/sdk`, so players can check independently.

**Rule 3.12.5 (public integrity report).** Every game day the jobs service publishes a signed report (V3 Part 8): money minted and destroyed by reason class, M0/M2 per bloc, systemic indicators, invariant check counts and failures, entropy commitments and reveals of the day, audit-log chain head, exploit-fix history entries released by 21. Shown in the Exchange diegetic "Stabilizer and Exchange report" screen (17).
