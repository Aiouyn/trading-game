## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

### §3.6 The contract engine

**§3.6.1 Principle.** A contract is a typed bundle of clauses the engine can execute (old 02 §8.2). No free-text legalese has legal force; free text is allowed only as non-binding notes. What the engine can verify, it enforces; what it cannot becomes a court claim (03 §15 split, owned now by 13; the table in §3.6.6 is the binding version for 15's engine side).

**§3.6.2 Parties.** 2–8 parties. A party is an entity (chr, cmp, fnd, ali, or an npc through 16's decision model); the signer must be the character controlling it or an alliance role holder with `APPROVE_DEALS`. Guests cannot be parties (14 §3.1.1). Each party sees the counterparty card (§3.6.7) before signing.

**§3.6.3 Lifecycle.**
```
DRAFT --offer--> OFFERED --sign(each)--> PARTIALLY_SIGNED --last sign--> [fund escrow next tick]
   ACTIVE <--funded-- | FAILED_TO_FUND (holds released)
OFFERED --expiry--> EXPIRED_UNSIGNED       (default expiry 720 ticks, max 7 real days)
ACTIVE --all obligations met--> COMPLETED
ACTIVE --engine-verified breach--> BREACHED  (penalties and collateral execute; may continue if clauses say so)
ACTIVE --termination clause / mutual / court order--> TERMINATED
any   --linked parties found / illegal content / court void--> VOIDED (unwound to the extent possible)
ACTIVE|BREACHED --claim filed--> DISPUTED (engine parts keep executing unless a 13 order pauses them)
```
Amending an ACTIVE contract needs a new signature from every party and creates a new version; the old version is kept in history.

**§3.6.4 Escrow.** Escrow is held by the Clearing House's escrow sub-ledger (07 provides `escrow.hold(entityId, bundle, contractId) → holdId`, `escrow.release(holdId, toEntityId)`, `escrow.returnToOwner(holdId)`). At the last signature, every bundle a party must deliver at activation (TRANSFER `ON_ACTIVATION`, LEASE deposit, OPTION writer collateral, LOAN principal, BOUNTY amount, PENALTY amount when engine-triggered) is held on the next tick. If any hold fails, the contract is `FAILED_TO_FUND` and all holds return. Escrowed assets count in the owner's net worth but cannot be used elsewhere.

**§3.6.5 Execution.** In P12 each tick the engine evaluates due clause events in order of `(contractId, clauseIndex)`; payments due "per period" post at the day close of the period end. A payment that the payer's cash cannot cover is retried at the next day close for `PARAM.payment_grace_game_days = 3`; then it is a default (engine-verified breach).

**§3.6.6 Clause rules** (engine side; 13 owns the court side and the arbitration process):

| Clause | Validation at drafting | Engine execution | Breach and outcome |
|---|---|---|---|
| TRANSFER | assets owned and unencumbered by the `from` party | atomic swap at the tick (both sides held, both settle or neither) | cannot breach (escrow) |
| LOAN | rate ≥ 0; term ≤ `PARAM.contract_max_term_game_days = 2,912` (8 game years); collateral owned | disbursement from escrow; schedule postings `CTR_LOAN_INTEREST`, `CTR_LOAN_PRINCIPAL`; covenants tested at each day close from 03 statements | missed payment after grace or covenant breach: collateral seized to lender; shortfall becomes a judgment debt (13 garnishment) |
| LEASE | lessor owns the property/business; lessee eligible to operate it (licenses, city access) | rent each period; operating rights move to lessee for the term (10/09) | missed rent after grace: lease ends, deposit to lessor |
| REVENUE_SHARE | payer controls the business; share 1–90% | at each day close, `sharePct × that day's operating profit (if > 0)` paid | cannot breach while the business exists; a sale without assignment is a court claim |
| EQUITY_STAKE | creates or references a holding cmp (09) | pro-rata dividends and votes; this is how syndicates work (§3.7.6) | — |
| OPTION | underlying deliverable; strike, premium > 0; expiry ≤ max term | premium paid on activation; `soc.contract.exercise` by holder before expiry settles from writer's collateral | auto-settles; unexercised expires |
| SERVICE_LEVEL | provider has the matching service business (09) | fee each period; for SECURITY, the engine watches 12's events for a successful op against a covered unit | covered breach: refund `refundPct × fees paid in the period`; arbitration if provider claims client neglect (unit coverage < 0.5) |
| NON_COMPETE | term ≤ 2 game years; scope non-empty | the engine refuses the restricted party's matching intents (`biz.open` in scope) at P1 | cannot breach; intents refused with reason |
| NDA | subjects are dataset/intel/model ids | none | court via provenance (13) |
| BOUNTY | offense class is a crime; no "hire to commit" wording; target exists | amount held; on a conviction of the target in the class before expiry, paid pro rata to evidence submitters (13 decides) | expires: returns to sponsor |

**§3.6.7 The counterparty card** (shown before signing, built from public data): handle, rank badge, account age, chapters played, Reputation and its last 10 public lines, contracts completed vs defaulted (counts, lifetime), convictions (public record), open public cases as defendant, alliance tag. Never shown: NW beyond the public board bucket, holdings, or anti-cheat link scores.

**§3.6.8 Fees and taxes.**
- Registration fee: `PARAM.contract_registration_fee = 0.5%` of `notionalReal`, min $100 real, max $5,000,000 real, paid by the offering party at activation (`CTR_REGISTRATION_FEE`, SINK). Waived for contracts registered between two attendees of a LIVE hosted event (14 §3.12.2).
- P2P transfer tax: `PARAM.p2p_tax = 2%` on every one-directional value transfer between different beneficial owners: the price side of TRANSFERs, gifts, lease rent, revenue-share payouts, loan interest, option premiums, license fees, service fees, supply payments, penalties, bounties (`CTR_P2P_TAX`, TRANSFER to the tax authority per E-9, paid by the payer). Exempt: loan principal and its repayment, escrow returns, collateral seizure (taxed as the debt it settles), transfers between entities of the same beneficial owner (03 consolidation).
- `notionalReal` = the larger of the total value delivered by either side over the life of the contract (estimated at drafting from clause amounts; for REVENUE_SHARE, `sharePct × trailing game-year profit × term`).

**§3.6.9 Termination and party loss.** A party whose account is deleted (14 §3.1.7) or whose character becomes ESTATE: ACTIVE contracts follow their TERMINATION clause if present; otherwise they terminate with escrow returned and pending payments settled pro rata. LOAN obligations survive into the estate and are paid in 07's liquidation order.

**§3.6.10 Forum.** Each contract elects COURT (13's civil court of the bloc of the first party's home city) or ARBITRATION (13 arbitration: an NPC panel, or a player arbiter licensed by 13 and selected by the parties; arbiters' reputation is a public record). Arbitration is faster (13 sets 2–6 real hours) and its award is engine-enforced from escrow where possible.

**§3.6.11 Mandate rules.** A mandate is valid only if `0 < maxLeverage ≤` the principal's own license cap, `0 < maxPositionPctNav ≤ 1`, `0 < maxDrawdownPct ≤ 0.9`. Every intent submitted by the operator for the principal is validated at P1 against: intent kind in `allowedIntentKinds`, asset class allowed, post-trade leverage and position limits computed on the scope, spend cap, legal-risk tag (13 marks intents such as trading during a blackout as risky), and the principal's own licenses and holds. When the scope's drawdown from its high-water mark exceeds `maxDrawdownPct`, the mandate becomes `SUSPENDED_BREAKER` (operator may only reduce risk) until the principal re-enables it. An operator that breaks the law under a mandate is the principal's legal problem as well (13: both may be charged; old 02 §4.1 rule 5). Tightening limits takes effect after `noticeTicksForChange`; loosening is immediate.

**§3.6.12 Anti-funneling** (old 02 §8.2, §10.1):
- Flags at drafting: price > 10% from fair value (05/06/09/10 marks), loan rate below the bloc policy rate − 2 percentage points, revenue share or gift to an account younger than 7 real days, any party pair with `LinkPair.suspect`.
- Flagged contracts are allowed but count fully against the payer's P2P cap and go to the integrity queue.
- Contracts between `linkedAccounts` are VOIDED (unwound, fees not refunded, 13 notified as a possible S4 scheme).
- P2P caps per payer per real day (all P2P value out, real): account age < 7 real days: `$10,000`; 7–20 days: `$1,000,000`; ≥ 21 days: `10% of the payer's rank-basis NW` (minimum $1,000,000). Loan principal counts at 50%. Inflows are uncapped.

**§3.6.13 Templates.** One-tap templates (22 lists text keys): Sell a business, Sell a property, Loan with collateral, Lease my office, Revenue share, Join a syndicate, Hire a manager (MANDATE), Security retainer (SERVICE_LEVEL), Model license, Supply agreement, Subcontract an order, Option to buy my stake, Bounty for evidence. Templates fill defaults; the advanced builder exposes every field.

### §3.5 Partitioning: homes, routing, holds, moves

**Rule 3.5.1 (home rules).** Every entity has exactly one home partition, computed by a pure function of the entity and the `PartitionMap`:

| Entity kind (00 §5.3) | Home |
|---|---|
| `chr` | `PLAYER` partition whose hash range contains `u32(SHA-256(chrId))` |
| `cmp`, `fnd`, `bnk`, `ins`, `spv`, `ali` controlled by a character | the controlling character's PLAYER partition (control = owner chain of 03; for an alliance treasury, the founder at creation; does not move when control changes except at the next snapshot boundary, §3.5.5) |
| `cmp` listed or controlled by an NPC | CITY partition of its HQ city |
| `biz`, `prop` | CITY partition of the city they are located in (wherever their owner is homed) |
| orders and the book of an asset | MARKET partition of the asset's group (§3.13.2) |
| `gov`, `cbk`, `reg`, `crt`, `exc`, `rat`, NPC `bnk`/`ins`/`fnd`, `frm` | FINANCE partition of their bloc |
| `hh` | CITY partition of its city |
| `ccp` | CCP |
| `npc` named actors and dynasties | ACTOR partition by `u32(hash(npcId)) mod nActorPartitions` |
| `row`, `sys` accounts, macro state, calendar | COORD |
| Isla Serena (no bloc) | its CITY partition; its institutions on FINANCE-FDL |
| hidden session (12) | the **victim** model's home (vision/02-multiplayer §4.2) |
| contract (15) between parties on different partitions | the home of the party with the lowest entity id (the "anchor") |

Every rule is deterministic, so any partition can compute where to send a message without asking anyone.

**Rule 3.5.2 (routing).** Partitions address messages to entities (`toEntity`), never to partitions. The bus layer resolves `toEntity → partitionId` from the current `PartitionMap`. A partition receiving a message for an entity it no longer homes (only possible across a map change) rejects the whole tick as a platform fault; map changes happen only at snapshot boundaries, so this signals a bug.

**Rule 3.5.3 (holds: money crosses partitions only by hold → settle).**
1. At P1, the actor's home partition validates the intent and places a **hold** on the resources it needs (cash for a buy at its limit price plus maximum fees, asset quantity for a sell, collateral for a margin product, escrow for a contract). A hold is a ledger-side reservation in the owning partition: `available = balance − Σ holds`. Postings never touch held amounts except the settlement of that hold.
2. The intent travels as a `PhaseMessage` with the hold id to the executing partition (MARKET for orders, CITY for property, FINANCE for an NPC bank product, the anchor for a contract).
3. The executing partition decides (fill, partial fill, award, reject) in its phase and returns a result message to the owning partition.
4. At P13 the owning partition posts the settlement against the hold and releases the remainder. A hold that receives no result by P13 of its tick stays open into the next tick only for resting orders (for which the hold lives as long as the order); for everything else it is released and the intent result is `REJECTED` with `PLATFORM_NO_RESULT` (a bug signal that the Truth Machine counts).
5. **Inter-partition clearing.** When the two legs of a posting belong to accounts on different partitions, each partition posts its own leg against its **inter-partition clearing account** `sys:ipc:<thisPartition>:<otherPartition>`. Invariant (20): for every pair `(A,B)` and every currency, `balance(ipc:A:B) + balance(ipc:B:A) = 0` after every P13. The ledger module (03) treats `ipc` accounts as `sys` TRANSFER accounts; they never appear in any player's net worth.

**Rule 3.5.4 (atomic multi-party settlement).** A P2P swap, an escrowed contract, an M&A closing or a syndicated loan touches several partitions. Procedure:
1. P1: each party's home places its hold and sends `HoldPlaced` to the anchor.
2. Anchor, in its owning phase (P12 for contracts, P6 for trades, P8 for finance), checks that every hold arrived and is sufficient. If yes it sends `Settle(holdId, legs)` to all; if not, `Abort(holdId)` to all.
3. P13: each partition posts or releases. Because phases are barriers and every message of a phase arrives before the next phase starts, there is no "in doubt" state: either all legs post in the same tick or none do. A partition crash aborts the whole tick for every partition (§3.7.4), so partial settlement is impossible.

**Rule 3.5.5 (rebalancing and moves).** The world moves an entity group (a character with everything homed with it, or a city, or an asset group) between partitions only at a **snapshot boundary** (end of day, `t = 719` commit):
1. COORD publishes the new `PartitionMap` with `effectiveTick = boundaryTick + 1` in the batch of the boundary tick as `SystemInput sys.partition_map`.
2. After P14 of the boundary tick, the source partition serializes the moving entities (`MOVE` snapshot), the target loads them, and both report entity hashes; COORD checks that the logical hashes match.
3. The next tick runs under the new map. A move that fails the hash check is cancelled (the old map stays) and an alert fires.
4. Moves never change any outcome: rule 3.6.6's logical state hash is identical with and without the move.

**Rule 3.5.6 (map change policy).** `PartitionMap` changes only by `sys.partition_map` at a snapshot boundary. Triggers (evaluated by COORD on platform metrics, never inside the engine): a PLAYER partition above `PARAM.partition_target_agents = 25000` agents or above 80% of its measured phase budget for `PARAM.rebalance_trigger_days = 3` consecutive game days is split (its hash range halved); two adjacent partitions below 30% each are merged; a host above `PARAM.host_cpu_target = 0.7` average gets partitions moved off. At most `PARAM.max_moves_per_boundary = 4` partition moves per boundary.

**Rule 3.5.7 (hosts versus partitions).** A host runs any number of partitions as worker threads. Which host runs a partition never affects results; host placement can change at any snapshot boundary with a `MOVE` snapshot and is not part of `PartitionMap.homeRules` (only `hostId`, which is excluded from all hashes).
