## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. Process layout (19 Rule 3.2.1): main thread = coordinator (T19B-08 onwards) + worker pool; one worker per partition; the host never runs web or gateway code (Rule 3.2.2). A host may run any number of partitions (Rule 3.5.7); `hostId` never enters any hash.
2. Worker: on `load`, `checkPin` against the coordinator's active configuration (sent in ctx); mismatch -> `error RUNTIME_MISMATCH` and the worker refuses all further messages (19 Rule 3.6.1). Then `engine.load(snapshot, ctx)`.
3. Fencing (19 Rule 3.2.3, §8 edge 8): the worker keeps the highest fencing token seen; a message with a lower token is answered `error FENCED` and ignored; an equal or higher token is processed (higher replaces). The coordinator's token is its lease epoch (T19B-11).
4. Phase messages: `phase` calls `engine.runPhase` (or returns an empty output when `!runsPhase(phase)`) and replies `phaseDone` with `outboxCount`, `outboxDigest` and timing (19 Rule 3.3.1 step 3). Before running, the worker checks every inbox message's `toEntity` is homed on it under the current map; otherwise `error WRONG_HOME` (19 Rule 3.5.2: platform fault, the whole tick is rejected).
5. Engine faults never kill the worker: thrown errors inside `runPhase` are already converted by T19B-02 into failures; anything else (out of memory, crash) ends the worker and `onFailure('EXIT')` fires.
6. Heartbeats: the pool pings every worker every `coord_heartbeat_ms`; `missedLimit` consecutive missing pongs -> failure HEARTBEAT (19 Rule 3.7.4 item 1). Hard timeout: the tick driver reports `HARD_TIMEOUT` when a phase has not returned after `phase_hard_timeout_ms` (T19B-08).
7. Config: strict zod schema (unknown keys rejected): only the listed secret references. INV-STR-004 (20 §3.1.8): the static check scans `apps/world/**` source, `infra/world/**` manifests and `apps/world` env schema for any variable name or secret reference matching `FORBIDDEN_WORLD_SECRET_PATTERNS` (`/COMMERCE/i`, `/ENTITLEMENT/i`, `/STORE_(DB|URL|KEY)/i`, `/AD_?NETWORK/i`, `/ADMOB/i`, `/APPLOVIN/i`, `/IRONSOURCE/i`, `/UNITY_ADS/i`, `/STRIPE/i`, `/PAYMENT/i`, `/IAP_/i`) and for the database role `commerce`; any hit fails with file and line.

# SPEC EXCERPTS (verbatim; binding game rules)

**[19 §1 Purpose]** (context)

## §1 Purpose

1. **One authoritative world.** The server is the only truth (L1, L14). Clients send intents and render deltas. No client ever runs the authoritative simulation, holds the world seed, or computes its own fills, balances or roll outcomes.
2. **One logical world on many machines.** The world is a single deterministic fold over sealed intents. It is executed by many single-writer **partitions** under a bulk-synchronous tick (one barrier per pipeline phase of 00 §5.2). The result of a tick never depends on how many partitions exist or which machine runs them. That is what makes partitioning invisible (L1) and replay exact.
3. **Fairness by construction.** Every actor (human UI, expert API, player AI, delegated manager, NPC) enters the world through the same intent pipeline with the same validation and the same tick (00 §5.5). Ordering inside a tick never rewards network speed.
4. **Provable honesty.** Every input is stored; every output is reproducible; every random outcome a player is party to is verifiable after the fact (§3.12). The Truth Machine (20) runs on the same engine packages.
5. **Privacy by serialization.** Data the client must not know never leaves the partition that owns it (L11). The gateway only relays deltas already filtered for their recipient.
6. **A builder's map.** §12 orders every module of 00 §1 into a build sequence with gates, so the game can be built bottom-up without a question.

**Rule 3.2.2 (no tick logic in web).** Next.js never runs world logic and never holds a socket to clients for game traffic (serverless-style request lifetimes cannot hold a 5 s loop). It talks to the world only through (a) the bus (submitting `SystemInput`s on behalf of authenticated platform flows, e.g. a verified ad receipt) and (b) read models.

**Rule 3.2.3 (coordinator).** Exactly one active coordinator (`COORD` partition plus the tick driver) exists. A warm standby follows the bus and the tick records; it takes over when the active one misses `PARAM.coord_failover_missed_heartbeats = 3` heartbeats of `PARAM.coord_heartbeat_ms = 500` ms, using a lease in PostgreSQL (`coord_lease` table, §11) with fencing token = lease epoch. Only the holder of the current fencing token can seal ticks; partitions reject seal messages carrying an older token.

### §3.14 Personal data and privacy mechanics

**Rule 3.14.1 (no personal data in the engine).** The engine knows characters by `chrId` and handle only. Email, IP, device ids, payment data and real names never enter batches, events, snapshots or engine state. Country and age band enter only as `sys.*` inputs carrying the game-relevant value (`country` code for boards and country rules, `ageBand` for chat rules).

**Rule 3.14.2 (separation).** Personal data lives in PostgreSQL schema `pii` with its own database role, readable only by `web` (auth flows), `jobs` (emails, exports) and `admin` (support, audited). Columns holding email are encrypted at the application layer with a KMS data key; lookup uses a keyed hash (`email_hmac`). IP addresses and user agents are stored only as keyed hashes rotated every `PARAM.ip_hash_salt_rotation_days = 30`.

**Rule 3.14.3 (export).** `POST /api/v1/me/export` enqueues a job that assembles account data, character public and private history (postings, intents, events visible to the character), chat messages authored, purchases, and delivers a download link valid 7 days, within `PARAM.export_sla_days = 30` (21 legal).

**Rule 3.14.4 (deletion).** `POST /api/v1/me/delete` sets `DELETION_PENDING` for `PARAM.deletion_grace_days = 14` (cancellable). Then: personal data in `pii` is deleted, the account becomes `ANONYMIZED`, the character is renamed to a generated label, removed from boards, and its unique assets go to the estate process (14, vision/02-multiplayer §3.7) through `sys.account_deleted`. The world's history keeps the pseudonymous `chrId` and the generated label, because removing world history would break replay and other players' records; no personal data remains attached to it. Chat messages authored are deleted or replaced by "[removed]".
