## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `forTick(N)`: `buffer.ensureCommitted(N)` creates `S_e` for every epoch up to `epochOf(N) + 2` from the prefetched KMS secrets (prefetch keeps at least 3 ahead; if the prefetch queue is empty the call awaits the KMS before sealing: the seal waits, it never uses a weaker source). A commitment for epoch `e` is emitted as input `sys.entropy_commit {epoch: e, commitment}` exactly in the batch of the last tick of epoch `e−2` (tick `(e−1)·epochTicks − 1`), so it is public at least one full epoch (720 ticks) before `e` starts (19 Rule 3.12.1; `entropy_commit_lead_ticks` = `entropy_epoch_ticks`, 23 §5.6).
2. `eN = buffer.eOf(N)` = HMAC-SHA-256(S_e, 'tick' ‖ N) (19 Rule 3.12.2). Missing secret (only after a corrupt restore) -> `fallback = true`; T19B-07 then uses 02's `fallbackEntropy` and flags the header.
3. Reveals (19 Rule 3.12.3): for each epoch `e` with `N >= (e+1)·epochTicks + revealLagTicks − 1` and not confirmed, add `sys.entropy_reveal {epoch, secret}`. If unwrapping fails (KMS outage), the reveal is omitted for this tick and retried at every next tick (edge 28: late, never skipped); `pendingReveals` exposes the backlog and a metric `entropy_reveal_backlog` is set. Ticks never wait for reveals.
4. Commitments for future epochs are always two ahead, so a KMS outage shorter than one epoch never stops sealing (edge 28). A longer outage stops sealing at the first tick whose epoch has no secret: the world shows CATCHING_UP (T19B-09) and pages.
5. Persistence: `confirmSealed` writes commits (with the wrapped secret in `entropy_secret_sealed`) and reveals (secret into `entropy_epoch.secret`, `revealed_tick`) after the batch is durable (T19B-07), in one transaction.
6. Standby: the active coordinator sends `replicationState()` to the standby with every heartbeat (T19B-11); secrets are only ever stored wrapped outside the world host's memory (19 Rule 3.9.6, no foresight 19#38).
7. Never log a secret or eN (logger redacts `secret`); unit test greps captured logs.

## §1 Purpose

1. **One authoritative world.** The server is the only truth (L1, L14). Clients send intents and render deltas. No client ever runs the authoritative simulation, holds the world seed, or computes its own fills, balances or roll outcomes.
2. **One logical world on many machines.** The world is a single deterministic fold over sealed intents. It is executed by many single-writer **partitions** under a bulk-synchronous tick (one barrier per pipeline phase of 00 §5.2). The result of a tick never depends on how many partitions exist or which machine runs them. That is what makes partitioning invisible (L1) and replay exact.
3. **Fairness by construction.** Every actor (human UI, expert API, player AI, delegated manager, NPC) enters the world through the same intent pipeline with the same validation and the same tick (00 §5.5). Ordering inside a tick never rewards network speed.
4. **Provable honesty.** Every input is stored; every output is reproducible; every random outcome a player is party to is verifiable after the fact (§3.12). The Truth Machine (20) runs on the same engine packages.
5. **Privacy by serialization.** Data the client must not know never leaves the partition that owns it (L11). The gateway only relays deltas already filtered for their recipient.
6. **A builder's map.** §12 orders every module of 00 §1 into a build sequence with gates, so the game can be built bottom-up without a question.

### §3.12 Entropy, commit-reveal and verifiable rolls

**Rule 3.12.1 (epochs).** Entropy is managed in epochs of `PARAM.entropy_epoch_ticks = 720` (one game day). Before epoch `e` starts, COORD obtains a fresh 256-bit secret `S_e` from the KMS-backed generator and publishes `C_e = SHA-256("tycoon-entropy" ‖ e ‖ S_e)` in the batch of the last tick of epoch `e−2` (so the commitment is public at least one full epoch in advance) and in a `sys.entropy_committed` PUBLIC event.

**Rule 3.12.2 (tick entropy).** `entropy(N) = HMAC-SHA-256(S_e, "tick" ‖ N)` for tick `N` in epoch `e`; this is 02's per-tick secret `e(N)`, and the value fed to RNG streams is 02 §3.11.2's `TickEntropy(N)`, which also mixes `intentsRoot(N)` and `worldHash(N−1)` (02 owns the entropy guarantees; ruling in 24). 02's RNG streams are seeded as `seed(stream, entity, N) = SHA-256(worldSeed ‖ entropy(N) ‖ streamId ‖ entityId)` for world-internal draws, and **player-party rolls** (breach, detection, any roll a player can dispute) use `rollU = u53(SHA-256(entropy(N) ‖ rollDomain ‖ sortedSubjectIds ‖ rollIndex)) / 2^53`, which does not involve the secret world seed, so players can verify it.

**Rule 3.12.3 (reveal).** `S_e` is revealed `PARAM.entropy_reveal_lag_ticks = 1000` ticks after epoch `e` ends (vision/02-multiplayer §3.3: "revealed at N+1000"), by `sys.entropy_revealed { epoch, secret }` (PUBLIC). Anyone can check `C_e`. Until reveal, nobody outside the world hosts can compute any tick's entropy, so no one can predict auction order keys or rolls.

**Rule 3.12.4 (verify a roll).** Each player-party roll event carries `{tick, rollDomain, subjectIds, rollIndex, threshold, outcome}` in the party's private event (thresholds as the owning module exposes them; where a module shows only bands, the band). After reveal, `GET /api/v1/verify/roll?eventId=…` recomputes `rollU` from the revealed secret and returns `rollU`, the threshold and whether `rollU < threshold` matches the recorded outcome. The same function is in `packages/sdk`, so players can check independently.

**Rule 3.12.5 (public integrity report).** Every game day the jobs service publishes a signed report (V3 Part 8): money minted and destroyed by reason class, M0/M2 per bloc, systemic indicators, invariant check counts and failures, entropy commitments and reveals of the day, audit-log chain head, exploit-fix history entries released by 21. Shown in the Exchange diegetic "Stabilizer and Exchange report" screen (17).

**[02 §3.11]** (from spec file 02-TIME-ENGINE-CORE.md)

### §3.11 Entropy: commit-reveal and epochs

#### §3.11.1 Commit-reveal per tick

- The coordinator keeps a buffer of secrets `e(N)` for future ticks, generated from its cryptographic random source (outside the engine; stored in the secret store, 19).
- **Commit:** `C(N) = SHA-256('TYC/commit' || worldId || N || e(N))` is published in the header of tick `N - PARAM.entropy_commit_lead_ticks` (DEFAULT 720 = 1 game day ahead). Because it is published before tick N's intake opens, the operator is bound to `e(N)` before seeing any intent of tick N.
- **Reveal:** `e(N)` is published in the header of tick `N + PARAM.entropy_reveal_lag_ticks` (DEFAULT 1,000, kept from 02-multiplayer §3.3). Anyone can then check `SHA-256(...e(N)) == C(N)`.
- If the coordinator ever fails to have a committed `e(N)` (bug, failover without the buffer), tick N uses `e(N) = SHA-256('TYC/fallback' || prevTickHash)`, the header flags `entropyFallback = true`, and a public integrity incident is logged (21). The standby coordinator replicates the entropy buffer synchronously, so this should never happen in normal failover.

- Implementation (ruling in 24): 19 §3.12 realises these per-tick secrets with one epoch secret `S_e` per game day, `e(N) = HMAC-SHA-256(S_e, "tick" ‖ N)`; the epoch commitment `C_e` (published at the end of epoch `e−2`, so at least 720 ticks before any tick of epoch `e`) replaces the per-tick `C(N)`, and `S_e` is revealed 1,000 ticks after epoch `e` ends, which is never earlier than `N + 1,000` for any tick `N` of the epoch. The guarantees of this section (bound before intake, reveal no earlier than `N + entropy_reveal_lag_ticks`) are unchanged.

#### §3.11.2 Tick entropy

```
TickEntropy(N).value = SHA-256('TYC/tick-entropy' || worldId || N || e(N) || intentsRoot(N) || worldHash(N-1))
```

Neither the operator (committed to `e(N)` in advance) nor any player (does not know `e(N)`) can steer it. Including `intentsRoot` means even a leaked `e(N)` does not let the operator pre-compute outcomes before intents arrive.

#### §3.11.3 What is public

Each `TickHeader` is public (served by the read API, 19) except that `entropyReveal` appears only after the lag. Players can download headers and verify (a) commit/reveal pairs, (b) that their own intent was included, using a Merkle inclusion proof from `intentsRoot` (the "Receipt" button, §7). They cannot recompute RNG draws because epoch roots (§3.11.4) are secret during the epoch.

#### §3.11.4 Epoch roots (seed rotation)

- **Epoch = chapter number.** Each epoch k has two roots:
  - `publicRoot(k)`: 32 random bytes, committed (`SHA-256`) in the first header of the epoch, **revealed one full chapter after the epoch ends** (in the first header of epoch k+2). After reveal, anyone holding a full replay of public inputs could verify public-root draws; in practice it is used by the integrity report and by independent auditors with replay access (21).
  - `secretRoot`: one per world, never revealed, used by all `S` streams; S streams are re-seeded at each epoch with `SHA-256('TYC/secret-epoch' || secretRoot || k)` as their epoch root.
- At the first tick of epoch k, every stream is re-seeded (§3.10.2) with its epoch root. Streams not yet created are seeded on first use with the current epoch root.
- Rationale: rotation bounds the damage of a leaked seed to one chapter; S streams keep persistent secrets (hidden personality traits, secret archives, hidden-session clue timing) hidden forever even after public roots are revealed.
- The **content seed** used by 22's generators at world genesis (cities, NPC actor rosters, company fundamentals) is part of `secretRoot` derivation and never revealed.
