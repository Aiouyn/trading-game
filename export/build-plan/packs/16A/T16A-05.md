## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## §1 Purpose

1. **A world that lives without the player** (W01, W03): households earn and spend, firms hire and invest, banks lend, politicians legislate, families feud, and news reports it, whether or not any player is online. Players are added to this foundation, never its only cause.

6. **Fairness**: NPCs see only what is public plus what is genuinely theirs; they never know private player plans and never punish success as such (C09, F05).

### §3.2 The aggregate economy (layer 1)

**§3.2.1 Inputs** at day close: from 04 per bloc: real growth `g`, inflation `π`, unemployment `u`, policy rate `i`, neutral rate `i_n`, consumer sentiment `S` (0–100), credit conditions `c` (−1 tight … +1 loose), nominal GDP `Y_b` per game year; from 10 per city: population `P_c`, wage index `ω_c`, housing stock; from 03: the Stabilizer demand lever `λ_d ∈ [0.9, 1.1]` (01 §8.2 lever 1).

**§3.2.2 Firm sector (per bloc).** Daily nominal output `Q_b = Y_b / 364`. Wage bill `W_b = PARAM.labor_share = 0.55 × Q_b × automationFactor_b`, where `automationFactor = 1 − 0.01 × (AUTOMATION level)` (§3.10), floor 0.85. Profit `Π_b = Q_b − W_b − intermediate_b`, `intermediate_b = 0.30 × Q_b`. Investment demand `I_b = Q_b × 0.18 × (1 + 0.5·(S−50)/50) × (1 − 5·(i − i_n))` (rate term 5, E-28/E-29; 04's closure reads final demand C + I only, never the intermediate), clamped to [0.08, 0.28] of `Q_b`. B2B demand by category = `intermediate_b × b2bShare_k` (22 table; e.g. LOGISTICS 0.16, CONSTRUCTION 0.12, IT_SERVICES 0.10, BUSINESS_SERVICES 0.12, ENERGY 0.12, DATA 0.04, COMPUTE 0.04, SECURITY 0.03, MAINTENANCE 0.08, COLD_CHAIN 0.03, MARKETING 0.08, LEGAL 0.08), plus `I_b × 0.6` to CONSTRUCTION. R&D by domain `= Q_b × PARAM.rnd_share = 0.025 × domainShare_b,d` (22 per-bloc table, e.g. Pacific League leans COMPUTE and MATERIALS). Dividends `= 0.5 × max(0, Π_b)`.

**§3.2.3 Household sector (per city).** City share of its bloc `φ_c = P_c ω_c / Σ_{c∈b} P_c ω_c`.
```
employed_c   = 0.5·P_c · (1 − u_b) · localEmploymentAdj_c          // adj from consequence impulses, default 1
wageIncome_c = φ_c · W_b
transfers_c  = φ_c · fiscalTransfers_b / 364                          // 04 fiscal
divIncome_c  = φ_c · 0.3 · dividends_b                                // 30% of NPC dividends reach households
taxes_c      = taxRateHH_b · (wageIncome_c + divIncome_c)            // 03/04 statutory rate (policy lever)
Yd_c         = wageIncome_c + transfers_c + divIncome_c − taxes_c
mpc_c        = clamp(0.85 + 0.05·(S_c − 50)/50 − 2.5·(i_b − i_n,b) + 0.03·c_b, 0.70, 0.95)
C_c          = λ_d · ( mpc_c · Yd_c + 0.04/364 · depositsHeld_c )   // wealth effect 4% per game year
savings_c    = Yd_c − C_c   (may be negative; then deposits fall)
```
Consumption by category: `C_c,k = C_c × share_k(incomeLevel_c, era)`, with launch shares (22 holds the full table) FOOD_BEV 0.14, RETAIL 0.12, HOUSING 0.22, TRANSPORT 0.09, ENTERTAINMENT 0.06, HEALTH 0.08, PERSONAL_SERVICES 0.06, TECH 0.05, FINANCIAL 0.04, EDUCATION 0.03, LUXURY 0.03, UTILITIES 0.08. Higher-income cities shift 0.02 from FOOD_BEV to LUXURY per +25% wage index; eras shift shares (§3.10).

**§3.2.4 Outputs** (each owner applies its own rule):
- 09: `demandPool(cityId, category, C_c,k)` for consumer sectors and `b2bPool(blocId, category, …)`; 09's logit market share splits each pool between NPC firms and player businesses.
- 10: `housingDemandIndex_c = (households_c / dwellings_c) × (1 + 0.5·(employed_c/employed_c,prev − 1)·30)` smoothed with a 30-game-day EMA (households = P_c / 2.3).
- 07: deposit flow `savings_c` into the city's NPC banks pro rata to their deposit share; credit demand `= mortgageDemand + consumerDemand`, `mortgageDemand_c = housingTurnover_c × avgPrice_c × LTV_c` (10/07), `consumerDemand_c = 0.02 × C_c × (1 + c_b)`.
- 04: realized consumption and investment are reported back as the demand side of next day's growth update (04 owns the closure).

**§3.2.5 Money closure.** Households and firms are real balance-sheet entities (03). Wages, NPC-to-NPC purchases and dividends are TRANSFERs inside the NPC economy (`HH_WAGES`, `HH_CONSUMPTION_NPC`, `FRM_DIVIDENDS`). Spending that lands at a player business is booked `HH_CONSUMPTION_PLAYER` / `FRM_B2B_PLAYER`, which 03's boundary rule classes as FAUCET for the player economy (old 01 §8.1 "NPC customers pay players"). Player payments to NPC firms are SINKs on the same boundary. Because the NPC economy is sized by 04's GDP (about 50× player net worth at launch, 01 §14.1), NPC sector income each day is posted from `row` by 04's nominal-GDP closure (`ROW_NPC_INCOME`), and any NPC cash leaving to players is replaced by that closure; 03 audits that `hh` and `frm` balances never go negative (if a day's spending would, consumption is cut to available cash plus credit drawn from 07). The Stabilizer acts only through `λ_d` (and its other levers), never by editing balances.

**§3.2.6 Ordinary activity between crises** (W06): every game day the aggregate step also emits low-key events that 09/10 turn into actor or city events: new NPC contracts, hiring rounds, construction starts, product launches, ownership changes. Their count per bloc per game day `= Poisson(λ)`, `λ = clamp(2 + 100·(g_b + 0.02), 1, 9)`, count clamped to [0, 12] (E-28/E-29); each is routed to a named actor in that bloc (§3.3) as a candidate action, so the motion is real, not decorative.

### §3.5 Money: perimeters and aggregates

#### §3.5.1 Perimeters

Every entity belongs to exactly one perimeter, recomputed in P13 of any tick in which control changes (§3.11.2):

| Perimeter | Members | Role |
|---|---|---|
| **PLAYER** (the "player economy", P) | every `chr`, every `ali`, and every entity whose ultimate controller (§3.11.2) is a `chr` or an `ali` (their companies, funds, banks, insurers, businesses, properties, SPVs) | what the Stabilizer targets and what boards rank |
| **NPC core** | every other non-elastic, non-system entity: central banks, treasuries, regulators, courts, exchanges, the CCP, rating agencies, NPC banks, funds, insurers, NPC companies, named NPC actors, NPC liquidity providers | real balance sheets with conserved money |
| **ELASTIC** | `hh` (one per city), `frm` (one per bloc), `row` (one) | the aggregate economy at the edge of the ledger (§3.5.2) |
| **SYSTEM** | `sys` | issuer of outside money, suspense, burn |

"Core" = PLAYER ∪ NPC core. Money is conserved inside the core except through FAUCET, SINK and CREDIT flows.

#### §3.5.2 Elastic sectors (how the aggregate economy plugs into an exact ledger)

The aggregate economy (Layer 1 of the living world: households, small firms, the rest of the world, V3 Part 7) is modelled by 04 (macro) and by 09/10 (demand pools, rents) with float models. Its spending is a **model output**, not a constrained cash balance. In the ledger:

1. Elastic sectors hold **real claims** booked exactly like any entity: deposits at core banks, bonds, shares (the free float not held by core entities), fund units, properties, loans to and from core banks. This keeps quantity conservation exact (I8) and lets bank runs, defaults and restructurings hit real balance sheets.
2. Their spending money is **virtual**: account `1009 Elastic money`, which may be negative, backed by `sys:2909`. When an elastic sector pays a core entity, the payment is a FAUCET (template `ELASTIC_IN`): outside money is minted at the central bank for the payee. When a core entity pays an elastic sector, it is a SINK (`ELASTIC_OUT`): the money is burned.
3. Consequence: the core economy is closed except at two kinds of edges, the `sys` issuer and the elastic sectors, and both are FAUCET/SINK codes. This resolves the old ambiguity (01 §8.1 called "NPC customers pay players" a faucet, while a full balance-sheet world would call it a transfer): **payments from the aggregate economy are faucets; payments between named balance sheets are transfers.**
4. Loans between core banks and elastic sectors: disbursement is a SINK (`BNK_ELASTIC_LOAN_DISBURSE`), repayment and interest are FAUCETs; they are not CREDIT codes, because the deposit created would sit in the elastic sector. The macro model (04) accounts for household credit growth in its own float state.

#### §3.5.3 Aggregates (per currency, every tick)

```
M0[c]      = cbk_c:2001 + cbk_c:2002 + cbk_c:2003                       (all base money)
M0_sys[c]  = sys:2900[c] = cbk_c:1910                                     (outside money)
M0_cb[c]   = M0[c] - M0_sys[c]                                            (central-bank credit, net of its capital)
M2[c]      = Σ_{e not bank, not cbk, not gov} e:1001[c]  +  Σ_{banks} bnk:2100[c]   (incl. deposits of elastic sectors)
PEM[c]     = Σ_{e in PLAYER} (e:1001 + e:1010 + e:1050 cash + e:1070)[c]  (player-economy money)
PEW        = Σ_{roots r in chr ∪ ali} NWrank_FDL(r)                      (player-economy wealth, §3.10)
N_a        = Σ_players exp(-days_since_last_active / 7)                    (02-multiplayer §1; days = real days, wall clock)
```

Identities checked every tick (I4, §3.16):

```
ΔM0_sys = Σ FAUCET − Σ SINK
ΔM0_cb  = Σ CBK_* CREDIT_CREATE − Σ CBK_* CREDIT_DESTROY + Δ(cbk own-account flows: interest received/paid, FX revaluation of reserves)
ΔM2     = Σ BNK/REPO_BANK/PB CREDIT_CREATE − CREDIT_DESTROY + ΔM0 held by non-banks + bank own-account flows
```

"Bank own-account flows" = net of all postings that debit or credit a bank's 2100 against the bank's own income/expense/equity (interest, fees, opex, dividends paid into deposits). The money report shows this line explicitly.

#### §3.5.4 Effect of each class

| Class | M0_sys | M0_cb | M2 | PEM | Core NW total |
|---|---|---|---|---|---|
| FAUCET | + | 0 | + (if payee non-bank) | + if payee in P | + |
| SINK | − | 0 | − | − if payer in P | − |
| TRANSFER | 0 | 0 | 0, except bank own-account flows | ± if one side in P and the other NPC core | 0 |
| CREDIT_CREATE (bank) | 0 | 0 | + | + if borrower in P | 0 |
| CREDIT_CREATE (cbk) | 0 | + | 0 to + | 0 | 0 |
| CREDIT_DESTROY | mirror | | | | 0 |
| REVALUE | 0 | 0 | 0 | 0 | ± |

#### §3.5.5 Player-perimeter flow accounting

Because a TRANSFER between P and the NPC core (e.g. a dividend from an NPC company to a player, a fee from a player to an NPC bank) also changes PEM, the daily money report (§3.7.7) shows two views: (a) world classes by reason code; (b) **P-crossing flows**: every posting with one side in P and the other outside P, grouped by family (§3.6), as inflows and outflows of P. The Stabilizer's error is computed from wealth (§3.7.2) and needs neither view as an input; both views are for transparency and balancing (20).

#### §3.5.6 Restricted cash

Some faucet cash must not fund certain actions immediately (L12; roadmap conflict C5, decided 2026-10-09):
- `ACCT_REWARDED_AD` and `ACCT_FRESH_START` credit `1001` sub-account `RESTRICTED:<releaseTick>` with `releaseTick = tick + 51,840` (72 real hours of world time, 02 §3.1.3).
- Restricted cash can pay for: businesses, property, licences, market trades in cash products, lifestyle items, taxes, upkeep. It cannot pay for: ops (12), insider-tier information or tips (16), margin or collateral (07), P2P transfers or contract payments to other players (15), alliance dues.
- `ledger.available(E, purpose)` excludes restricted sub-accounts for the forbidden purposes. Spending draws restricted cash first for allowed purposes. At `releaseTick`, a `LED_RECLASS` moves the remainder to unrestricted.
