## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. `commonAcctValidate` (14 §4): `i.onBehalfOf` or `i.mandateId` set → `ACCT_NOT_SELF`; character ANONYMIZED → `ACCT_ANONYMIZED`; account SUSPENDED or BANNED → `ACCT_ACCOUNT_BLOCKED`; Held (`ports.isHeld`) and not `heldAllowed` → `ACCT_HELD`. Rate limits are enforced by intake (G9), not here.
2. `checkHandle`: `HANDLE_RE` fails → `ACCT_HANDLE_INVALID` (covers "ab", "1234", leading digit, bad chars); key in `reservedHandleKeys()` or starts with `guest_` or `former_` → `ACCT_HANDLE_RESERVED`; key used by a live profile, or by a `handleHoldTable` row with `heldUntilTick > tick` → `ACCT_HANDLE_TAKEN`. Moderation filter (21) is a later port: not present → accepted.
3. `acct.handle.change` (common validate; `heldAllowed` false): `ports.handleChangeBlocked` → `ACCT_HANDLE_BLOCKED` (14 §9 #18). `chapterOf(handleChangedTick) == chapterOf(tick)` → `ACCT_HANDLE_ONCE_PER_CHAPTER`. Fee `realToNominal(handle_change_fee_real)`; place a cash hold with `HoldApiExt.placeCashFor(chr, 'FDL', fee, tick+1, intentId, 'ACCT_HANDLE_FEE')` in P1 (fails → `ACCT_INSUFFICIENT_FUNDS`). Apply P12: `burn(chr, fee, 'FDL', 'ACCT_HANDLE_FEE', {holdId})`; old key into `handleHoldTable` with `heldUntilTick = (chapterOf(tick) + 1 + handle_release_hold_chapters) × TICKS_PER_CHAPTER` (held for the rest of this chapter plus 1); `formerHandle` shown until the end of the next chapter. A guest-generated handle may be replaced once free of charge at registration time (first change from a `guest_` handle has fee 0: conservative reading of "generated handle"; open question).
4. `acct.profile.update`: `chosenTitleId` must be earned (14B port, default: only `titleAwardTable` rows); `pinnedReceiptIds.length <= profile_pinned_receipts_max`; `displayCompanyName` checked by 09 later (port not present → refused unless null); `shellId` must be in `shellsEarned` or in `cosmeticsOwned` (cosmetic shells allowed, labeled; never read by any rule, INV-PRG-002). Applied next tick (`ctx.send(chr,'acct.profile.apply',…,'NEXT')`). Allowed while Held for cosmetic fields only (`avatar`, `shellId`, `chosenTitleId`).
5. `acct.publication.set`: merges the partial into `publication` next tick. Public payload rebuilds belong to 14B / 15.
6. `acct.homeCity.change`: `cityAccessible` (§3.2.6: own bloc from R0; other four blocs from R2; Isla Serena from R4) else `ACCT_CITY_NOT_ACCESSIBLE`; once per chapter → `ACCT_CITY_ONCE_PER_CHAPTER`; fee `home_city_change_fee_real × MSI` burned with `ACCT_HOME_CITY_FEE`; `pendingHomeCityId` set; `applyPendingHomeCities` at DAY_CLOSE P12 swaps and emits nothing public; 15 resets the city-board scores on `acct.homeCity.changed` (new PRIVATE event `{characterId, from, to}`; add to EVENTS_14A).
7. 2FA (§3.1.6): `evaluateTwoFactor` sets `twoFactorRequired = true` (sticky) for characters in any of the three input lists (inputs are provided by 03 NWI percentile and 15 boards through T14A-11 wiring; empty lists without them). `twoFactorGate` is exported for 15 (P2P and contract signature above $1M real).

# SPEC EXCERPTS (verbatim; binding game rules)

**[14 §1 Purpose]** (context)

## §1 Purpose

1. **Make money feel like something.** Rank, home, shell, possessions and titles turn net worth into a place and an identity. A player should feel the jump from $50k to $5M without reading a number (old 04 §0.1).
2. **Drain money in a way players want.** Lifestyle is the economy's most voluntary sink. Mass luxury loses value on purchase and fades in Prestige, so it must be refreshed; collectibles hold value but carry upkeep (old 04 §5.1).
3. **Give small, real, capped advantages** for spending (access, convenience, talent, collateral, reach, physical security) so spending is a decision, never a cash faucet (old 04 §0.4).
4. **Keep three separate social axes**: Prestige (status from what you own and display), Reputation (trust from clean conduct), Notoriety (fame from crime). A player can be high on all three (old 04 §7.1, bible decision 5).
5. **Remember.** The world never resets (L1), so Legacy, Houses and succession give a permanent public history: founding plaques, generations, heirlooms, chapter portraits (V3 Part 9).
6. **Respect the player.** No demotion, no punishing streaks, no real-money path to any of this (L7), quiet money stays a valid strategy (old 04 §7.8).

### §3.4 The shell

The shell is the interface's material theme (old 04 §9.3; layouts and visuals in 17). Rules here: a character earns shell `rK` on reaching rank K and keeps every earned shell forever; the active shell can be any earned shell or any owned cosmetic shell (21). Cosmetic shells are visibly labeled as purchased in the profile's shell field and never count toward Prestige, titles or any rule (L7). The shell never changes what information a player sees (17 §1 rule 4). The default active shell is the highest earned; a player who has chosen a shell manually keeps it on rank-up (the ceremony offers a one-tap switch).

### §3.12 Anti-cheat and integrity

**§3.12.1 Threats and counters** (old 02 §10.1, kept and made exact):

| Threat | Counter |
|---|---|
| Client tampering | server authority; clients send intents only (19) |
| UI botting outside the in-game AI and API | 20 intents per tick per character (00 §5.5); timing analysis (§3.12.4); no speed advantage (batch auction); in-game AIs and the official API are cheaper anyway |
| Multi-accounting and alt funneling | link scoring (§3.12.2), P2P caps by account age (§3.6.12), no P2P for guests, off-market flags, voiding between linked accounts |
| Collusion (fake lawsuits, fake hacks, wash trades, farmed boards) | value-flow graph (§3.12.3); 13 voids settlements between linked accounts; 12 voids sessions between linked accounts; boards ignore scores earned against linked accounts; 05 blocks self-matching of the same beneficial owner |
| Real-money trading | ToS ban; P2P caps; flags on large transfers to new accounts; handle-change limits (14); 24-hour hold on P2P transfers above $1M real after a password or email change |
| Exploiting bugs | event log finds every beneficiary; targeted rollback by compensating ledger entries (`INTEGRITY_CLAWBACK`, reason-coded, second admin approval, 21); never a world rollback |
| Real account theft | 2FA for top-1% and Chairs (14 §3.1.6), new-device alerts, the 24-hour hold above |
| Harassment | block, mute, report, slow mode, 21 moderation; 12/13 repeat-targeting caps |
| Leaking hidden sessions by datamining | identical serialization and hourly refresh (12 owns) |
| Timing attacks on news or the seed | batches close before publication; seed secret; commit-reveal entropy (02) |
| Insider abuse by staff | admin actions are ledger events with reason codes, second approval for any mint, internal audit log (21) |

**§3.12.2 Link scoring.** For each pair of accounts with any shared signal, signals are scored and combined:

| Signal | Strength `s` |
|---|---|
| `DEVICE` (same device fingerprint seen on both within 30 real days) | 0.5 |
| `PAYMENT` (same payment instrument for cosmetics, 21) | 0.6 |
| `IP_ASN` (fraction of sessions sharing IP /24 in the last 30 real days, × 0.4) | ≤ 0.4 |
| `EMAIL_PATTERN` (normalized email local-part similarity ≥ 0.8) | 0.1 |
| `LOGIN_TIMING` (never both online at once over ≥ 20 sessions while sharing IP) | 0.2 |
| `BEHAVIOR` (intent-sequence similarity ≥ 0.9, computed weekly) | 0.2 |
| `VALUE_FLOW` (§3.12.3 one-directional flow flag) | 0.3 |
| `REFERRAL` (one referred the other) | 0.05 |
| `ADMIN_CONFIRMED` | 1.0 |
| `DECLARED_HOUSEHOLD` | 1.0 |

```
score = 1 − Π_signals (1 − s)
linked  = score ≥ PARAM.link_hard = 0.7  OR admin-confirmed OR declared OR same beneficial owner (03)
suspect = PARAM.link_soft = 0.4 ≤ score < 0.7
```

The exported predicate used by every module is `linkedAccounts(a: EntityId, b: EntityId): boolean`, evaluated on the controlling characters of the entities (`true` also when both are controlled by the same character). Effects of `linked`: contracts voided (§3.6.12), sessions voided (12), settlements voided (13), board, ladder, Most Wanted and Defender scores against the other ignored, Reputation events between them ignored (14), P2P transfers refused. Effects of `suspect`: P2P between them capped at $10,000 real per real day, every contract flagged, a review case opened. Families who share devices can **declare a household** (`soc.integrity.declareHousehold`): the pair is linked for all rules above, but no sanction applies. Link scores and signals are never shown to players.

**§3.12.3 Value-flow graph.** Daily, for every ordered pair (a→b) with ≥ 5 value-moving interactions in the trailing 14 real days (contract payments, auction wins at above fair value, P2P transfers, settlements, op loot), compute `flowRatio = value(a→b) / (value(a→b) + value(b→a))`. If `flowRatio ≥ 0.8` and `value(a→b) ≥ $50,000 real`, add `VALUE_FLOW` evidence and open an `ALT_FUNNEL` review. Clusters (connected components of suspect or linked pairs with ≥ 3 accounts) open a `COLLUSION` review.

**§3.12.4 Botting signals.** A character is flagged `BOTTING` for review if any holds for 3 consecutive real days: presence ≥ 20 real hours per real day; intent inter-arrival times with coefficient of variation < 0.05 over ≥ 500 intents; ≥ 90% of ticks with an intent while present. The sanctioned automation routes are the in-game AI (11) and the official intent API (19) under the same limits. **V3 question 3 resolved** (`DEFAULT, Mathis may override`): the official read/write intent API is available to a character holding license LIC2 Pro or higher, with 2FA (MFA) enabled and account age ≥ 7 real days (ruling in 24; 19 Rule 3.10.3 implements the `api.eligible` flag), using the same 20 intents per tick and the same validation as the UI. Rank and Reputation are not API gates.

**§3.12.5 Enforcement ladder** (old 02 §10.2): warning → asset clawback of exploit gains → temporary ban (character frozen like Held, removed from boards for the rest of the chapter) → account ban. Every step is logged with evidence and appealable through 21's support flow. Confidence < 0.6 never bans; it can place the character in a **shadow pool** (§3.12.6).

**§3.12.6 Shadow pools.** A character with an open integrity case of confidence 0.4–0.6 is grouped in leagues only with other shadow-pool characters and hidden from public top-100 views; everything else (trading, contracts with unlinked players subject to caps) works normally. The pool lasts until the case closes or 14 real days pass.

**§3.12.7 Integrity telemetry** (21 dashboard, also per partition and country): money minted and destroyed per tick by reason code, top 20 wealth deltas per game day with explanation breakdown, P2P flow graph, contract defaults, flagged accounts, tick timing. The public Stabilizer and Exchange integrity report (03, 20) publishes aggregates and exploit-fix history.
