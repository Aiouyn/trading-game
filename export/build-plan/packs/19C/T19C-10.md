## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Implementation steps
1. Connect: fetch a ticket, open the socket, send `hello {protoVersion, sessionToken, lastSeen, locale, device}`; on `bye UPGRADE_REQUIRED` stop reconnecting and emit `bye`; on close reconnect with backoff 0.5 s doubling to 30 s with jitter from the injected random source; on reconnect send `lastSeen` from `ChannelStore` and resubmit `PendingIntents.resendable()` with their original intentIds (dedupe makes it safe, §8 edges 4-5).
2. Ping every `ws_ping_s` (15); `ClockSync` uses the NTP-style offset `((serverMs − sent) + (serverMs − recv)) / 2` and the median of the last 5 samples (Rule 3.8.1 item 3); used only for the tick-pulse countdown, never for which tick an intent lands in.
3. Signing: generate the key pair with `extractable: false`; register the public key; sign `signingBytes(intent)`; base64url signature. Nonces strictly increasing and saved before sending (IndexedDB in the browser via the injected store; a file or memory store for bots).
4. Intents: `newIntentId` once per user action; `clientTick` = the tick the client believes is next (from the last `tick` message + 1); the client shows "pending tick N" until the result (no prediction, Rule 3.17.2).
5. Channels: `snap` replaces state; `delta` with `seq === current + 1` applies with `applyOps`; a gap returns `GAP`, the client resubscribes for a fresh `snap`; `stale` set when the gateway signals backpressure (fresh snap follows).
6. Worker (Rule 3.17.1): owns the `TycoonClient`; frames are binary MessagePack in production (JSON only with `ws_json_frames` in dev); it coalesces all channel changes of a tick into one `changes` message to the main thread (compact patches, no full bodies after the first snap); the main thread never opens a socket for game traffic (Rule 3.2.2).

# SPEC EXCERPTS (verbatim; binding game rules)

**[19 §1 Purpose]** (context)

## §1 Purpose

1. **One authoritative world.** The server is the only truth (L1, L14). Clients send intents and render deltas. No client ever runs the authoritative simulation, holds the world seed, or computes its own fills, balances or roll outcomes.
2. **One logical world on many machines.** The world is a single deterministic fold over sealed intents. It is executed by many single-writer **partitions** under a bulk-synchronous tick (one barrier per pipeline phase of 00 §5.2). The result of a tick never depends on how many partitions exist or which machine runs them. That is what makes partitioning invisible (L1) and replay exact.
3. **Fairness by construction.** Every actor (human UI, expert API, player AI, delegated manager, NPC) enters the world through the same intent pipeline with the same validation and the same tick (00 §5.5). Ordering inside a tick never rewards network speed.
4. **Provable honesty.** Every input is stored; every output is reproducible; every random outcome a player is party to is verifiable after the fact (§3.12). The Truth Machine (20) runs on the same engine packages.
5. **Privacy by serialization.** Data the client must not know never leaves the partition that owns it (L11). The gateway only relays deltas already filtered for their recipient.
6. **A builder's map.** §12 orders every module of 00 §1 into a build sequence with gates, so the game can be built bottom-up without a question.

### §3.17 The client application

**Rule 3.17.1 (structure).** `apps/web` is one Next.js 16 App Router codebase for web, PWA and native shells: route groups `(marketing)` (server-rendered, public), `(account)`, `(game)` (client-rendered game shell), `(store)` (21). The game shell is client-side after first load. A dedicated Web Worker owns the WebSocket, decodes MessagePack, applies deltas to normalized channel state and posts compact change sets to the main thread, where Zustand stores (one per channel family) feed React. TanStack Query handles HTTP reads.

**Rule 3.17.2 (no prediction of money).** The client never predicts fills, balances or outcomes. A submitted intent shows "pending tick N" with the tick ring countdown (17) until its `IntentResult`. Only cosmetic actions (layout, renaming a widget locally before confirmation) are optimistic.

**Rule 3.17.3 (performance budgets).** Trade screen first load ≤ `PARAM.ui_js_budget_kb = 200` KB gzipped JS; tick render ≤ `PARAM.ui_perf_tick_render_ms = 8` ms on the reference mid-range Android device (22 lists it); 60 fps scrolling for lists of 500 rows (virtualized); city renderer (three.js, instanced) ≥ 30 fps on the reference device at default quality, streaming city chunks from the CDN.

**Rule 3.17.4 (sandbox mode).** The client can run the engine locally in a Web Worker for the Academy (18), tutorials and the replay viewer, from a local seed. Sandbox results are **unranked and non-transferable**: they never affect the persistent world, boards or character, except Academy lesson completion flags and sandbox-only cosmetic badges recorded through ordinary HTTP. This resolves roadmap Q4 (option A, tightened: only Academy completion and sandbox badges carry over) and V3 Part 11 ("solo as a non-competitive sandbox"). Roadmap Q5 is resolved by the server existing: shared weekly challenges and the AI tournament run on server-side harness worlds with committed seeds revealed after lock (§3.12, 15). Roadmap Q8 (Held in solo) is 13's rule; in sandbox mode DEFAULT (Mathis may override): Held is off and replaced by the fine, op ban and record, matching the roadmap's recommendation B.

**Rule 3.17.5 (PWA).** Web App Manifest via the Next 16 metadata route; a Serwist service worker caches the app shell and static assets only, never market data; offline screen shows the last `me` snapshot read-only with its tick; Web Push for opted-in notifications (≤ 5 pushes per real day and quiet hours, 15).

**Rule 3.17.6 (native).** Capacitor wraps a static export of the game shell (the marketing and account routes stay on the web); data only via socket and HTTP. Native plugins: push, haptics on fills and alerts, secure storage for tokens and signing keys, share sheet, biometric unlock of the session. Purchases on native go through the platform stores (21).

**Rule 3.17.7 (localization and accessibility hooks).** Every user-visible string is an i18n key (L8) in `packages/i18n`; the protocol sends codes and params, never prose, except player-authored text and news text already localized by 16 into both languages. Numbers and money are formatted on the client by locale.
