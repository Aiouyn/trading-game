## Goal
Implement 19 Rule 3.10.3: the expert API is unlocked by flag `api.eligible` (account FULL, MFA enabled, account age >= `api_min_account_age_days` (7) real days, license >= LIC2, no active automation sanction); eligible players register up to `max_api_keys` (5) public keys with scopes `read`, `trade` (`mkt.*`), `manage` (other intent kinds); the same WebSocket protocol is served at `wss://api.<domain>/v1/ws` with authentication by signing a server challenge, and the read-only HTTP routes accept a signed `Authorization` header within `api_sig_skew_s` (60). API intents use the same validation, tick and rate bucket as the UI (threats E6, E7 of 19 §9); `me.connections` keeps the UI refresh limit (once per game hour, 12 §3.7, threat E11).

## Implementation steps
1. Eligibility: evaluated on every key creation, every API connection and every HTTP signed call (cached 60 s); conditions in rule order; account age in real days from `account_ref.created_at`; `api.eligible` is a platform flag, never an engine input. The API screen (T19C-11, 17 screen 32) shows `unmet` condition codes as i18n keys.
2. Keys: the player's tooling generates the pair; the server stores only the public key, alg, scopes, label, `last_used_at`; POST requires MFA verified within the last 10 real minutes (T19C-02, 19 §4.2, threat E13) and sends a notification email through the jobs service; at most 5 active keys; revocation publishes on the revocation channel so gateways close API sockets with `bye SESSION_REVOKED` within 1 s; both actions write audit rows.
3. API WebSocket: separate hostname behind the same CDN (T19D-07); the first frame carries a 32-byte random challenge; the client answers `apiHello {keyId, challengeSig}`; the gateway verifies the signature with the stored key, checks eligibility and opens a normal session with `channel: 'API'`. From there the protocol is identical: same `intent` frames signed by the API key with its own nonce window, same intake check order, same seal timing, same channels and authorization. Scope check runs after KIND: an intent kind outside the key's scopes is rejected `BAD_SCHEMA` with code `API_SCOPE`.
4. Same bucket (Rule 3.8.6): `takeIntentToken` keys buckets by actor and principal, never by channel, so UI and API intents of one player share one budget per tick (E6). No extra data: the API exposes exactly the channels and HTTP routes of the UI; no order type or field exists only on the API (E7).
5. Signed HTTP: `Authorization: Tycoon-Sig keyId=<id>,ts=<ms>,sig=<b64u>` over `method \n path \n bodySha256 \n ts`; rejects when |now − ts| > 60 s (`SIG_SKEW`); read-only routes only (GET); keys with scope `read` or wider.
6. `me.connections` (12 §3.7): the refresh limiter is keyed by character, not by channel, so the API cannot refresh more than once per game hour (E11).
