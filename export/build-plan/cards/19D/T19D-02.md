## Goal
Deploy without missing a tick (19 Rule 3.16.1): stateless services roll; engine versions change only at a snapshot boundary, the new bundle is loaded on standby hosts from the boundary snapshots and takes over partition by partition in the gap after P14, and if any partition fails the whole world stays on the old version for that boundary (19#60, §8 edge 11). Before any engine deploy the golden replay gate of Rule 3.6.7 replays the last `deploy_replay_game_days` of production batches on old and new engine and blocks on any divergence not listed in the change's `intendedDivergence` manifest (19#61). Plus the host side of param and content changes (Rule 3.16.2), feature flag separation (Rule 3.16.3), database migration rules (Rule 3.16.4) and state migrations (Rule 3.16.5).

## Implementation steps
1. Rolling services: order of `ROLL_ORDER`; gateways drain by sending `bye RECONNECT` to sockets in batches so clients reconnect to other instances with `lastSeen` (resume, no gap); web, projector and jobs roll one instance at a time. Protocol compatibility: the gateway keeps accepting `proto_min_version` (current − 1) for 14 real days after a native release (§8 edge 24).
2. Engine upgrade (Rule 3.16.1): staff approve `sys.engine_upgrade {engineVersion, bundleHash, effectiveTick}` (2 approvals, T19B-13); the precondition is a green `GateResult` for that bundleHash (step 4), converted into the `CiReplayReport` T02-18 requires for `adm.version.cutover`. Before the boundary, `prepareStandby` starts new-version processes on standby hosts. After the DAILY snapshot of boundary tick N (`tickOfDay(N) === 719`), each standby loads its partitions' snapshots, runs the registered pure state migrations (Rule 3.16.5) before P0 of N+1, and reports its logical hash of the migrated image; `takeover` switches partitions over in the inter-tick gap. If any partition fails to load, mismatches the expected migrated hash or the gap runs out, no partition switches (a mixed-version tick is never allowed, §8 edge 11): the old processes keep running, the upgrade is retried at the next boundary and an alert fires.
3. Param and content changes (Rule 3.16.2): the admin console (21) submits `sys.param_change` / `sys.content_change`; this card provides `validateChange` running 23's range checks before approval and the host conversion to 02's `adm.param.cutover` directive; the batch records `paramsVersion` and `contentVersion`, so a safe-mode replay of a tick re-executes with the same versions (§8 edge 12).
4. Golden gate (Rule 3.6.7): CI job `deploy-gate` runs (a) all regression seeds of 20 on old and new bundles with `compareDigestStreams`, and (b) a replay of the last `deploy_replay_game_days` (1 game day, 720 ticks) of production batches from the latest DAILY snapshot on both bundles, comparing per tick `worldHash`, event digest and posting digest; for every divergent tick the per-event diff is classified as intended when its kind is in `eventKinds` (and entity in `entityIds` when given, tick at or after `fromTick`). Any unintended divergence fails the gate and blocks the `deploy.yml` engine step.
5. Migrations (Rule 3.16.4): expand-migrate-contract; `lintMigration` rejects destructive statements in an expand release, column renames, NOT NULL without default and non-concurrent index builds on hot tables (`engine_event`, `intent_batch`, `tick_record`, `auth_session`); `measureLockMs` runs each migration against a staging copy under a probe query loop and fails above `migration_max_lock_ms` (1,000).
6. Flags (Rule 3.16.3): world-affecting flags are params (go through step 3); client presentation flags live in the platform database and may vary per user; the boundary config of T19A-04 forbids `packages/engine` from importing `@tycoon/platform/flags`.
