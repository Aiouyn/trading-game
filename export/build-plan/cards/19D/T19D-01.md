## Goal
Take the world host from one machine to many (19 Rule 3.5.7, Rule 3.13.1 architecture target of about 40 hosts): hosts register with the coordinator, partitions are placed on hosts (placement is not part of `PartitionMap.homeRules`; only `hostId`, excluded from every hash), the coordinator plans map changes from platform metrics (Rule 3.5.6), seals `sys.partition_map` at a snapshot boundary and executes entity-group moves with `MOVE` snapshots and a logical hash check after P14 (Rule 3.5.5), cancelling on mismatch. Clients never see a disconnect or delta gap (19#25). Also the capacity formulas of Rule 3.13.2 and 3.13.3 used for sizing.

## Implementation steps
1. Hosts: each world host joins over `ctl.host.join` with cores, AZ and engine version; heartbeats every 500 ms on the lease channel (T19B-12); a host missing 3 heartbeats is `DOWN` and its partitions are recovered on standby capacity from the last snapshot plus PHASE replay (T19B-12 `recoverPartition`). Placement maps partitions to hosts; `hostId` appears in no hash, no event and no player payload (threat E23 of 19 §9).
2. Metrics: per game day per partition the coordinator records agent count and the max p95 phase share (`tick_phase_ms{phase,partition}` / phase budget); per host the average CPU over the game day. Values come from platform telemetry (T19B-03), never from engine state.
3. Planner (Rule 3.5.6): SPLIT a PLAYER partition whose `agents > partition_target_agents` (25,000) or `phaseBudgetShare > 0.8` on each of the last `rebalance_trigger_days` (3) game days: its hash range is halved, the upper half goes to a new partition id; MERGE two PLAYER partitions with adjacent hash ranges both below 0.3 share for the same 3 days; MOVE_HOST partitions off a host whose average CPU exceeds `host_cpu_target` (0.7), largest first, to the least loaded READY host. At most `max_moves_per_boundary` (4) changes; the rest wait for the next boundary. A persistently slow but alive host (19 §8 edge 9) is handled the same way. MARKET, CITY, FINANCE, CCP, COORD, ACTOR partitions move only by MOVE_HOST; a single asset is never split (§8 edge 18).
4. Seal: when the plan changes the map, COORD includes `sys.partition_map {map}` with `version = old + 1` and `effectiveTick = N + 1` in the batch of the boundary tick N (`tickOfDay(N) === 719`), signed by the COORD key. MOVE_HOST changes alter placement only and need no map version.
5. Move (Rule 3.5.5): after P14 of N and the DAILY snapshot point, for each group the source host serializes the moving entities into a `MOVE` snapshot (T19B-11), the target loads it, both report per-entity hashes and the logical hash of the group; COORD compares them. All equal: TickRecord N+1 is produced under the new map (`partition_map` row `active_from_tick = N + 1`). Any mismatch, load failure or the inter-tick gap running out: the move is cancelled, the old map stays active (the next TickRecord records the old `partitionMapVersion`), an alert fires, and the planner retries at the next boundary. The engine's T_PENDING MAP row is informational and cleared at effectiveTick either way; logical state does not depend on the layout (19 Rule 3.6.6), so a cancelled move never changes outcomes. Replay and recovery use each TickRecord's recorded `partitionMapVersion`.
6. Homes across control changes (§8 edges 13, 14): routing uses the map's recorded home; an entity whose controller changed moves only with the next boundary's move plan; contract anchors never move before a boundary.
7. Gateways: `onMapChange` updates presence routing; deltas are keyed by channel and tick, not by partition, so subscriptions, resume buffers and seq numbers continue unchanged across the boundary; nothing is sent to clients about the move.
8. Capacity helpers implement Rule 3.13.2 and 3.13.3 exactly and feed `shapeFor` (T19B-16) and the deployment sizing of T19D-07.

## Test plan
`cluster.test.ts`:
- planner: a PLAYER partition with 25,001 agents on 1 day -> SPLIT with its range halved (lower half stays, upper half goes to the new partition id); 0.81 share on days 1, 2 only -> no change, on day 3 -> SPLIT; two adjacent at 0.29 and 0.25 for 3 days -> MERGE; 6 eligible changes -> exactly 4 planned, ordered; a host at CPU 0.75 -> MOVE_HOST of its largest partition to the least loaded host.
- capacity: `playerPartitions(40000, 25000) === 2`, `playerPartitions(750000, 25000) === 30`, `gatewaysFor(5000, 10000) === 2`, `gatewaysFor(100000, 10000) === 13`, `actorPartitions(600) === 2`; `marketGrouping` never puts one asset in two groups and keeps each group <= 60% of the budget when possible.
- cancellation: a target that reports a different group hash -> `{ ok: false, reason: 'HASH_MISMATCH' }`, the next TickRecord has the old map version, an alert is recorded.
`rebalance.e2e.ts` (headless multi-host world: 2 host processes simulated by two worker pools over the memory bus, fixture modules of T19B-08, 3 game days = 2,160 ticks):
- `19#25 Moving a PLAYER hash range between partitions at a boundary leaves logicalStateHash identical to a run without the move, and no client sees a disconnect or delta gap`: run A with `standardMap(16)` and no change; run B identical batches with a SPLIT of one PLAYER partition sealed at tick 719 and a MOVE_HOST at tick 1,439: `logicalStateHash` equal at every tick 0..2,159; 50 SDK clients (T19C-10) subscribed to `me`, `clock` and one book through the gateway see zero `bye`, zero socket closes and zero `GAP` results, and every channel seq is contiguous across ticks 719-720 and 1,439-1,440.
- host down: killing one host at tick 900 -> its partitions recover on the other host, ticks continue, hashes still equal run A.
