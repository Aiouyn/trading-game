## Goal
Build the machinery of 03's reason-code catalog (one definition per code, each in exactly one class, with the templates that class allows) and transcribe the 37 FAUCET and 86 SINK codes of 03 §3.4.1 and §3.4.2 completely, with the per-code ledger metadata the template layer needs (value-leg defaults, elastic sectors, tax tag, faucet/sink family, restricted-cash permission). The remaining classes follow in T03-03, T03-04 and T03-05; T03-05 assembles the final catalog (the 384 codes of 03 §3.4 plus the codes 24 §8 registers).

## Imports
- T03-01: `FlowClass`, `CashFlowClass`, `TemplateId`, `TaxTag`, `ReasonCodeDef`, `CHART`.

## Implementation steps
1. `types.ts`: types as exported; `CLASS_TEMPLATES` exactly as commented; `ILLICIT_CODES` = the six codes listed in the legend.
2. `registry.ts`:
   - `rowsToEntries(cls, rows)`: `allowedTemplates = tpl.split(' ')`; `elasticSectors = sectors === '-' ? [] : sectors.split(',')`; legs: all digits → number, else the literal string; `taxTag = tax === '-' ? undefined : tax`; `stabilizerFamily = fam === '-' ? undefined : fam`; `requestableBy = alsoBy === '-' ? [] : alsoBy === 'ALL' ? 'ALL' : alsoBy.split(',').map(Number)`; `illicit = ILLICIT_CODES.includes(code)`; `descriptionKey = 'reason.' + code`; `source` default '03'. Omit undefined optional fields (exactOptionalPropertyTypes).
   - `validateCodeEntry`: code matches `^[A-Z][A-Z0-9_]*$`; every template in `CLASS_TEMPLATES[cls]` and at least one; elasticSectors non-empty iff an ELASTIC template is allowed; `owner` in 2..21; cf in OP/INV/FIN/NC; REVALUE codes have cf `NC`; a numeric leg is a code present in `CHART` (T03-01); MINT/BURN-only codes have legB '-'. Messages are `<code>: <problem>`.
   - `buildCatalog`: concatenates parts, reports `DUPLICATE <code>`, every validation error, and alias errors (`ALIAS_TARGET_MISSING <name>`, `ALIAS_SHADOWS_CODE <name>`); entries stored in a `SortedMap` keyed by code; aliases in a second `SortedMap`. `mayRequest(code, m)`: `m === owner || requestableBy === 'ALL' || requestableBy.includes(m)`; unknown code → false. `templateAllowed` checks the entry's `allowedTemplates`.
3. `faucet.ts` and `sink.ts`: one `CodeRow` per row of the tables below, in the same order; owner, CF and description copied from the row of the same code in the spec excerpts 03 §3.4.1 / §3.4.2. Then `FAUCET_CODES = rowsToEntries('FAUCET', FAUCET_ROWS)`, same for SINK.
4. Families follow 03 §3.6 ("Codes (main)" column, with `LAB_*_ELASTIC`, `BNK_ELASTIC_*` in, `LIFE_*` sinks and `LAB_COMPUTE_*_NPC` expanded to concrete codes). Codes with no family are shown as "other" in the money report (T03-11).
5. Rulings: `ACCT_REWARDED_AD` is the ad faucet; its amount ($250 real × MSI, 24 Y2) is computed by its owner (21), never by the catalog; `AD_GRANT` is only the restricted-lot tag and is never a reason code (24 R23).

Column legend (identical in every catalog task T03-02..T03-05):
- **Code**: the reason code exactly as in the spec table (owner, description and CF come from the spec excerpt row of the same code; transcribe them verbatim: `owner` as a number, `descriptionEn` = the Description cell, `cf` = the CF cell).
- **Tpl**: `allowedTemplates` (space separated when several). It must belong to the class's template set (`CLASS_TEMPLATES`).
- **Sectors**: `elasticSectors` for ELASTIC_IN / ELASTIC_OUT codes (comma separated `hh`, `frm`, `row`), `-` = none.
- **Leg A / Leg B**: default value-leg accounts (03 §3.3.3 "value leg"). Meaning per template: PAY: A = payer's debit account, B = payee's credit account; MINT / BURN: A = the entity's value leg (MINT credits it, BURN debits it), B unused; ELASTIC_IN: A = sector's debit account, B = core payee's credit account; ELASTIC_OUT: A = core payer's debit account, B = sector's credit account; SWAP_ASSET: A = buyer's (receiver's) asset or issuance account, B = seller's (giver's) asset or issuance account; MOVE_QTY: A = giver's value-leg debit, B = receiver's value-leg credit, while the moved asset accounts come from `PostOptsExt.assetAcct` (receiver) and `assetAcctFrom` (giver, default the same code); LEND / REPAY / CB_CREDIT / CB_CREDIT_UNWIND: A = the account debited in step (2), B = the account credited in step (2); ACCRUE / RECLASS: A = dr, B = cr. `@ASSET` = the caller must pass the asset account code (`valueLegA` / `valueLegB` in PostOpts) because it depends on the asset (1500, 1580, 1870, ...); `@` = caller must pass it (any account); `-` = not used. A caller may always override a default through `PostOpts.valueLegA` / `valueLegB`.
- **Tax**: `taxTag` (`-` = none).
- **Fam**: `stabilizerFamily` of 03 §3.6 (`-` = none).
- **R**: `restrictedOk` (Y = restricted cash may fund it, 03 §3.5.6; every other code is a forbidden purpose for restricted cash).
- **Also by**: `requestableBy` beyond the owner: module numbers, `ALL`, or `-` (owner only). These are service codes other modules post through 03 (taxes at source, accruals, depreciation, intragroup sweeps).
- `illicit` = true exactly for `OPS_LOOT_CASH`, `OPS_RANSOM`, `OPS_FENCE_SALE_NPC`, `OPS_BRIBE_NPC`, `OPS_BRIBE_CORE`, `SOC_EMBEZZLEMENT` (03 §3.12.14 finding (a)).
- `descriptionKey` = `reason.<CODE>` (i18n key).

Notes on the tables:
- Asset sales to or purchases from elastic sectors (`@ASSET` legs, e.g. `PROP_SALE_TO_ELASTIC`, `COLL_BUY_FROM_NPC`, `LP_INVENTORY_*_ROW`) move a quantity with the money: the template layer (T03-07) books `Dr receiver:asset / Cr giver:asset` with `qty`, plus the seller's book-value adjustment of `SWAP_ASSET` step (3).
- `BIZ_UPGRADE_CAPEX` debits 1830 in full; 09 then posts `LED_IMPAIRMENT` for 30% as a separate REVALUE entry (03 §3.4.2 row).
- `LIFE_PURCHASE` credits the sector with the sink part only; the VAT part is a separate `TAX_VAT_REMIT` PAY to the residency treasury inside the same purchase (03 §3.12.9; T03-21 computes it).
