## Goal
Finish the reason-code catalog: transcribe the 12 CREDIT_CREATE, 13 CREDIT_DESTROY and 27 REVALUE codes, register the six codes that the 24 §8 alias table assigns to 03's catalog, encode the 24 §8 alias table (module names that must be posted as the 03 canonical code), provide the R23 extension point for codes other modules define, assemble the frozen `REASON_CATALOG`, write the CI scanner of acceptance test 03#1, and implement invariant INV-LED-002. It also defines the shared invariant-check view used by every 03 invariant.

## Implementation steps
1. `credit.ts`, `revalue.ts`: one `CodeRow` per row of the tables below; owner, CF and description verbatim from the spec excerpts (03 §3.4.4, §3.4.5, §3.4.6). `CBK_CREDIT_CODES` = codes starting with `CBK_` in both credit tables (10 codes).
2. Template notes (implemented by T03-07, recorded here as comments): `BNK_SECURITY_PURCHASE`/`BNK_SECURITY_SALE` replace LEND/REPAY step (2) by the security leg (`Dr bank:1520 / Cr seller:1520` with qty, or the reverse). `CB_CREDIT` codes whose counterparty is not a bank (QE from a fund, 03 §8 edge 16) use settlement cash `1001`/`2001` instead of reserves `1002`/`2002`. `CBK_ASSET_PURCHASE`/`CBK_ASSET_SALE` carry the asset leg (`@ASSET`, qty). `CBK_FX_INTERVENTION_BUY/SELL` carry a second currency leg (foreign settlement cash between the counterparty and the cbk, booked against 3800 per currency like `FX`). 04 §3.18 says QE and FX intervention trade through 05 (`MKT_TRADE`); both paths stay valid: through 05 the trade is a TRANSFER and 04 then posts no CBK credit code; through `cbCredit` the class is CREDIT_CREATE. 03 owns the class of its codes (00 §3.5); the code stays in the catalog.
3. `QTY_ONLY_CODES`: `EQ_SPLIT` (quantity of every holder and of the issuer's 3100 account scaled, value unchanged) and `LED_DISSOLUTION` (closing record, 03 §3.1.3) produce entries whose postings may have `amount = 0n`. They are the only exception to 03 §3.3.2 rule 1 and to INV-LED-007; the exception is listed in those checks. Resolution of a spec gap: 03 §3.1 calls the dissolution record "amount 0" while I1 requires amount > 0; the owner's specific statement wins for these two codes.

Column legend (identical in every catalog task T03-02..T03-05):
- **Code**: the reason code exactly as in the spec table (owner, description and CF come from the spec excerpt row of the same code; transcribe them verbatim: `owner` as a number, `descriptionEn` = the Description cell, `cf` = the CF cell).
- **Tpl**: `allowedTemplates` (space separated when several). It must belong to the class's template set (`CLASS_TEMPLATES`).
- **Sectors**: `elasticSectors` for ELASTIC_IN / ELASTIC_OUT codes (comma separated `hh`, `frm`, `row`), `-` = none.
- **Leg A / Leg B**: default value-leg accounts (03 §3.3.3 "value leg"). Meaning per template: PAY: A = payer's debit account, B = payee's credit account; MINT / BURN: A = the entity's value leg (MINT credits it, BURN debits it), B unused; ELASTIC_IN: A = sector's debit account, B = core payee's credit account; ELASTIC_OUT: A = core payer's debit account, B = sector's credit account; SWAP_ASSET: A = buyer's (receiver's) asset or issuance account, B = seller's (giver's) asset or issuance account; MOVE_QTY: A = giver's value-leg debit, B = receiver's value-leg credit, while the moved asset accounts come from `PostOptsExt.assetAcct` (receiver) and `assetAcctFrom` (giver, default the same code); LEND / REPAY / CB_CREDIT / CB_CREDIT_UNWIND: A = the account debited in step (2), B = the account credited in step (2); ACCRUE / RECLASS: A = dr, B = cr. `@ASSET` = the caller must pass the asset account code (`valueLegA` / `valueLegB` in PostOpts) because it depends on the asset (1500, 1580, 1870, ...); `@` = caller must pass it (any account); `-` = not used. A caller may always override a default through `PostOpts.valueLegA` / `valueLegB`.
- **Tax**: `taxTag` (`-` = none).
- **Fam**: `stabilizerFamily` of 03 §3.6 (`-` = none).
- **R**: `restrictedOk` (Y = restricted cash may fund it, 03 §3.5.6; every other code is a forbidden purpose for restricted cash).
- **Also by**: `requestableBy` beyond the owner: module numbers, `ALL`, or `-` (owner only). These are service codes other modules post through 03 (taxes at source, accruals, depreciation, intragroup sweeps).
- `illicit` = true exactly for `OPS_LOOT_CASH`, `OPS_RANSOM`, `OPS_FENCE_SALE_NPC`, `OPS_BRIBE_NPC`, `OPS_BRIBE_CORE`, `SOC_EMBEZZLEMENT` (03 §3.12.14 finding (a)).
- `descriptionKey` = `reason.<CODE>` (i18n key).
