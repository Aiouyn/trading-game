## Goal
The only way to build ledger entries (03 §3.3.3): pure builder functions, one per template, that take the reason code, the parties and amounts, look up the code's catalog entry (class, allowed templates, default value legs, elastic sectors), produce the full balanced posting list (cash legs through the rail of T03-06), and return an `Entry`. Invalid requests do not throw: they return an `Entry` with `invalid` set so P13 fails it deterministically (the safe-mode attribution of 02 §3.15.3 then quarantines the culprit).

## Implementation steps
1. Common prologue of every builder, in this order (first failure → `invalidEntry`, no throw):
   a. `entry = catalog.get(code)`: missing → `INV-LED-002 code=<code>`; template not in `allowedTemplates` → `INV-LED-002 template=<tpl>`;
   b. `catalog.mayRequest(code, env.moduleNumber)` false → `INV-LED-002 requester=<module>`;
   c. amounts: `amt >= 0n` after the negative-swap rule (a negative `amt` on ACCRUE/ACCRUE_PAIR swaps dr and cr, 03 §8 edge 18; on any other template negative is invalid `INV-LED-007`); `amt === 0n` returns an entry with no postings (allowed; it commits nothing) except QTY_ONLY codes;
   d. every named entity exists in `env.rail.entity` and is not DISSOLVED → else `INV-LED-007 entity=<id>`;
   e. value legs: `legA/legB` from `o.valueLegA/valueLegB` else the catalog default; a default of `@ASSET`/`@` without an override → `INV-LED-007 leg_missing`.
   The entry has `entryId = env.newEntryId()`, `tick`, `template`, `reason = code`, `requestedBy`, `holdId = o.holdId`, postings numbered 0.. in emission order with `refs = o.refs ?? []`; `headline = { amount: amt, ccy, counterpartyId: <the other party, if any> }`.
2. Postings per template (E:code = account of entity E; accounts per ccy; `cb = cbkId(ccy)`; sub-keys: holder subs on the cbk as T03-06, counterparty or contract subs per the 03 §3.2 Sub column):
   - PAY: cash leg `cashLeg(rail, A, B, amt, ccy, code, { restrictedOk: entry.restrictedOk, fixedSources: o.fixedSources })` then `Dr A:legA / Cr B:legB` (amount amt; sub = `o.sub` if given). `from === to` allowed only for `MAC_TREASURY_SWEEP` (cash leg between the two 1003 subs of `o.payeeSub`, no value leg).
   - SWAP_ASSET: (1) cash leg buyer→seller; (2) `Dr buyer:<legA>:<assetId> / Cr seller:<legB>:<assetId>` with `qty`, `assetId`, amount = `amt` (notional); (3) if the seller's account (legB) is an ASSET-class account: `bv = bookValueOf(seller account, qty)`; if `amt > bv`: `Dr seller:<legB>:<asset> / Cr seller:<4060|4090>` for `amt − bv`; if `amt < bv`: `Dr seller:<5160|5190> / Cr seller:<legB>:<asset>` for `bv − amt` (4090/5190 when `isNonFinancialAssetCode(legB)`). Issuance accounts (3100, 2300, 2310, 2320, 2330, 3150) get no adjustment.
   - MINT: (1) payee money: `Dr E:<receiving account> / Cr cb:<holder sub>` (via `cashLeg` with the cbk as payer, T03-06 CB_ISSUE); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:5900 / Cr E:<legA>` (default 4110). Restricted lot crediting for `ACCT_REWARDED_AD`/`ACCT_FRESH_START` is decided by T03-12 through `o.sub` (`RESTRICTED:<releaseTick>:<tag>`); the money account is then `E:1001:<that sub>`.
   - BURN: (1) `cashLeg(rail, E, cb, ...)` (destroys the holder's base money); (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr E:<legA> / Cr sys:4900`.
   - ELASTIC_IN (sector X must be `hh`/`frm`/`row` and `kindOfId(X)` ∈ `entry.elasticSectors`, else invalid): (1) payee money as MINT (1); (2) `Dr cb:1910 / Cr sys:2900`; (3) `Dr sys:2909:X / Cr X:1009`; (4) `Dr X:<legA> / Cr E:<legB>`; if `o.qty` (asset sold to the sector): (4) is `Dr X:<assetAcct>:<asset> / Cr E:<assetAcctFrom ?? assetAcct>:<asset>` with qty and the seller adjustment of SWAP step (3) for E.
   - ELASTIC_OUT: mirror: (1) payer's money destroyed via `cashLeg(rail, E, cb, ...)`; (2) `Dr sys:2900 / Cr cb:1910`; (3) `Dr X:1009 / Cr sys:2909:X`; (4) `Dr E:<legA> / Cr X:<legB>` (or the asset leg `Dr E:asset / Cr X:asset` with qty and no adjustment for the elastic seller: elastic sectors carry assets at the transaction price; they are outside every NW board).
   - LEND: (1) `Dr C:1010:B / Cr B:2100:C` (new deposit); if C's `receiveInto` is not a deposit at B, follow with a TRANSFER rail move of the same amount from `C:1010:B` to C's receiving account inside the same entry (reason `BNK_DEPOSIT_OUT` as supporting posting); (2) `Dr B:<legA>:<loanId> / Cr C:<legB>:<loanId>`. `BNK_SECURITY_PURCHASE`: step (2) is `Dr B:1520:<asset> / Cr C:<assetAcct>:<asset>` with qty and C's book adjustment.
   - REPAY: if C's paying source is not a deposit at B, first a rail move into `C:1010:B` (supporting `BNK_DEPOSIT_IN`); (1) `Dr B:2100:C / Cr C:1010:B`; (2) `Dr C:<legA>:<loanId> / Cr B:<legB>:<loanId>`. `BNK_SECURITY_SALE` mirrors.
   - CB_CREDIT: counterparty bank: (1) `Dr B:1002 / Cr cb:2002:B`; counterparty non-bank (QE from a fund, 03 §8 edge 16): `Dr F:<receiving money account> / Cr cb:2001:F` (or reserves of F's bank and the deposit legs, via `cashLeg` with the cbk as payer); (2) `Dr cb:<legA> / Cr cpty:<legB>` (1307/2120 for facilities; for `CBK_ASSET_PURCHASE` the asset leg `Dr cb:1520:<asset> / Cr F:<assetAcct>:<asset>` with qty and F's book adjustment); `CBK_FX_INTERVENTION_BUY`: (2) is the foreign leg: `o.ccy2/amt2` cash from cpty to cb via the rail in ccy2 plus `Dr cb:3800:<ccy2> / Cr cpty:3800:<ccy2>` and `Dr cpty:3800:<ccy> / Cr cb:3800:<ccy>` for amt.
   - CB_CREDIT_UNWIND: mirror of CB_CREDIT.
   - ACCRUE: one posting `Dr E:dr / Cr E:cr` (same entity; amount, qty if `o.qty` for quantity-bearing writedowns is not allowed: ACCRUE moves value only).
   - ACCRUE_PAIR: `Dr A:<legA> / Cr A:<income>` and `Dr B:<expense> / Cr B:<payable>`; defaults for `LED_ACCRUAL`: A receivable 1110 / income 4020, B expense 5090 / payable 2520; overrides `o.valueLegA` (A receivable), `o.valueLegB` (B payable); income/expense codes follow from the receivable (1110→4020/5090, 1100→4000/5000, 2540 rent payable→4010/5020, 2510 wages→ (B side only, A is hh: 4190)). Sub of both = `o.sub` (loanId or contractId).
   - FX: (1) ccy1 cash A→B; (2) `Dr A:3800:<ccy1> / Cr B:3800:<ccy1>`; (3) ccy2 cash B→A; (4) `Dr B:3800:<ccy2> / Cr A:3800:<ccy2>`. Each entity balances per currency (I2).
   - MOVE_QTY: `Dr B:<assetAcct>:<asset> / Cr A:<assetAcctFrom ?? assetAcct>:<asset>` with qty and amount = bookValue; plus `Dr A:<legA> / Cr B:<legB>` amount bookValue (skipped when bookValue is 0n; `qty` 0n with bookValue > 0 allowed only for `INSOLV_DEBT_DISCHARGE`, where both legs are explicit liability/receivable accounts).
   - RECLASS: one posting `Dr E:toAcct / Cr E:fromAcct` (moves a balance from `fromAcct` to `toAcct`; for a credit-normal balance the caller swaps). QTY_ONLY codes: `EQ_SPLIT` emits, for every account holding the asset (all holders and the issuer's 3100 issuance account), one posting `{ debitAccount: <that account>, creditAccount: 'sys_SYSTEM:9200:<assetId>:<ccy>', amount: 0n, qty: newQty - oldQty }` (a negative delta is normalized by swapping sides); 9200 is MEMO so books stay balanced, and the per-asset qty sum over non-MEMO accounts stays 0 because holders and issuer scale together (03 §8 edge 5). `LED_DISSOLUTION` emits no postings.
3. Every built entry is checked with `isBalancedPerEntity`; an unbalanced result (a builder bug) becomes `invalidEntry(... 'INV-LED-001' ...)`.
4. `composeEntries`: concatenates postings of supporting entries into the primary (renumbered), keeps the primary's `entryId`, reason and template; used for at-source taxes and fees inside a trade (T03-21).
5. `payProRata` (03 §8 edge 4): parts = `allocate(total, holders as weights)` (02 §3.9.3, ties by id byte order); one PAY cash leg + value legs per holder with part > 0n, all in one entry; holders with 0n receive nothing; the payer pays exactly `total`.
6. Elastic boundary (03 §3.5.2 context): any code whose class is FAUCET/SINK and has sectors must be called through ELASTIC_IN/OUT with a sector entity; payments between named balance sheets are TRANSFER templates.
