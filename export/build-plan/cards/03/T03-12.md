## Goal
Faucet cash that must not fund certain actions immediately (L12, 03 §3.5.6): rewarded-ad cash (`ACCT_REWARDED_AD`, lot tag `AD_GRANT`) and fresh-start cash (`ACCT_FRESH_START`, tag `FRESH_START`) land in restricted sub-accounts of settlement cash for 51,840 ticks (72 real hours). They can pay for businesses, property, licences, cash-product trades, lifestyle items, taxes and upkeep, never for ops, insider information, margin or collateral, P2P transfers, contract payments or alliance dues. This task owns the lot records, the automatic restricted crediting, the release reclassification and invariant INV-LED-014.

## Implementation steps
1. Edit `packages/engine/ledger/rules/templates.ts` (`tplMint`, `tplElasticIn` not affected): when `code in RESTRICTED_FAUCETS` and `o.sub` is undefined, credit `E:1001:<restrictedSub(tick + RESTRICTED_WINDOW_TICKS, tag)>:<ccy>` instead of `E:1001`. The amount itself is the owner's decision (21: $250 real × MSI per ad, 24 Y2; 14: top-up to $5,000 real, `PARAM.fresh_start_cash_real`, 24 R17); 03 never computes it. `AD_GRANT` is the lot tag only, never a reason code (24 R23, D113).
2. Edit `packages/engine/ledger/commit.ts` (T03-09) to call `recordLotOnMint` for each applied MINT entry whose reason is in `RESTRICTED_FAUCETS` (creates the `led.rlot` row, id = the sub-account key) and `queueReleases` before applying the queue.
3. Spending (03 §3.5.6 "spending draws restricted cash first for allowed purposes"): already implemented by the rail (`restrictedOk` sources first, T03-06) and holds (`placeCashFor` with the purpose code, T03-08). Verify here: `placeCashFor(owner, ccy, amt, exp, ref, purpose)` returns `{ code: 'LED_RESTRICTED_FUNDS' }` when unrestricted spendable < amt ≤ unrestricted + restricted and the purpose is forbidden. Reject code naming: the spec's `REJECT_RESTRICTED_FUNDS` is emitted as `LED_RESTRICTED_FUNDS` (GLOBAL G9 `<MOD>_<REASON>` format; i18n key `err.LED_RESTRICTED_FUNDS`).
4. `ledger.available(E, purpose)` of 03 §3.5.6 is `LedgerApiExt.availableFor(E, ccy, purposeCode)` (T03-09); G7 `available(E, ccy)` excludes restricted lots (the conservative reading for callers that do not name a purpose).
5. Release: `queueReleases` iterates `led.rlot` index byRelease up to `tick`; for each unreleased lot with balance > 0 queue `reclass(entity, balance, ccy, 'LED_RECLASS', 1001, 1001, { sub: from-sub → to unrestricted })` implemented as one posting `Dr E:1001:<ccy> / Cr E:1001:RESTRICTED:…:<ccy>`; mark `released`. Lots with balance 0 are marked released without posting.
6. NW (03 §3.10.2): restricted cash counts at face; nothing to do here (balances are in 1001 subs, which NW sums).
7. Edge case 12 (03 §8): restricted cash and a fresh start in the same tick as a fine: `LAW_FINE_*` codes are forbidden purposes, so the fine is never paid from restricted cash; 13 books it as payable (2550) and garnishes later. Test it.
8. `INV_LED_014` (TICK, FATAL; I21): for every staged posting that credits (pays out of) an account `isRestrictedKey`: the posting's reason and the entry's primary reason are `restrictedOk` in the catalog, or the reason is `LED_RECLASS` moving to the same entity's unrestricted 1001, or an `ADM_*` code (two-approval admin corrections, 21); FIFO: within one entity and ccy, a lot with a later `releaseTick` decreased this tick only if every earlier lot of that entity is 0 after the tick; Σ lot balances ≤ the holder's total 1001 balance (trivially true unless a lot is negative: a negative lot fails). Observed `I21: account=<key> reason=<code>`.
