## Goal
Provide the read-model machinery of 19 Rule 3.10.2 that every module's projection plugs into: consume `EVENTS` strictly in `(tick, seq)` order, apply each event at most once per projection version using `readmodel.projection_watermark`, rebuild a new projection version from the event archive in the background and swap atomically, report lag against `projector_lag_ticks_p95`, plus the ClickHouse tables of 19 §11.3 and the two platform projections (warm event tier, integrity metrics). Owner modules register their own projections (candles 05, boards 15, profiles 14, news 16, statements 03, ...).

## Implementation steps
1. Ordering: the runner consumes `ev.<tick>` messages (one per committed tick, rows in seq order) in bus seq order; within a projection events are applied strictly increasing by `(tick, seq)`; an event not after the watermark is skipped (idempotence, 19 Rule 3.10.2).
2. Exactly-once effect: for PostgreSQL projections the event's effect and the watermark update (`projection_watermark(projection, version, tick, seq)`) commit in one transaction; for ClickHouse projections use ReplacingMergeTree keyed by natural keys plus the watermark row in PostgreSQL written after the ClickHouse insert acknowledges (a crash between them re-applies rows that replace identically).
3. Rebuild: a new version creates its tables with the suffix, replays the Parquet archive (T19B-15) then hot PostgreSQL events, then tails live until caught up, then swaps in one transaction (rename tables or switch a view) and records the new version in the watermark table; the old version is dropped later.
4. Lag: `projector_lag_ticks{projection}` each tick; the SLO "projector lag p95 <= 2 ticks" (19 Rule 3.15.2) alerts when exceeded over a 1 real hour window.
5. Visibility: projections that serve public HTTP routes must store only PUBLIC data or partition rows by `party_ids` for authorized reads (the HTTP layer filters by viewer, E22); SEALED events are never projected into public read models.

- `19#51 replaying the same event range twice into a projection yields identical read-model rows; rebuilding a projection from the archive matches the live one`: a fixture projection (counts per kind and last payload per subject) over 5,000 events: rows after one pass equal rows after re-feeding the same range (watermark skips them and forced re-application via a reset watermark also gives identical rows); rebuild v2 from a Parquet archive of the same events equals v1 row for row; after swap, reads hit v2.

- crash between ClickHouse insert and watermark write: restart re-applies, no duplicate rows.
