## Goal
Implement the account side of 19 §2.5 and Rule 3.9.3 with Better Auth: sign-in by passkey, email magic link, Google, Apple and Discord with optional TOTP; device-bound guest accounts that upgrade to FULL keeping the character; cookie and token lifetimes; the PII separation of Rule 3.14.2 (email encrypted with a KMS data key, looked up by keyed hash; IP and user agent stored only as keyed hashes with rotating salts); the MFA-required rule as the R22 union; brute-force defenses; and the security-change flow that alerts the user and submits `sys.account_security` so the engine holds value removal for 24 real hours.

## Imports
- T19B-04: `accountRef`, `authSession`, `device`, `accountPii` tables, `connect`, `tx`, `appendAudit`. T19B-01: `PlatformSigner` (WEB key), `SystemInput`. T19B-03: `Bus`, `logger` (no PII in logs).
- T14A-??: character creation hook (`acct.character_create` intent kind and the `chr` id it returns) to fill `account_ref.character_id`; ageBand and country rules of 14/15 (values only).
- GLOBAL-CONTEXT: Better Auth (passkey, magic link, social providers, two-factor plugins), Valkey 8 client.

## Implementation steps
1. Better Auth (`apps/web/lib/auth/auth.ts`, route handler under `/api/auth/*` with Next 16 conventions; read `node_modules/next/dist/docs/` first): plugins passkey, magic link, two-factor (TOTP), social Google, Apple, Discord; Drizzle adapter on schemas `platform` (sessions) and `pii` (email, OAuth links in `account_pii.oauth_links`). Web cookie: HttpOnly, Secure, SameSite=Lax, rolling idle `session_idle_days` (30), absolute `session_max_days` (90). Native: refresh token stored by the app in secure storage, access token `access_token_ttl_min` (15). Every session row stores `device_id`, `ip_hash`, `ua_hash`, `strength` (GUEST, PASSWORD_LESS, MFA).
2. Guests (Rule 3.9.3 item 2): device-bound (device id cookie or native install id), limited as 15 specifies (no P2P, no chat, no API: flag `GUEST` checked by those features); upgrading keeps the character and submits `sys.guest_upgrade` (WEB key).
3. PII (Rule 3.14.2): `account_pii.email_enc` = AES-256-GCM with a KMS-wrapped data key (12-byte random nonce prefixed), `email_hmac` unique keyed hash used for lookup; `account_ref` holds no email. Connection roles: only web, jobs and admin can use the `pii` schema (T19B-04 roles). Logs never contain email or IP (T19B-03 redaction).
4. IP and UA hashing with salts rotating every `ip_hash_salt_rotation_days` (30); the salt id prefix keeps old hashes comparable within a period only (clustering signals of Rule 3.9.9 use same-period hashes).
5. MFA (R22, which merges 14 §3.1.6 and 19 Rule 3.9.3 item 3): required for creating API keys, turning on `API_ENABLED`, staff accounts, top-100 of any global board, top 1% NWI and alliance Chairs. Signals come from read models (boards 15, NWI 14) and roles; until those producers exist their signals are false (event edge; fixtures in tests). Where required and absent, flag `REQUIRES_2FA` is set; 14/15 block P2P and contract signatures above $1M real until enabled; MFA is offered to everyone.
6. Brute force (Rule 3.9.3 item 6, Rule 3.8.6): `auth_attempts_per_15min` per account and per IP hash in Valkey with exponential backoff (retryAfter = 2^(failures − limit) seconds, max 15 minutes); CAPTCHA required after `auth_captcha_after_failures` (5) consecutive failures. Breached-password checks apply only if a password method is ever added (none at launch).
7. Security changes (Rule 3.9.3 item 5): email change, MFA reset or removal, password change if added: revoke all signing keys of the account, alert email "new device / security change", submit `sys.account_security` with `holdUntilTick = currentTick + security_change_hold_hours x 720` (24 x 720 = 17,280 ticks), audit row `account.security_change`.

## Test plan
`accounts.test.ts` (PostgreSQL when `PG_URL` set, else in-memory adapters; fake KMS):
- `putEmail` then `findAccountByEmail(' Ann@Example.com ')` finds the account (normalization); the `account_pii.email_enc` bytes do not contain the email text; `account_ref` has no email column.
- `ipHash` stable within a 30-day salt period, different across periods; the hash never equals a plain SHA-256 of the IP.
- guest upgrade keeps characterId and submits exactly one signed `sys.guest_upgrade`.
- security change: two active signing keys become revoked; one `sys.account_security` input with holdUntilTick = 1,000 + 17,280 = 18,280 for current tick 1,000; audit row written.
- auth limits: 10 failures in 15 minutes allowed, the 11th refused with retryAfter; captcha true from the 6th failure.
`mfa-policy.test.ts`: each R22 signal alone requires MFA; none requires nothing; `refreshRequires2faFlag` sets and clears the flag.
