## Goal
Make `packages/protocol` the single place where client-visible shapes live (19 Rule 3.8.3, privacy by serialization): the binding channel catalog of 19 Rule 3.8.2 with a body schema per channel family and its visible-field allowlist, intent payload schemas generated from each engine module's handlers (19 Rule 3.9.2) so gateway and engine validate with the same shape, the doc-sync file `docs/intents.json` extracted from the spec's intent tables, and two CI checks: 19#27 (no hidden field can reach a protocol schema) and INV-STR-005 (every protocol intent kind has exactly one engine handler and a spec entry).

## Imports
- T19A-02: `registerIntentKind`, `intentKinds`, `parseIntentPayload`, `DeltaOpSchema`, `MoneyStr`, `IdStr`, `TickNum`, `INTENT_NAMESPACES`. T19A-05: `registerStaticCheck`.
- T19B-02: `productionModules` (scripts only, never protocol runtime). T02-11: `ModuleDef`, `IntentHandler`. T19B-14: `sysModule` (its `sys.*`/`adm.*` kinds are system inputs, excluded from the player intent list).

## Implementation steps
1. Catalog: transcribe every row of the 19 Rule 3.8.2 table into `CHANNELS` (who may subscribe -> `auth`, producer, cadence). `me.connections` cadence is at most once per `ui_connections_refresh_ticks` (30); `book`/`tape` limited by `max_book_subs` per socket; total by `max_subscriptions_per_socket`. Patterns use `{param}` segments matching `[A-Za-z0-9_:-]{1,64}`.
2. Channel bodies: owner modules (via 17.B and their own cards) register body schemas with `registerChannelBody`; this task registers the platform bodies: `clock {tick, phase, startMs, nextSealMs, worldStatus}`, `status {worldStatus, maintenance: {startUtcMs, endUtcMs}[], versionNotice?}`, and the platform part of `me` (`intentResults: IntentResult[]` of 19 §2.3, `alerts: {code, params}[]`). All objects strict.
3. Allowlist: `allowlist.json` maps `family/view` to the exact list of leaf field paths allowed. 19#27 check (`PROTO-PRIVACY`): (a) for every registered body, `schemaFieldPaths` is a subset of its allowlist entry; (b) no leaf field name of any protocol schema (bodies, intent payloads, server messages) equals a name in `hiddenFieldNames()`, the union of every engine module's `export const HIDDEN_FIELDS: readonly string[]` in `schema.ts` (convention set here for all engine modules: hidden variables, other players' positions, connection-entry mappings of 12, NPC decision parameters, sealed evidence fields). Failure lists family, path and owning module.
4. Generated intent schemas (19 Rule 3.9.2): engine handler schemas must use only the subset the converter supports (strict objects, bounded strings, decimal-string money via `MoneyStr` pattern, integers with bounds, enums, bounded arrays, discriminated unions); `gen-intent-schemas` fails on any other construct. The generated JSON is committed; a test regenerates it and compares (stale file fails). Unknown fields are rejected (strict).
5. Spec doc-sync: `extractSpecIntents('docs/spec')` reads files `00`..`21`, finds each `## §4` section ("Player intents"; for 13 its §4 equivalent heading containing "intents"), and collects the backticked kind in the first column of every table row (`` `mkt.order_place` ``), mapping to the file's module number; writes `docs/intents.json` sorted by kind.
6. INV-STR-005 (20 §3.1.8): for every module whose engine folder exists: each player intent kind in `intentKinds()` has exactly one handler across `productionModules()`, that handler's module equals the kind's module, and the kind appears in `docs/intents.json` for that module; every handler kind is registered in protocol; no kind matches `/\.import_sandbox$/` (20 Rule on sandbox progress). `sys.*` and `adm.*` are system inputs (T19B-01) and are checked against `SYSTEM_INPUT_KINDS` instead.
