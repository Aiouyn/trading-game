## Goal
Deliver what the engine already filtered (privacy by serialization, 19 Rule 3.8.3) to the right sockets and nothing else: authorize every `sub` against the channel catalog (Rule 3.8.2) with an answer that never reveals whether an entity exists, route committed deltas from `dl.tick.<tick>` to recipients and public channel subscribers once per tick (coalesced, Rule 3.8.4), keep 720 ticks of `me` deltas per recipient for resume and the latest snapshot of each public channel (Rule 3.8.9), apply backpressure (Rule 3.8.8), serve the small `req` reads over the socket (Rule 3.8.5) through a world view service, and revoke subscriptions when rights change (19 §8 edge 17).

## Implementation steps
1. `sub` (Rule 3.8.2): rate `max_sub_changes_per_s` (10); total `max_subscriptions_per_socket` (64); `book`/`tape` at most `max_book_subs` (4) per socket. Unknown channel, forbidden channel and nonexistent entity all answer exactly `notice {code: 'CHANNEL_DENIED'}` with no params, after the same constant delay (pad to 20 ms) so timing gives no hint (19#30, E22).
2. Authorization per `ChannelAuth`: OWN_CHARACTER for `me*`, `rank`, `onboarding` (the session's character only); ALLIANCE_MEMBER, LEAGUE_MEMBER, CHAT_MEMBER, OWNER_OR_ROLE (`inst:`), OWN_LISTS_OR_PUBLIC (`ticker`), LICENSE_TIER (`book`/`tape`, 06 license visibility), PUBLIC_OR_PARTY (`fund`, `company`: full view for owner, manager, investors or authorized roles, else public view). Facts come from read models (Valkey caches maintained by the projector) and the session; until a producer module exists its facts answer false (deny by default).
3. Rights changes (§8 edge 17): the projector publishes rights-change notices on Valkey channel `rights`; `recheck` closes affected subscriptions with `notice CHANNEL_REVOKED` in the same tick.
4. Delta router (`dl.tick.<tick>` consumer): recipient deltas are written to the resume stream and forwarded to the gateways holding a socket of that character (`rcpt:<chrId>` set maintained by gateways on hello/close); a recipient without a socket only gets the resume buffer (§8 edge 16: expires after 720 ticks). Public deltas are produced once per tick, applied to the stored public snapshot and fanned out once (`dl.pub`). One frame per channel per tick: all ops of a tick for a channel are coalesced in order.
5. Resume (Rule 3.8.9): on `hello` with `lastSeen.me >= currentTick − resume_buffer_ticks` (720), replay `me` from the buffer with no gap (strictly after lastSeen); otherwise, and for every other channel, a fresh `snap`. `me` snapshots come from the character's PLAYER partition via `viewClient`; public snapshots from Valkey `ps:<channel>`.
6. Backpressure (Rule 3.8.8): socket buffered bytes > `ws_soft_buffer_bytes` (1 MiB): stop public deltas, mark stale; `me` continues; when drained, a fresh `snap` per stale channel; > `ws_hard_buffer_bytes` (4 MiB): `bye SLOW_CONSUMER`. Other sockets unaffected (per-socket state only).
7. `req` (Rule 3.8.5): `max_req_per_s` (10) per socket; `intent.preview` additionally `max_preview_per_tick` (5); each op maps to one view of the owning partition (`queryView` on the last committed state); previews never reveal more than the owning module's bands. Unknown op or bad args -> `res {ok: false, err: 'BAD_REQUEST'}`.
8. Partition ids never appear in any client payload (E23): the view service resolves partitions server side.

## Test plan
`delivery.test.ts` (gateway + router + memory bus + Valkey double, fixture view handlers):
- `19#30 subscribing to another character's me, an alliance the character is not in, or an inst: channel without a role returns CHANNEL_DENIED and no data; the error is identical whether or not the entity exists`: four cases (other `me`, foreign alliance existing, alliance id that does not exist, `inst:` without role): each yields exactly one frame `notice {code: 'CHANNEL_DENIED'}`, byte-identical, and no `snap`/`delta`; response times within 5 ms of each other.
- `19#32 reconnecting after 600 ticks resumes me from the buffer with no gap; after 800 ticks the client receives a snapshot`: client sees tick 1,000 then disconnects; router writes `me` deltas for ticks 1,001..1,600; reconnect at 1,600 with lastSeen.me = 1,000 -> mode BUFFER with deltas 1,001..1,600 contiguous and applying them to the old state equals the current snapshot; disconnect at 2,000 and reconnect at 2,800 -> SNAPSHOT.
- `19#33 a slow consumer above 1 MiB buffer stops receiving public deltas and keeps me; above 4 MiB it is closed with SLOW_CONSUMER; other sockets on the gateway are unaffected`: simulated socket with a non-draining buffer: at 1.1 MiB public deltas stop and `me` still flows; after drain a fresh snap arrives for each public channel; at 4.1 MiB `bye SLOW_CONSUMER`; a second socket subscribed to the same channels receives every tick.
- rights change: leaving an alliance -> `notice CHANNEL_REVOKED` within the tick.
- req limits: 11th request in a second -> `res ok false RATE_LIMITED`; 6th preview in a tick refused.
`deltas.test.ts`: `applyOps` worked examples: `{a:{b:1}}` + set `/a/c` 2 -> `{a:{b:1,c:2}}`; ins `/list` idx 0 into `[1]` -> `[x,1]`; trim keepLast 2 of `[1,2,3]` -> `[2,3]`; del of a missing path throws DeltaPathError.
