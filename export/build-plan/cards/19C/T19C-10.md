## Goal
Write `packages/sdk`, the official TypeScript client of 19 Rule 3.10.3 item 4 (also used by 20's bot swarm with player-level permissions): socket connection with `hello`, resume via `lastSeen`, reconnect with backoff, session signing keys (non-extractable WebCrypto keys, Ed25519 with ES256 fallback, Rule 3.9.1), per-key nonce management, intent construction with one ULID per user action (19 §8 edges 3-4), typed channel subscriptions with delta application, and the clock offset from ping/pong. Then the web client's dedicated Web Worker (Rule 3.17.1) that owns the WebSocket through the SDK, decodes MessagePack, keeps normalized channel state and posts compact change sets to the main thread.

## Imports
- T19A-02: `ClientMsg`, `ServerMsg`, `Intent`, `signingBytes`, `canonDecode`, `canonEncode`, `PROTO_VERSION`. T19C-01: `CHANNELS`, `parseChannel`. T19C-05: `applyOps` (copied into the sdk build as a pure dependency of `@tycoon/platform/deltas/apply-ops`; the sdk may import that file only).
- T19C-03/T19C-07: HTTP endpoints `/api/v1/session/ws-ticket`, `/api/v1/session/keys`. T19C-04: frame codes (`bye` codes, `intentAck` statuses).

## Implementation steps
1. Connect: fetch a ticket, open the socket, send `hello {protoVersion, sessionToken, lastSeen, locale, device}`; on `bye UPGRADE_REQUIRED` stop reconnecting and emit `bye`; on close reconnect with backoff 0.5 s doubling to 30 s with jitter from the injected random source; on reconnect send `lastSeen` from `ChannelStore` and resubmit `PendingIntents.resendable()` with their original intentIds (dedupe makes it safe, §8 edges 4-5).
2. Ping every `ws_ping_s` (15); `ClockSync` uses the NTP-style offset `((serverMs − sent) + (serverMs − recv)) / 2` and the median of the last 5 samples (Rule 3.8.1 item 3); used only for the tick-pulse countdown, never for which tick an intent lands in.
3. Signing: generate the key pair with `extractable: false`; register the public key; sign `signingBytes(intent)`; base64url signature. Nonces strictly increasing and saved before sending (IndexedDB in the browser via the injected store; a file or memory store for bots).
4. Intents: `newIntentId` once per user action; `clientTick` = the tick the client believes is next (from the last `tick` message + 1); the client shows "pending tick N" until the result (no prediction, Rule 3.17.2).
5. Channels: `snap` replaces state; `delta` with `seq === current + 1` applies with `applyOps`; a gap returns `GAP`, the client resubscribes for a fresh `snap`; `stale` set when the gateway signals backpressure (fresh snap follows).
6. Worker (Rule 3.17.1): owns the `TycoonClient`; frames are binary MessagePack in production (JSON only with `ws_json_frames` in dev); it coalesces all channel changes of a tick into one `changes` message to the main thread (compact patches, no full bodies after the first snap); the main thread never opens a socket for game traffic (Rule 3.2.2).

## Test plan
`sdk.test.ts` (in-process gateway double speaking the protocol):
- connect, subscribe `clock`, receive snap then 10 deltas; `lastSeen` reflects the last tick; reconnect sends lastSeen and resends one pending intent with the same intentId; the double answers DUPLICATE with the original sealTick and the pending state becomes SEALED.
- nonce manager never repeats across a simulated restart (persisted value).
- signature produced by the sdk verifies with T19C-03's `verifyIntentSignature` for both algs.
- ClockSync worked example: samples (sent 1,000, server 1,560, recv 1,100) -> offset ((1,560 − 1,000) + (1,560 − 1,100)) / 2 = 510; with five samples [510, 500, 530, 490, 505] median 505.
- gap detection: delta seq 5 after 3 -> GAP and a resubscribe is sent.
`worker.test.ts` (worker logic run in a test harness without a real Worker): one `changes` message per tick containing all channels changed in it; `submit` from main produces an `ack` message.
