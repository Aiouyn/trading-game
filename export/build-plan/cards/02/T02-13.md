## Goal
Make time and causality exact: boundary hooks run in P2 of the boundary tick in the order 02 §3.4 prescribes (end hooks innermost first, start hooks outermost first, module order, then the module's own entity order), the core boundary events are emitted, every consequence discovered in tick N lands as an input of tick N+1 before any intent of N+1 (02 §3.5.4), all `core.*` event kinds have zod schemas (02 §5), and client deltas pass a recipient filter so no PRIVATE/PARTIES/SEALED fact reaches anyone outside its parties (INV-ENG-005, L11). INV-ENG-007 checks the tick number and boundary firing.

## Implementation steps
1. `hookPlan`: boundaries present at the tick; end hooks first in END_HOOK_ORDER (DAY_CLOSE, WEEK_CLOSE, MONTH_CLOSE, QUARTER_CLOSE, YEAR_CLOSE, CHAPTER_CLOSE: innermost first) then start hooks in START_HOOK_ORDER (CHAPTER_OPEN, YEAR_OPEN, QUARTER_OPEN, MONTH_OPEN, WEEK_OPEN, DAY_OPEN, HOUR: outermost first), then PHASE_CHANGE; within a boundary, modules in module-number order (03, 04, 05, …; core '02' first). Entities in sorted id order is the module's own loop (document in JSDoc: modules must iterate `store.iter` which is sorted). Hooks run in P2 after P0/P1 (02 §3.4) on the partition that owns the module's state (T02-14 routes; single partition here).
2. Core's own boundary work (module '02' hooks, implemented here as functions T02-21 registers): PHASE_CHANGE -> `core.phase.changed` {phase, productFamiliesOpen} PUBLIC; DAY_OPEN with holidays -> `core.holiday` {holidayId, blocs} PUBLIC per holiday; every *_OPEN/*_CLOSE of week/month/quarter/year/chapter -> `core.period.boundary` {period, edge, index} PUBLIC; CHAPTER_OPEN -> `core.epoch.rotated` {epoch, publicRootCommit, revealedEpoch?} PUBLIC; DAY_CLOSE commit -> `core.day.closed` {dayIndex, gameDate canonical string} emitted in P14 after commit; every commit -> `core.tick.committed` {tick, worldHash, intentsRoot, mode} PUBLIC (worldHash is known after P13; emit in P14 with seq after all phase events).
3. Consequences: `ctx.send(to, kind, body, 'NEXT')` messages are collected after P12, sorted by canonicalKey, and written to T_INBOX (`inbox_<N+1>`) as part of tick N's state (so they are hashed and survive a crash). At tick N+1, R1 starts by delivering them: phase handlers read them via `ctx.inbox(kind)` in the phase named by the consequence (`PhaseMessage.phase` = executedIn), and SYSTEM consequence intents (liquidations, contract payments, freezes) are prepended to P1 processing BEFORE any intent of N+1, in canonicalKey order, bypassing rate limits (02 §3.5.4 table). After delivery the inbox row is deleted. `CONSEQUENCE_KINDS` lists the 8 rows of the table (liquidation order P7->P1, default-waterfall step P7->P7, bank-run wave P8->P8, hidden session opened P10->P10, freeze/Held start P11->P1, contract scheduled payment P12->P1, corporate action effective P2->P2, news publication P3->delivered at P14).
4. B1/B2/B3 messages in single-partition mode are delivered to the target phase within the same tick (T02-14 implements barriers); here they go into the inbox of the next phase in the same runtime.
5. Delta filter (INV-ENG-005, L11): each ClientDelta carries `sourceVisibility` and `partyIds`. Rules: PUBLIC -> any recipient incl. `pub:*`; OWNER -> recipient must equal the single owner id; PARTIES/PRIVATE -> recipient ∈ partyIds and never a `pub:` channel; SEALED events never produce deltas. A delta violating its rule is dropped and recorded in the audit fact; INV-ENG-005 fails when the audit is non-empty (TICK, FATAL: the tick does not commit, so the leaking code is found by safe mode). Events with PARTIES/PRIVATE visibility get `partyIds` defaulting to subjectIds when omitted.
6. INV-ENG-007 (TICK, FATAL): post T_WORLD.tick === pre T_WORLD.tick + 1 (genesis: pre absent and tick 0); `FACT_HOOKS_FIRED` equals `hookPlan(calendarOf(tick))` exactly (no boundary skipped or doubled, 20 §8 edge 1).
7. Edit `PartitionRuntime.runTick` to call these at the right places; nothing else changes.
