## Goal
Turn raw intents received for tick N into the fair-ordered, sealed list every module processes (02 §3.12): stateless P0 checks with stable reject codes (`REJECT_REPLAY`, `REJECT_STALE`, `REJECT_RATE_LIMIT`, `REJECT_SCHEMA`, `REJECT_SIGNATURE`), the rate limits ruled by 24 R07 (20 per character across its own channels, 20 per operator under a Mandate, at most 100 combined), the fair `orderKey`, the per-actor nonce-run placement, the intents Merkle root, and the gateway batch assembly with the seal-grace roll-over. The pipeline (T02-12) calls this in P0.

## Implementation steps
1. `checkEnvelopes` then `sealTick`, order of operations (02 §3.12):
   a. schema: `knownKinds(kind)` and `schemaOk(kind, payload)` else REJECT_SCHEMA; `signatureValid === false` (gateway verified, recorded in the batch) else REJECT_SIGNATURE; SYSTEM/NPC/ADMIN channel intents skip nonce and signature checks (02 §6.1: NPC intents have no signature or nonce).
   b. staleness: `clientTick < tick − maxAgeTicks` (DEFAULT 3) -> REJECT_STALE (R29: applies under every tick policy).
   c. replay: per actor, nonce must be > `nonces.last(actor)` and strictly increasing within the batch after sorting that actor's intents by nonce; duplicates or non-increasing -> REJECT_REPLAY (the first occurrence wins; same intentId twice -> second REJECT_REPLAY).
   d. rate limits (`applyRateLimits`): see step 3. Excess -> REJECT_RATE_LIMIT.
   e. (end of `checkEnvelopes`) intentsRoot = merkleRoot(canonEncode of each accepted intent sorted by intentId). It must be order-free because TickEntropy(N) mixes intentsRoot (02 §3.11.2) while the fair order depends on TickEntropy (02 §3.12 rule 3); 02 §2.5's "fair-ordered" wording is resolved this way (owner module's own circularity; reported). Receipts prove inclusion against this root. nextNonces = max accepted nonce per actor.
   f. `sealTick` (stage B): orderKey for each accepted intent, then `fairOrder`.
2. `fairOrder`: group by actorId; each group sorted by nonce; group position key = the minimum orderKey of the group; groups sorted by position key (cmpStr on hex), ties impossible (distinct intentIds) but break by actorId; output groups consecutively (02 §3.12 rule 3). Gateway receipt order (`receivedSeq`) is never used.
3. `applyRateLimits` (R07, keeping the lowest nonces): principal = onBehalfOf ?? actorId. For each actor: own intents (actorId === principal, channels UI/API) keep the 20 lowest nonces; an operator (actorId !== principal, channels AI/MANAGER under a mandate) keeps its 20 lowest; then per principal, if the kept total > 100, keep the character's own first, then operators in ascending actorId order (cmpStr) until 100. SYSTEM/NPC/ADMIN intents are not rate limited (consequences bypass limits, 02 §3.5.4 table: liquidation orders channel SYSTEM). Liquidation SYSTEM intents also bypass.
4. `assembleTickBatch`: batches with `forTick === tick` and `closedAtMs ≤ sealedAtMs + graceMs` are taken; a late batch is returned in `rolledToNext` whole (its forTick becomes tick+1 by the caller) and its gateway id listed in `lateGateways` (telemetry `core.gateway.late`, T02-13). Intake order of `intake` is irrelevant (fair order is applied later), but make it canonical (sort by intentId) so hashing never sees gateway order.
5. Exploit counters (02 §9): sniping and latency (sealed batches and orderKey from unknown entropy), replay (nonce + intentId + max age), flooding (rate limits).
