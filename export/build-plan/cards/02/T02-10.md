## Goal
Serialize a partition's committed state into canonical, hash-verified chunks and load it back bit-exactly (02 §3.16.2), choose which snapshots are taken and kept (02 §3.16.1 cadence and retention), and refuse any snapshot whose recomputed `stateHash` differs from its `TickRecord` so the previous one is used (02 AT 33). Compression (zstd) and object storage belong to the world host (19.B): this task produces uncompressed canonical bytes and the manifest, pure and deterministic.

## Implementation steps
1. Chunks: one per (module, table) named `<module>/<table>` with rows in id order (iter order), plus `core/rng` (streams sorted by key; Uint32Array state as 4 numbers, draws as bigint), plus `core/meta` (header pointers, nonce book is a normal table so it is already a chunk). A chunk whose encoding exceeds MAX_CHUNK_BYTES is split into `<name>#0`, `#1`, … at row boundaries.
2. Floats are encoded by the canonical encoder as 8-byte float64 (02 §3.7.2 rule 5); bigints as extension type 1: provided by `canonEncode`; do not post-process.
3. `stateHash` and `logicalStateHash` in the manifest are the store's hashes at encode time (hex). Chunk sha256 over the uncompressed bytes.
4. `decodeSnapshot`: check engineVersion (SNAP_VERSION unless equal; migrations are T02-18's job), every chunk hash (SNAP_CHUNK_HASH), rebuild a PartitionStore by `asSystem`-free internal loading (add an internal `loadCommitted(table, rows)` method on PartitionStore via a module-private symbol, document it in the report), recompute `stateHash`; mismatch with `expectedStateHash` (the TickRecord value) -> SnapshotRejected('SNAP_STATE_HASH').
5. `selectRestorable`: candidates sorted by tick descending; try each with `recordHash(tick)`; return the first that decodes, listing rejected ones (02 AT 33: "rejected and the previous snapshot is used").
6. Cadence (02 §3.16.1): after commit of a tick with tickOfDay 719 -> DAILY; last tick of a chapter -> CHAPTER as well; `rebalanceAt === tick` -> REBALANCE; `versionCutoverAt - 1 === tick` -> PRE_VERSION; adhoc -> ADHOC.
7. Retention: DAILY rolling `dailyRetentionRealDays` (DEFAULT 30 real days = 720 snapshots) then thinned to one per game week (keep the WEEK_CLOSE day's DAILY) for one real year (365 × 17,280 ticks), then one per chapter; CHAPTER and PRE_VERSION FOREVER; REBALANCE 7 real days; ADHOC 30 real days. `thin` returns which ticks to keep and drop.

## Test plan
snapshot.test.ts:
- round trip: a store with 3 tables (floats incl. -0 normalized, bigints, nested arrays) and 5 RNG streams encodes and decodes to identical stateHash, logicalStateHash and identical next RNG draws.
- `02#33 a snapshot whose recomputed stateHash differs from the TickRecord is rejected and the previous snapshot is used`: three snapshots at ticks 719, 1439, 2159; corrupt one row byte of 2159 and recompute its chunk sha (so only the state hash catches it) -> rejected 'SNAP_STATE_HASH', 1439 chosen; corrupt a chunk without fixing its sha -> 'SNAP_CHUNK_HASH'.
- chunk splitting: a table of 70 MB synthetic rows is split into 2 chunks and still round-trips (mark NIGHTLY if slow).

- tick 719 -> ['DAILY']; tick 967,679 -> ['DAILY','CHAPTER']; versionCutoverAt 5,000 -> PRE_VERSION at 4,999.
- thin over 400 real days of DAILY snapshots keeps the last 720 dailies, one per game week for the rest of the year, one per chapter beyond.
