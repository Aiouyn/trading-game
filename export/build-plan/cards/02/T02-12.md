## Goal
Run one full tick P0..P14 for a world held in one partition (the launch single-process shape; T02-14 adds multiple partitions with identical results): seal intents (T02-08), build each phase's `PhaseCtx`, validate intents in fair order in P1 and apply them in their `applyPhase`, run every module's phase function in module order, prepare postings and holds through the ledger port in P13, run the TICK/PHASE/DAY_CLOSE invariants of the 20.A registry, commit or abort atomically, then sequence events (19 Rule 3.6.4) and flush deltas in P14. This is the heart of `step()` (02 §3.6): pure, synchronous, and fed only by the header, the sealed intents and entropy.

## Implementation steps
1. Core tables are registered by core's ModuleDef '02' (T02-21) but defined here.
2. `runTick` sequence (single partition; partition kinds and barriers come in T02-14, so here R1..R6 collapse into a function sequence):
   - P0: `checkEnvelopes` with `nonces` from T_NONCE, limits from params, `knownKinds` from ModuleSet, `schemaOk` = handler zod `safeParse`; entropy = deriveTickEntropy(worldId, tick, eN, intentsRoot, prevWorldHash); then `sealTick(accepted, tick, entropy)` gives the fair order; header.intentsRoot = the order-free root. Envelope rejects become IntentResults REJECTED and `core.intent.rejected` PRIVATE events (payload {intentId, code, module:'02'}, partyIds [actorId]).
   - Begin tick: store.beginTick, rng.beginTick(tick, epoch = chapter of tick, entropy.words), new IdFactory, MoneyProvenance begin.
   - Inbox: NEXT messages stored in T_INBOX for this tick are delivered first (T02-13 implements consequence routing; here `inbox()` reads them).
   - P1: for each sealed intent in fair order: skip quarantined (T02-16); handler.validate(vctx, i); reject -> REJECTED result + `core.intent.rejected` event with the module code; accepted -> if applyPhase === 'P1' apply now, else queue by applyPhase.
   - P2: boundary hooks (T02-13 fills ordering; here call `boundaries[b]` for b in calendar order END_HOOK_ORDER then START_HOOK_ORDER, module order).
   - P3..P12: at the start of each phase run queued `apply()` for that phase in fair order, then each module's `phases[P]` in module order (module number then unit id). NPC intents: messages of kind NPC_INTENT_KIND sent in P3/P4 are validated and applied inline at the end of P4 in orderKey order (orderKey from entropy and the new intent id).
   - PHASE invariants: after each phase, `runInvariants(registry,'PHASE',ctx,phase)`.
   - P13: `ledger.prepare(tick)` (if a ledger provider exists), TICK invariants, and DAY_CLOSE invariants when tickOfDay === 719; facts supplied: rng ledger and counter deltas, id log and written ids, store violations, read stamps, events so far, deltas so far (T02-13), telemetry durations (T02-16). Any FATAL failure (or any thrown error converted by T02-16) -> committed false. ALERT failures are reported but do not block commit.
   - P14 (only when committed): sequence events, update T_WORLD (tick, lastWorldHash), T_NONCE (nextNonces): NOTE these core writes happen before the stateHash is computed; order: core writes, then stateHash, then events/deltas packaged. Deltas flushed via T02-13's filter.
3. `PhaseCtx` construction (`phase-ctx.ts`): `store` = store.bind({module, phase}); `rng(key)` = rng.stream(module, def.streams, key); `newId` from IdFactory (records written ids); `ledger`/`holds` = ledger.apiFor(module, phase, tick) or throwing proxies (EngineFault 'I0.no_ledger'); `emit` collects with (phase, origin = subjectIds[0] ?? 'mod:'+module, pseq); `send` collects messages with canonicalKey = `${toEntity}|${kind}|${fromEntity}|${localSeq}` (19 §2.6); `fail` records a failure attributed to (module, phase, current entity/intent); `delta` collects ClientDelta. `ValidateCtx` omits emit/send/delta (type and runtime).
4. Event sequencing (19 Rule 3.6.4): order by (phase index, origin cmpStr, pseq) and assign seq 0..n−1. INV-ENG-004 (TICK, FATAL) checks density and that the order equals that sort (negative test: a crafted event list with a gap).
5. Postings never commit before P13 (02 §3.5.2): the ledger port is only committed in `commit()`. Balances read in P1–P12 are committed balances minus holds (03 implements; nothing here).
6. Budgets: measured with the injected clock only for telemetry (`durationsMs`, never hashed, never aborting, 02 §3.5.1 rule 1); `DESIGN_BUDGET_MS` sum asserted to be 2,500 in a unit test (the load-test half of 02 AT 40 is in 20B).
7. Determinism: no Date; iteration only over sorted structures; all outputs canonical.
