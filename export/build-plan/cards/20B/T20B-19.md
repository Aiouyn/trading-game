## Goal
Implement the performance gates of 20 §3.14 against a staging world on production-equivalent hosts: the synthetic load driver (Rule 3.14.1) that opens real WebSocket sessions through the gateway, each behaving like a POP_BASELINE agent at 1.5× the real intent rate and subscribing to the channels a client of that archetype uses, at the LAUNCH profile (5,000 CCU, 25,000 agents including player AIs) and the TARGET profile (100,000 CCU), with pass criteria over 72 real hours (zero missed ticks, tick commit p99 ≤ `tm_tick_p99_ms` 2,500 ms and p99.9 ≤ 4,000 ms, delta delivery p99 ≤ 800 ms after commit, zero ledger and shadow mismatch, invariant cost ≤ 10% of P13); the chaos gate (Rule 3.14.2); the rolling deploy drill (Rule 3.14.3); and the restore drill used by G4. It also carries 02 AT 40 (phase design budgets sum to 2,500 ms; launch load p99 tick work < 2,500 ms; no tick over 5,000 ms except chapter-end ticks), which needs the whole game under load.

## Implementation steps
1. Sessions log in through the normal auth flow, create characters, subscribe to the archetype's channels and submit intents at 1.5× the POP_BASELINE real rate; player AIs run inside the world (11). Measurement uses commit timestamps from TickRecords (telemetry fields), delta delivery timestamps at the client, invariant timing facts and P13 durations.
2. Pass criteria per profile over 72 real hours exactly as Rule 3.14.1; the 02 AT 40 checks are evaluated on the LAUNCH run: Σ DESIGN_BUDGET_MS = 2,500; p99 of tick work (P0-P14 compute, excluding barrier waits) < 2,500 ms; every tick with commit > 5,000 ms is a chapter-end tick.
3. Chaos (each under LAUNCH load): kill a PLAYER partition process (recovery from snapshot + replay ≤ 60 s, the world waits at the tick boundary, zero divergence after recovery); kill the active coordinator (standby within 3 missed heartbeats, zero double-sealed ticks); partition the bus 10 s (pause, resume, zero divergence); kill a gateway (clients reconnect and receive missed `me` deltas); restart the PostgreSQL primary (failover, no intent lost since intents are in JetStream). Each passes with zero invariant failures and zero shadow mismatch.
4. Deploy drill: roll partitions one at a time between ticks; zero missed ticks. Restore drill: recover a full partition set in staging from snapshot + log and compare state hashes.
5. `infra/staging/load-gate.yaml` declares the staging topology and the G4 job that runs load, chaos, deploy and restore drills.
