## Goal
Provide the harness host of 20 Rule 3.5.1: `buildHarnessWorld(spec)` turns a `HarnessWorldSpec` (T20A-04) into a runnable `HeadlessWorldDriver` over the production engine bundle (every unit's ModuleDef through 19.B's PartitionEngine factory) with no wall clock (the next tick runs as soon as the previous commits), drives test agents strictly as players (Rule 3.5.2: characters created through the normal character flow, intents through the same envelope checks, P1 validation, rate limits and license gates, observations only through the views and channels that character's client could use), runs probes that read full state without ever feeding agents (Rule 3.5.2 last paragraph), expands the population templates of Rule 3.5.4, forks MIRROR worlds from a DAILY snapshot through a pseudonymizer (Rule 3.5.7), keeps harness randomness on its own streams (`tm:agentparams`, `tm:partitionmap`, `sim.bot`), never touches production (Rules 3.5.1, 3.5.8), and writes run outputs to the result sinks (`tm_runs`, `tm_band_results`, `tm_findings`).

## Implementation steps
1. `buildHarnessWorld`: reject seed sets other than DEV, VALIDATION, WITHHELD, REGRESSION (SeedSetError SEED_NOT_ENTITLED); derive the seed; build GenesisConfig from the preset with harness epoch roots (local seed, 02 §3.21 (b)); partitions from the spec (1, 4, 16 standard maps or a random map from `tm:partitionmap`); apply `paramOverrides`; fast-forward `startWorldAgeDays` with NPC-only ticks; the driver advances without waiting for wall time. The process refuses to start when any production connection string is present in its environment (Rule 3.5.1).
2. Agents: for each population entry create an account and a character through `acct.register` (the normal flow), then the policy runs every `cadenceTicks` with an `AgentApi` bound to that character. `submit` builds a RawIntent with the next nonce, channel 'API', and enters the same intake as a gateway batch (`checkEnvelopes`, `applyRateLimits` with 20 per character and per principal, combined cap 100, 24 R07), then P1 validation in the pipeline. AI DU caps (2,000 per player per tick) are enforced by 11 inside the pipeline; the driver only measures them.
3. Observation isolation: `view` uses a ViewerContext of the agent's character (19's queryView semantics); `inbox` returns only deltas of channels the character may subscribe to (19.C channel table); nothing in AgentApi exposes Store, RNG streams other than the agent's own `sim.bot:<agentId>`, seeds, entropy or other agents. Ring agents (A16-A18) get `ringChannel`; everyone else coordinates only through game intents and the harness chat channel.
4. Probes read the full store and run outputs; their results go to metrics and oracles only, never into AgentApi during a run (enforced by construction: AgentApi holds no reference to the world object).
5. Populations: templates exactly as Rule 3.5.4; POP_CONFLICT replaces A01 and A14 proportionally; POP_EXPLOIT adds 5% hunters; POP_LATE uses COHORTS join schedule at days 365, 395, 425; counts scale from per-1,000 with largest remainder (`allocate`).
6. Mirror: requires TM_ENGINEER (21 §3.1), writes an access log row, pseudonymizes, drops chat, sets deletion at now + `tm_mirror_retention_days` (14) real days; existing characters run a scripted "hold and accrue" policy; test agents act only on characters created for the run.
7. Sinks: rows mirror the 20A types; ClickHouse in CI, memory in tests.
