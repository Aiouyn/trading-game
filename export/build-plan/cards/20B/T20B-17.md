## Goal
Implement 20 §3.11: the shadow verifier (Rule 3.11.1) that follows the production world from the latest DAILY snapshot, consumes sealed IntentBatches and entropy reveals from the bus only after they are public, re-executes every tick with 4 partitions (or 1 when production runs 4), compares `logicalStateHash`, `eventDigest` and `postingDigest` with the production TickRecord, tracks lag against `tm_shadow_max_lag_ticks` (720; above 2× pages INC-3), on a mismatch halts itself (production continues), files a CRITICAL RegressionCase with both TickRecords, emits `tm.shadow.mismatch` and starts the hotfix investigation, and resolves ties with a second verifier on the other CPU architecture; the G4 canary that runs a candidate engine against live batches for `tm_canary_ticks`; the launch live monitors compared with their bands (Rule 3.11.2, a breach for `tm_live_band_breach_days` game days in a row opens an `E6_LIVE` Finding); and the live exposure job that runs a finding's signature over the production event store (Rule 3.11.3). Also the recovery path of 20 §8 edge 5 (reload DAILY snapshot after a gap, nightly OFFLINE replay of the skipped range).

## Implementation steps
1. Startup: load the latest DAILY snapshot, build a world with `chooseVerifierPartitions(production)` partitions, then for each next sealed batch wait for its public reveal (the verifier never holds the live seed, so lag ≥ reveal delay), run `stepWorld`, compare the three digests with the production record. Lag = production tick − last verified; > `tm_shadow_max_lag_ticks` reported via `tm.shadow.lag`, > 2× pages INC-3.
2. Mismatch: stop (state HALTED), production continues; file a CRITICAL RegressionCase (source SHADOW) with both TickRecords and the first-divergence report; emit `tm.shadow.mismatch` within the same tick of reaching it; create an INC-1 through 21. With `tm_shadow_verifiers` ≥ 2 the second verifier (other architecture) re-runs the tick: agreeing with production -> first host suspect; agreeing with the first verifier -> production suspect, staff decide on a halt (21 §3.3).
3. Gap recovery (20 §8 edge 5): when lag exceeds one game day after a snapshot gap, reload the latest DAILY snapshot and continue; the skipped range is queued for a nightly OFFLINE replay job so no tick stays unverified for more than 2 real days.
4. Canary: the candidate engine re-executes live batches for `tm_canary_ticks` (720) ticks; any divergence not declared intended (field and effective tick) fails G4.
5. Monitors: money minted vs destroyed per tick by reason code; top 20 wealth deltas per game day with cause breakdown; P2P flow graph anomalies; contract defaults; flagged accounts; tick timing per phase; ops per hour by type; breach and detection rates by tier band; case outcomes vs ledger truth; dogpile-cap hits; heat-shield activations; protection-window early exits; top 20 attacker-victim pairs; ad grants per hour; fresh starts per hour; quarantined intents per hour (projector consumers); each compared with its band; `tm_live_band_breach_days` (3) consecutive game days outside the band opens a Finding tagged E6_LIVE.
6. Exposure: CRITICAL and HIGH findings run `liveExposure` within one real hour and hand suspects to 21 (no punishment on a pattern match alone).
