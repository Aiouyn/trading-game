## Goal
Create the engine side of module 19 (`packages/engine/sys`, unit folder `sys` of T19A-04): every system input of 19 §4.3 is validated at P1 like a player intent (the engine never trusts the submitting service) and applied with the effect the table names. This part covers the inputs that need only 02 and 03: presence, load scale, partition map, param, content and engine changes, entropy commit and reveal, world and market halts, scheduled world events, manual snapshots, and the security-change hold of 19 Rule 3.9.3 item 5. It emits the platform events of 19 §5 that the engine owns. (Account status, freeze, deletion, profile, guest upgrade, wall-clock mark and ad grant follow in T19C-06; compensation and clawback in T19B-14.)

## Implementation steps
1. Plumbing: T19B-02's `beginTick` converts every system input with `systemInputToSealed` and passes them first in the COORD partition's P1 list. Every handler's `validate` first checks the input's approvals count against `SYSTEM_INPUT_APPROVALS[kind]` with distinct admin ids (reject `SYS_APPROVALS`) and the payload against the strict schema (`SYS_SCHEMA`). The source-key check already happened at sealing (T19B-06); the engine re-checks the recorded `signatureValid` flag (reject `SYS_SIGNATURE`).
2. Per kind, validation at P1 and effect (19 §4.3):
   - `sys.presence`: send `{present}` to the character's home with `when: 'NEXT'`; the sys phase hook at P1 of N+1 on PLAYER writes `T_PRESENCE` (sinceTick = N+1). No event, ever (19 §5, E12). Read by 12 and 15 through view `sys.presence_of` restricted to the owning modules' phases (not a client view).
   - `sys.load_scale` (a broadcast kind, T19B-02 `BROADCAST_SYSTEM_KINDS`: every partition receives it in its own P1 list): `duScale` in (0, 1]; the named partition writes its `T_LOAD` row at P1 of the same tick, so P5 of that tick uses it (19 Rule 3.11.5 'the current sys.load_scale input'); COORD emits `sys.load_scaled {partitionScope: 'world', duScale}` PUBLIC (E23).
   - `sys.partition_map`: valid only when N is a snapshot boundary (`tickOfDay(N) === 719`) and `effectiveTick === N + 1`; record in `T_PENDING` kind MAP; the host applies it after P14 of N (T19D-01). Reject `SYS_NOT_BOUNDARY`.
   - `sys.engine_upgrade`: boundary tick (`tickOfDay(effectiveTick) === 0`), 2 approvals, semver greater than the current; record kind ENGINE; the host converts it to 02's `adm.version.cutover` directive (T02-18 validates the CI report); `sys.engine_upgraded {engineVersion, effectiveTick, patchNotesKey}` is emitted at the effective tick.
   - `sys.param_change`: 2 approvals; every change passes `validateParamChange` of 23 (range, live, step, frequency; reject with the 23 code); `effectiveTick` default next day close; record kind PARAM; the host schedules 02's PARAM_CUTOVER; `sys.param_changed {paramsVersion, changedKeys}` PUBLIC at the effective tick (19 Rule 3.16.2; §8 edge 12: applies by tick number, so a safe-mode replay uses the same paramsVersion).
   - `sys.content_change`: 2 approvals; effective at a daily boundary (T02-18 `contentVersionAllowedAt`); `sys.content_changed {contentVersion}`.
   - `sys.entropy_commit`: epoch = epochOf(N) + 2 and no row yet (reject `SYS_ENTROPY_EPOCH`); write `T_ENTROPY`; emit `sys.entropy_committed {epoch, commitment}`. `sys.entropy_reveal`: `SHA-256("tycoon-entropy" ‖ u64be(epoch) ‖ secret) === commitment` (reject `SYS_ENTROPY_MISMATCH`) and N >= end of epoch + `entropy_reveal_lag_ticks` − 1 (reject `SYS_ENTROPY_EARLY`); emit `sys.entropy_revealed`.
   - `sys.account_security {characterId, holdUntilTick}`: holdUntilTick >= N; send to the character's home (NEXT); write `T_SECURITY_HOLD` (max of existing and new). `guardValueRemoval` is exported for the P1 validators of the modules that move value to other parties. Modules built before 19.B (03, 14.A, 13.A) cannot import it (G6.1): they declare a port `SecurityHoldPort { guardValueRemoval(store, chrId, tick): Reject | null }` and this module exports the implementation as `providesPorts: { SecurityHoldPort: ... }`; modules built after 19.B (15.A and later) import `guardValueRemoval` directly.
   - `adm.halt_world` / `adm.resume_world`: 2 approvals, then 02's `validateDirective` for `adm.halt` / `adm.resume` (status preconditions); effect via 02's directive (T02-18) and the host's scheduler (T19B-10); emit `sys.world_status {status, reasonKey}` PUBLIC.
   - `adm.halt_market` / `adm.resume_market`: 1 approval (emergency) sets `confirmByUtcMs = wallclock + 3,600,000` using the last `sys.wallclock_mark` (R26; the engine's only wall clock); a second approval (a later input with the same target) confirms; when a wall-clock mark passes `confirmByUtcMs` unconfirmed, the halt is lifted automatically (auto-resume). 05 reads `sys.market_halts`.
   - `adm.inject_event` / `adm.cancel_event`: 2 approvals; tick > N; write/cancel `T_SCHEDULED`; 16 and 21 consume the view. `adm.snapshot`: 1 approval; write `T_SNAPREQ` (host writes a MANUAL snapshot after the commit).
   - Every accepted `adm.*` input also emits `adm.action {kind, reasonKey, ticketId}` PRIVATE to the affected character when one exists (no staff identity).
3. No `adm.*` kind here can create money, change odds, ranks or Prestige, or read sealed evidence (19 §4.3 last paragraph): none of these handlers calls the ledger.
4. Determinism: wall-clock values come only from recorded `sys.wallclock_mark` inputs.

## Test plan

- schema and approvals: `adm.halt_world` with one approval -> `SYS_APPROVALS`; with two distinct -> accepted and `sys.world_status` emitted.

- entropy: commit for epoch current+1 -> SYS_ENTROPY_EPOCH; reveal with wrong secret -> SYS_ENTROPY_MISMATCH; correct after the lag -> `sys.entropy_revealed`.
- presence produces no event and is written on the home partition at N+1.
- halt_market with one approval auto-resumes when a wall-clock mark 61 real minutes later arrives; with a confirming second approval it stays halted.

- `19#62 after an email or MFA change, P2P transfers and value removal are rejected for 24 real hours with the hold's reject code; trading inside the character's own accounts still works`: `sys.account_security {characterId, holdUntilTick: N + 17,280}` (`holdUntilTickFor(N)` with 24 hours x 720); a fixture P2P transfer intent whose validator calls `guardValueRemoval` is rejected with `SYS_SECURITY_HOLD` at N+1 and at N+17,279, accepted at N+17,280; a fixture own-account trade intent is accepted throughout.
