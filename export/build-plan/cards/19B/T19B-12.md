## Goal
Keep the world correct and quickly running through process loss (19 Rules 3.2.3, 3.7.4, 3.7.5): a failed partition is rebuilt on a standby worker from its latest snapshot plus the recorded inbound messages of the `PHASE` stream, checked hash by hash against the TickRecords, while the rest of the world waits at the tick boundary; when PHASE data is missing the whole world is rebuilt from batches; the coordinator runs under a PostgreSQL lease whose epoch is the fencing token, a warm standby follows batches and records and takes over after three missed heartbeats, re-executing the identical durable batch of any tick that never committed.

## Implementation steps
1. Partition failure (19 Rule 3.7.4): when the pool or the driver reports a failure (heartbeats `partition_failover_missed_heartbeats` x 500 ms, exit, hard timeout), the coordinator `abortAll` for the open tick, marks the partition RECOVERING (descriptor status), sets status CATCHING_UP, and calls `recover`. The other partitions wait at the tick boundary (never run ahead).
2. `recover`: spawn a fresh worker, load the latest snapshot of the partition (`SnapshotWriter.latest`, verified by stateHash), then for each committed tick after it up to `uptoTick`: `begin` with `inputsFor` (the coordinator rebuilds the partition's `TickBegin` from the durable batch, the entropy service and the TickRecord header data), feed each recorded delivery point's messages from `readInbound` instead of other partitions' outputs, `prepare`, `commit`, and compare the stateHash with `tick_record.partition_hashes[partitionId]`. Mismatch -> `ReplayMismatch`: halt and case file (19 Rule 3.6.5, §8 edge 10: never accept and continue). Missing PHASE records -> `PhaseDataMissing` -> whole-world recovery.
3. Rejoin: when caught up the worker replaces the failed handle, the aborted tick re-runs for every partition from the same durable batch. Target `partition_rto_s` (60 s); exceeding it alerts.
4. `recoverWorld`: from the last common DAILY snapshot of every partition re-run all partitions from the batches (reference driver over workers), checking every TickRecord; target `world_rto_s` (900 s).
5. Lease (19 Rule 3.2.3): the active coordinator renews every `coord_heartbeat_ms`; `expires_at = now + coord_failover_missed_heartbeats x coord_heartbeat_ms`. A failed renew means the lease is lost: stop sealing and exit. The standby polls `tryAcquire` every heartbeat; it succeeds only after expiry, increasing the epoch (fencing token). 02's `coord_failover_timeout_ms` (3,000) is the budget for the complete takeover (detection, lease, fencing confirmation); exceeding it pages.
6. Fencing confirmation (19 Rule 3.7.5): the TickRecord transaction of T19B-09 calls `assertHeld` so a stale coordinator can no longer commit a record once the epoch moved; partitions reject control messages with a lower token (T19B-07, edge 8). The new coordinator seals only after its lease row is committed.
7. `planTakeover`: last TickRecord tick L; if `batch.<L+1>` is durable on BATCH it is the pending batch: it is re-executed identically (same batchHash, edge 6, 19#21) and the intents acked as sealed for L+1 keep their seal tick; INTAKE is re-read from the intake position recorded with the last durable batch (stored as the BATCH message header `intake-seq`); the dedupe window is rebuilt from the last 17,280 batches.
8. Edge 7 (multi-host: partitions alive elsewhere hold tick L+1 prepared): `remotePrepared` collects their reports; if every partition reports complete with stateHashes whose worldHash matches a re-computation from the batch, write the TickRecord; otherwise order rollback and re-run L+1. In the single-host deployment the partitions died with the host and the follower's state at L is used.
9. Warm standby: `StandbyFollower` runs every committed batch through its own workers (reference order of T19B-02) using the replicated entropy state, verifying each TickRecord's hashes; at takeover it already holds state at L.
