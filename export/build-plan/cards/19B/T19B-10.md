## Goal
Decide when each tick is sealed and how the world reacts to being late, without ever skipping a tick or committing partially: overrun waits (19 Rule 3.3.4), CATCHING_UP after consecutive late ticks, re-basing the real-time anchor when catching up takes too long (as a recorded REANCHOR directive and a `sys.clock_rebased` event), load levers and wall-clock marks entering only as system inputs of the next batch (so replay reproduces them), halts that stop sealing and resumes that re-anchor, and holding the tick while the `BATCH` stream lacks quorum. `world-loop.ts` ties sealer, driver, commit pipeline and scheduler into the coordinator's main loop.

## Implementation steps
1. Seal time (19 Rule 3.3.4 item 1 with 02 §3.19.1; both D389 and D029 are in force and are combined, each module's own constant kept): `nextSealAt = max(scheduled(N), lastCommitMs + gap, lastSealMs + minInterval)` where `gap = min_inter_tick_gap_ms` (200) in RUNNING and `catchup_gap_ms` (200) in CATCHING_UP, and `minInterval = tickMs` in RUNNING and `catchup_min_interval_ms` (2,500) in CATCHING_UP (players always get at least 2.5 s of intake per tick). Processing of N starts only when N is sealed and N−1 committed. Intents for N+1 are collected while N runs.
2. Lateness (rule 3.3.4 item 2): `lateness(N) = commitMs(N) − scheduledCommit(N)`. `lateStreak` counts consecutive ticks with lateness > 0; when it reaches `catchup_trigger_ticks` (3) status becomes CATCHING_UP (`statusChanged`). While CATCHING_UP, `catchupTicks` counts ticks; status returns to RUNNING when lateness <= 0.
3. Re-base (rule 3.3.4 item 3 with 02 §3.19.3): when `lag = now − scheduled(lastCommitted + 1)` exceeds `catchup_max_lag_ms` (300,000) or `catchupTicks` reaches `catchup_max_ticks` (120), emit `reanchor {deltaMs: lag, fromTick: N+1}`: the next header carries an `AdminDirective` of kind `REANCHOR` (02 §3.19.3), `reanchorOffsetMs += lag`, status RUNNING, and the coordinator appends the platform event `sys.clock_rebased {delayMs, fromTick}` (PUBLIC). The game calendar is never skipped; every tick number runs (no `ticks_missed_total` increment except the re-based delay counter required by 19 Rule 3.15.1).
4. Platform events decided by the host (`sys.world_status`, `sys.clock_rebased`, `sys.tick_committed`) are appended by the coordinator after the engine events of the tick (seq after the last engine event), stored in `engine_event`, and excluded from the engine `eventDigest`; the header directives and TickRecord make them reproducible.
5. Load levers (rule 3.3.4 item 4, 19#19): `LoadMonitor.decide` runs on platform metrics after commit of N and its decisions become `sys.load_scale` system inputs of the batch of N+1 (signed by the COORD key). A partition never changes behaviour from wall time or measured load. Wall-clock marks (R26, `ad_clock_mark_minutes` = 15) are added the same way.
6. Halt and resume (02 §3.20, which owns halt semantics): after a tick whose results contain an accepted `adm.halt_world` (validated by T19B-12 and 02's directive validator) or a safe-mode HALT, `onHalted` stops sealing; status HALTED_EXCHANGE; world time stops. Resume: an `adm.resume_world` system input is verified by the coordinator (signature, two approvals) while halted; `onResume` sets the first seal at `announceMs + resume_notice_ms` and re-anchors by the halt duration; the resume input is the first system input of that tick's batch. Gateways refuse new intents while halted (19C; 19D tests 19#59).
7. No quorum (19 §8 edge 20): `makeDurable` failing with `NoQuorumError` leaves the tick unsealed; retry every 100 ms; status CATCHING_UP is reported; intake continues to queue on INTAKE.
8. `world-loop.ts` runOne: wait until `nextSealAt`; broadcast SEAL(N); `entropy.forTick`; `platformInputsFor`; `sealer.seal`; `makeDurable`; `replyToGateways`; `runTickWithSafeMode`; `onCommitted`; publish status changes. Times come only from the injected clock.

## Test plan
`scheduler.test.ts` (pure):
- Worked example 1: genesis 0, tickMs 5,000, tick 10 commits at 54,950 (scheduledCommit(10) = 55,000 − 200 = 54,800, lateness 150): nextSealAt(11) = max(55,000, 54,950 + 200, 50,000 + 5,000) = 55,150.
- Worked example 2: CATCHING_UP, last seal 60,000, last commit 61,000, scheduled(12) = 60,000: nextSealAt = max(60,000, 61,200, 62,500) = 62,500.
- `19#18 after 3 late ticks, WorldStatus = CATCHING_UP is broadcast; after the backlog clears it returns to RUNNING; a re-base emits sys.clock_rebased`: 3 commits with lateness > 0 -> statusChanged CATCHING_UP exactly at the third; fast ticks with lateness <= 0 -> RUNNING; a run kept late for 120 ticks -> reanchor with deltaMs = lag and status RUNNING; a lag of 300,001 ms at tick 5 also re-bases immediately.
`world-loop.test.ts` (worker threads, fixture modules, fake clocks):
- `19#17 injecting a 7 s delay in P6 delays that tick's commit, commits nothing partially, and the next tick seals at least 200 ms after commit; no tick number is skipped`: fixture P6 hook busy-waits 7,000 ms on tick 20 (fake hard timeout 15,000): tick 20 commits late, no partition state of tick 20 visible before its record, seal(21) >= commit(20) + 200, the committed tick sequence is 0..40 without gaps.
- `19#19 a sys.load_scale decision appears in the next batch; replaying without the live load monitor reproduces the scaled AI results exactly`: a fixture AI module reads the load scale for its partition at P5 and scales its work; the monitor decides 0.5 at tick 30: batch 31 contains `sys.load_scale {partitionId, duScale: 0.5}`; replaying batches 0..40 through the reference driver (no monitor) gives identical stateHashes and fixture outputs.
- No quorum: memory bus quorum lost for 1 s: tick not sealed, status CATCHING_UP reported, then resumes with the next tick number.
- Halt/resume: accepted `adm.halt_world` at tick 50 -> no tick 51 sealed while halted; `adm.resume_world` -> tick 51 sealed at announce + 60,000 ms with a REANCHOR directive equal to the halt duration.
